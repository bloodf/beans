# Agent execution

`crates/agent` (`beans-agent`) is a port of pi-agent-core: `run_agent_loop` / `run_agent_loop_continue`, the same event sequence (`agent_start`, `turn_start`, `message_start/update/end`, `tool_execution_start/update/end`, `turn_end`, `agent_end`), steering and follow-up queues, `before_tool_call` / `after_tool_call` / `should_stop_after_turn` hooks, sequential or parallel tool execution, and `terminate` hints from tools, plus pi's harness behaviors: a model catalog with rates and windows, thinking levels, token usage and cost completeness on every message, compaction, and turn-level retry. Tool arguments are salvaged from cut-off JSON, coerced and checked against the tool's schema before a call runs (a failure is an error result the model reads), and never run from a message the token limit cut off; a `prepare_next_turn` hook can swap the context or provider between turns. A tool can declare an `output_schema` and return `structured` output beside its text, and return an error result (`is_error`) when a failure has output to go with it. A tool that calls other tools while it runs (`Tool::execute_with`) gets the loop's `ToolRunner`, which puts each call through the same argument shim, schema check, `before_tool_call`, and `after_tool_call` as the model's own, with the calling call as the hooks' `parent`. Every adapter puts the transcript through the same transform first (another model's thinking as text, failed turns left out, a result for every call, images downgraded for a text-only model) and retries a request that fails before it streams. A `Provider` turns a request into a stream of assistant events and never fails: errors become an assistant message with `stop_reason` `error` or `aborted`. The crate also ships `agent::harness::AgentHarness`, a general agent over the loop for hosts other than Beans (model switching through a provider factory, skills and prompt templates, queues, hooks, events, an example chat), with persistence left to the host; the Beans CLI uses the loop directly. `docs/agent/` is the crate's own documentation.

Provider HTTP attempt admission, response reporting, and default output-cap metadata are defined in [Providers](providers.md). The CLI's OpenCode header wrapper preserves the underlying adapter's default cap while adding routing headers; it does not derive a cap from catalog pricing or change unknown-cost handling.
The loop records token usage and the known dollar subtotal on each assistant message. A catalog entry without rates does not establish a known cost: `cost.known == Some(true)` only when every contributing call has known rates. Missing pricing remains unknown rather than zero.



```
on decrypted Job:
  build context from the chat (this bot's turns are assistant, other bots' text is user "[Name]: …",
                               this bot's tool rows become tool_call + tool_result pairs)
    + this turn's notes, which later turns leave out: the recent-work brief, the group's turn cue or
      a finished command's, "Continue." after the bot's own reply, a template bot's setup
    cache points: the rebuilt transcript's end, and where the last turn's ended
  run_agent_loop_continue(context, provider = the account's creds, tools, sink)
    events → job.started / job.finished / job.retry / job.thinking (chat, bot) → local app WS, which shows the bot at work
           → the turn and what it is doing (thinking, a retry) → this Runner's `machine` blob, which every
             other Device's CLI turns into the same events
           → each finished turn's usage → chat.usage (context size, cost so far)
           → a reply grows in chunks, not tokens: the text so far is re-sent at paragraph ends,
             or at a sentence end after 1.5 s of silence, never mid-word; the end sends it complete
           → every chunk and every completed message is encrypted with the account DEK → relay,
             so a paired phone watches the reply grow the way the local app does
    tool calls execute: each call's row goes up as the app sees it when the call starts, for the
                        status line on other Devices, and whole when it ends
  a pending confirmation or a turn ending with a reply or failure → an encrypted phone push (see [Notifications](runtime.md#notifications))
```

Turns in one chat run one at a time on a Runner. A direct turn registers an `AgentMessageQueue` from `crates/agent` while it owns the chat lock. A new user message goes into that queue, and the agent loop drains it at its next safe boundary: the current provider step and any tool calls finish, then the message is added before the next provider call. Until then the message is `queued`: the Runner marks it before it pushes it and clears it when the turn reads it (the promotion), when a turn starts on it as its trigger, or on Stop, so every Device shows it waiting with Send now under it. `chats.send_now { chat_id, message_id }`, here or sealed to the bot's Runner as a `request`, has the turn read it at once (`turns::send_now`): every command running in the chat goes to the background and runs on (`Sessions::background_chat`, so a call waiting on one returns), then the turn's `StepInterrupt` cancels the step, so a reply in progress stops where it got to (its words stay a bubble) and other tools are cancelled, and the loop reads its queue. Send now is for direct chats. A question never holds a message back: the user's message dismisses whatever the chat's turn is asking them (a command's card or a permission card; `mcp::dismiss_questions`), the action does not run, and the call returns telling the bot the user wrote instead of answering, with a hint that ends the run unless the message is there to read next. A question that would go up while the queue holds a message is dismissed without asking. In a group, where a member's turn has no queue, the dismissed call ends the member's turn, and the room the message admitted answers it. Every message still admits a Job, so delivery survives Device races; the active turn marks messages it actually promotes, and those Jobs exit when they later reach the chat lock. In a group, a newer room waits while the current member settles, then takes the lock before another member starts. `chats.stop` is separate: it cancels active and waiting jobs immediately and sends a sealed `job_cancel` to another Runner.

An unread user message also releases a `bash_output` wait on a background command without stopping it. `hear_user_message` queues steering before waking the chat's background sessions; `TurnSessions` reads the active steering queue. The loop then consumes the message at its next safe boundary. Foreground commands and `bash_input` waits are not interrupted by this notification, and no new work or update admission is created.

The loop bounds cancellation waits for `before_tool_call` and execution futures with the one-second `STOP_GRACE`, in sequential and parallel batches and child calls through `LoopRunner`. Each top-level call owns a separate `ExecutionScope`; registered pipe workers survive disposal of parent or child execution futures. A cutoff closes admission before disposing execution, then drains its inclusive scope subtree before execution-end, run completion, or Send now promotion. Codemode also closes, cancels, disposes remaining calls after its existing wind-down, and drains on every script exit, including normal completion and independent timeout. Bash alone starts its existing total one-second cleanup deadline when it observes cancellation; scheduling and result formatting can delay return, so loop completion has no strict wall-clock bound. Cutoff exposes only bounded cleanup counts and a sanitized failed-call identity, never child output or structured objects. Current-state authorization still runs synchronously immediately before prepared top-level or child execution. Normal child finalization remains; event sinks, other hooks, non-yielding work, arbitrary external task abortion, and runtime teardown are not graceful-completion guarantees. `AgentLoopConfig` keeps its existing fields.
