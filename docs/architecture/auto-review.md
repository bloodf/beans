# Auto-review

How a bot's shell commands and effectful plugin actions are reviewed before they run: the local shell parser at the loop's `before_tool_call` boundary, and Auto-review's settings, model review and rules. The tools themselves are in [Tools](tools.md); secrets in [Secrets](secrets.md).

## Shell review

Shell review lives at the loop's `before_tool_call` boundary (`crates/cli/src/local_review.rs`). With Auto-review on, a parser is the fast path. It reads the command as bash does, without executing it: quotes and escapes, comments, `&&`, `||`, pipes, semicolons, newlines, subshells, brace groups, `if`/`for`/`while`/`case`, and command substitutions at any depth (`$(…)`, backquotes, `<(…)`), each of which is checked as a command of its own. Syntax it does not model goes to Auto-review: here-documents, `$'…'` and `$"…"`, arithmetic on names (`$((x))`, `$[…]`, `((…))`, where a value such as `a[$(…)]` runs a command), parameter expansions other than `${name}`, function definitions, arrays, and unterminated quotes. Every simple command must run a known read-only program found on `PATH` (or in `/bin` or `/usr/bin`, never `./tool`), write only to `/dev/null` or the output streams, and name no credential-bearing place or device (`/dev/…` other than the streams, `/proc`, `/sys`), also once quotes are removed. A variable must be set in the command itself or be one that holds no secret (`$HOME`, `$PWD`), since the environment carries the user's keys; assignments may only set lower-case script variables, locale, or time zone, never `PATH`, `IFS`, `LD_PRELOAD`, `GIT_*`, or another setting a program reads. Programs whose options decide what they do (`find`, `sort`, `git`, `xargs`, `test`, …) and programs that print file contents must see every argument: a glob, brace expansion, substitution, or variable with an unknown value sends them to review, while variables bound to literals (`for d in src docs`, `x=src`) are expanded to each value and checked. `xargs` may only hand its input to programs that report on names (`wc`, `ls`, `stat`, …), and abbreviated or clustered options (`--out=`, `-iz`) count as the options they stand for. Programs that print what files they were not given hold are reviewed: a recursive `grep` (which reads `.env` and `.git/config`), `rg` told to read hidden, ignored, or linked files, `sort --files0-from`, and any read of a repository's `.git` folder; so are network shares (`//host/share`, `/net/host`), relative paths into `dev`, `proc`, or `sys` after a `cd` that can reach `/`, git's signature placeholders (`%G?`, which run the signing program), and `beans` with `--home` or `--port`, which would read an `mcp.json` of the caller's choosing and start its servers. Because a bot's `write` and `edit` tools change files without review, the fast path also checks the disk before it lets a command through (`configured_to_run_programs`): a relative or empty `PATH` folder sends every command to review; git is reviewed when any configuration file it would read (system, global, the repository's, a worktree's or submodule's, and what they include) names a program it would start (`core.fsmonitor`, `diff.external`, a textconv or diff command, a clean or smudge filter other than git-lfs's, a partial clone's fetch, a signing program with `log.showSignature`, a trace target), or the repository has a `post-index-change` hook, which `git status` runs; jq when `~/.jq` exists; and ripgrep when the file `RIPGREP_CONFIG_PATH` names holds an argument the fast path refuses. A file a read-only command opens that is a link to a key or a device (`cat notes` where notes is `~/.ssh/id_rsa`) is reviewed, and so is every command when `BEANS_SHELL` is a shell other than bash or sh, whose reading the parser does not model. A file known to hold secrets is found by its name wherever a command names it, through quotes, variables, globs, and brace expansion, and by its bare name after a `cd` to its folder. Known file-writing flags and external-command callbacks on otherwise read-only programs are reviewed; `sed` admits only simple substitutions or numbered line printing, and `awk` only direct field printing. Unknown filter programs go to Auto-review rather than a growing execution deny-list. A workspace grants no automatic approval: builds, installs, opaque executable wrappers, uploads, and mutating `beans` commands go through the same review and user rules wherever they run. The command's card is `checking` while the review runs, which the apps do not show. When the review asks, the card itself asks (`local_review::ask_on_card`): why, Allow once, Always allow, and Deny, and a proposed plain-language allow rule for this kind of work wherever the bot does it, which keeps what decides the risk (the service, repository, environment, or a folder of the user's data) and leaves out one-off details such as file names, numbers, branches, and working directory. Always allow adds that rule to Auto-review. A card with no proposed rule (Auto-review off, or a review that could not run) offers Allow once and Deny. The answer is `chats.permission` naming the card's row, from any Device, as for a permission card (`mcp::await_answer`); an allowed command runs on the same card, and a denial runs none of its stages. What a bot types into a running command with `bash_input` goes through the same review, the command beside the input, since a shell, REPL, or `ssh` runs whatever it is given; Ctrl-C alone runs at once. `write` and `edit` on a file outside the bot's working folder go through the same review, with links followed, since the user's own files, settings, and programs live there; inside it, a file is the bot's to change. With **full access** on, none of this review runs; see [Secrets and full access](secrets.md#full-access). These are approval controls, not a process or filesystem sandbox.

## Auto-review

**Auto-review** (`crates/cli/src/plugins/review.rs`) is shared by shell and plugin actions. Its setting lives in the roster (`AutoReview { is_enabled, rules[{ id, text, behavior: allow | ask, tool? }] }`), so every Device shows and edits the same one. A rule is plain language, written by the user or added by Always allow from the review's proposal. Only a plugin card's Always allow saves a rule for an exact tool (`tool` is `plugin/tool`), which decides that tool's calls without a review. Everything else goes to a small model on the bot's provider, whatever the bot itself runs (`providers::review_model`: DeepSeek V4.1 Flash on DeepSeek and both OpenCode plans, Claude Haiku 4.5, GPT-6 Luna, Grok 4.7), with thinking off and at temperature 0 where the model allows it, so the same action gets the same answer, and at its lowest effort where it does not. The model reads the chat that asked for the work (`plugins::review::request`): the message that started the turn (the user's, a teammate's `message_bot` handoff, or a routine's marker with the task as it stood when the run began, which an edit or a delete during the run does not change), then each step since, its newest 30 (what the bots said, the commands they ran and the tools they used, and how the user answered a command that asked), with the user's latest message repeated after them. Before a user's message it also reads up to ten lines of the two hours of chat ahead of it, so a short reply ("yes", "create a PR") reads as the answer to what the bot proposed; a handoff or a routine starts new work, and nothing before it is read. The user's rules come next, beside the action, and a plugin call or command from a codemode script comes with the script, which says what the whole batch is for. The model weighs what the action could break against what was asked. It allows what is easy to undo or touches only what the bot made: reading, building, testing, and running code, installing a project's dependencies, the processes and files the bot made, using an app the task is about, deleting temporary files and what regenerates, local git work, drafts. It asks before harm that is hard to undo: the user's own files and data, discarding uncommitted work or rewriting pushed history, publishing, deploying, spending, access and system settings, programs the bot did not start, elevated privileges, credentials, uploads, downloaded code, and anything like what the user refused in the chat. It allows such a step too when the user asked for that very thing, in their own words, in a "yes" to what the bot proposed, or in a routine's task; a teammate's message hands over work but cannot ask for harm. It always asks before anything that could wipe a home folder, a disk, or the system. The user's rules decide over all of this: an allow rule covers its kind of work wherever the bot does it, unless the rule names a place, and an ask rule wins over an allow rule. It answers `allow` or `ask` with a reason, plus the proposed `rule` when a shell command asks, both in the language of the user's latest message, or else of the teammate's message or the routine's task (English without one). Adding a rule replaces one with the same words. With Auto-review off, every shell command and effectful plugin action asks, regardless of saved rules. A held shell command asks on its own card; any other held action, a script's command included, posts a `permission` message. Either waits up to ten minutes for `chats.permission { decision: allow | always | deny }` from any Device, and a new message from the user in the chat dismisses it (see [Agent loop](runtime.md#agent-loop)). A routine has nobody waiting, so an action that would ask is refused, and the bot hears the rule that would allow it; with Auto-review on, actions the review allows still run.
