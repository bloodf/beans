# Bot automation

## Routines

See [Routine scheduling](routines.md). The execution owner also requires [routine admission](tasks.md#routine-checks-and-retention).

## Attention

A run is a `routine` Job in the bot's DM. It opens with a "Routine · Name" marker (a system notice carrying the routine id), then the turn runs with the routine's prompt as the task and a system prompt that says nobody is typing: the bot does the work, replies with what the user should know, or answers `PASS`, which leaves only the marker. Later turns rebuild the marker as `[Routine "Name" ran on its schedule. Task: …]`; the daily log names the routine as the turn's source. `job.started` / `job.finished` carry `routine_id`, so the apps show the routine as running and the bot at work. A run's outcome (`sent`, `pass`, `error`) is kept on the routine. Run Now from a Device that is not the Runner seals the job to the Runner like any turn.

**Checks.** A routine that watches for something (an inbox, a repository, a feed, a page) carries a `check`: JavaScript the Runner runs at each due time before the bot does, without a model, so an interval with nothing new runs no turn; only the small-model calls a check makes with `models.ask()` cost anything, in the chat's spending. The bot writes it with the `routines` tool (`check`, at most 8,000 characters; `""` on edit removes it). It runs as a codemode script (see [Codemode](plugins.md#codemode)) in a sandbox of its own (`routines::run_check`, five minutes at most) whose calls only read: the bot's `read`, `grep`, `find`, and `ls`, and the plugin tools whose manifest lists them as read-only or whose server marks them `readOnlyHint`, the same test Auto-review applies. `CheckRunner` refuses any other call, which ends the check. `store()` and `load()` reach the values the bot's scripts keep in its DM, so a check keeps what it has seen and returns only what is new, and `models.ask()` can screen items on the small model. What the check returns starts the run: a `routine` Job whose `check` carries it as text (at most 4,000 characters), which the turn reads after the transcript as tool data, not instructions; Auto-review reads the routine's task, never what the check found. A check that returns nothing, `null`, `false`, or an empty string, list, or object ends there: no marker, turn, or roster write. The Runner keeps the time each check ran in memory (`routines::Checks`), the schedule counts from it, and the local app hears the routines again (`roster.changed`, sent and not uploaded) so it shows the next check. A check that fails starts the run with its error, so the bot does the task without it and fixes or removes the check. Saving a check runs it once, in the turn that saved it, and hands the bot the result, so a broken check shows at once and its first run records what is already there. Run Now runs the check first, then the turn whatever it found. One check of a routine runs at a time: a check on save or Run Now waits for one already running (`routines::check_now`). A due check that finds something while a run started by hand waits for it still starts its own run, after that one, since the waiting run's check no longer sees what the first one stored as seen. The roster carries `check` so every Device shows it, and only the Runner writes it: a roster from a build without the field keeps the Runner's check (`routines::keep_checks`) and goes up again with it. Other Devices never hear of empty checks, so a past-due routine with a check shows as due at its next schedule time.

A routine is a task a bot runs on a schedule in its direct chat, on its assigned Runner. The roster carries its schedule, timezone, missed-run policy, and check health. See [Routines](routines.md) for scheduling, read-only checks, recovery, and how the apps show them.

A service's events start work in a bot's DM too, through [event subscriptions](event-triggers.md) on its Runner: each runs the subscription's own task, unattended as a routine's run is, and one that targets a routine waits while the routine is paused.

A workflow adds the routines it needs paused, and `routines.set_enabled` keeps one it added off until the user has read the workflow's sample; a routine of the user's that a workflow reuses keeps its own state: [Workflow onboarding](workflows.md).

## Saved workflows

A saved workflow is a bot's definition kept in the roster beside its routines (`WorkflowRecord { id, bot_id, name, definition, created_at }`, `workflows.create` / `workflows.list` / `workflows.delete`). A `definition` is `{ version: 1, revision, steps }`, one to 20 steps of a `prompt` (at most 8,000 characters), optional `tools` (at most 16 unique names, each as the agent lists it: a built-in such as `read` or `bash`, or a plugin tool by its catalog name, `<plugin>__<tool>`, letters, digits and `_` only) and an optional `approval` flag, at most 64 KiB in all; any other field is refused. A bot keeps 20 workflows with distinct names. `workflows.create` refuses the create at either bound and writes nothing, naming the bound and telling the caller to delete a workflow first, because the roster admits the record and counts it under the same lock. Nothing runs a definition, and a definition grants nothing: only the bot's Runner saves one, and it refuses a tool the bot's live capabilities deny or that is not one of the bot's own tools or a tool a plugin installed there last offered. The roster keeps the definition as the JSON it was saved with, so a newer schema passes through any Device untouched. A record that arrives over a bound (a 64-character id or bot id, a 60-character name, 64 KiB), for a bot the roster does not have, or under an id that appears twice is not taken: the definition this Device already holds under that id stays, a new one is skipped, and the rest of the roster applies. Over 20 per bot or 256 in all, the records already held win and the rest are taken in id order, whatever order they arrive in. Status never travels; each Device works it out. `workflows.list` marks a definition `unavailable` when it fails a check later (a newer schema, a revoked tool) and `unverified` on a Device that is not the bot's Runner; it never deletes or rewrites one. Deleting a bot deletes its workflows (`crates/cli/src/workflow.rs`).
