# Bots, Routines, and Memory

## The lead bot

A new identity starts with one bot, **Chef**, a chief of staff on the first Runner: an ordinary bot whose description has it plan the work, delegate each task to the right teammate with `message_bot`, propose a new one for `create_bot` when none fits, and do hands-on work when necessary. Nothing about it is privileged; rename or delete it like any bot.

A chat has a `kind`. A DM is one bot and never gains or loses members; there is one DM per bot. A group holds one to six bots, can add or remove them after creation, and has an `owner_bot_id` (the bot holding the work, marked as the owner in every member's system prompt; defaults to the first member, and moves to the first remaining one when the owner leaves). `chats.set_owner` changes it: in the macOS and Windows/Linux inspectors the owner's row reads Owner, and a click or right-click on a member of a group with several offers Make Owner beside Remove from Chat; on the phone, tapping a member in Details makes it the owner; `beans chats set-owner <group> <bot>` does it from a terminal. A group may also carry a `description`, what it is for in the user's words, which every member's system prompt gives below the member list; `chats.set_description` changes it, and a DM has none, since its bot's own description says what it is for. The macOS and Windows/Linux inspectors show a group's Name and Description in a Group section (Description's Edit… opens an editing sheet), and the phone's Group Info has the same two rows, Description pushing a full editor.

Creating a bot reserves its own DM and persists both profiles plus the pending chat-creation marker in one local SQLite transaction before publishing one roster change. A preferred DM id that already belongs to any chat is refused before either object is created; a failed store write leaves neither an orphan bot nor a published capability policy. Other Devices first see the bot and its DM together.

Bot profiles carry optional generated `look` settings independently of the photo in `avatar`. `bots.create` validates the look before image storage; `bots.update` keeps omitted look, resets null, and replaces an object draft. Both travel in the encrypted roster with fieldwise sync. See [Bot avatars](avatars.md) for the contract and protocol-5/`beans-v2` writer requirement.

Deleting a bot removes its DM and routines and removes it from every group. A group with other bots keeps its transcript and moves ownership when needed; a group whose last bot was deleted is removed. The macOS sidebar treats Delete on a DM as this bot deletion and says so in its confirmation sheet. Deleting a group removes only that chat.

Who answers, after Grok Bot's rooms:

- **DM:** its bot, always. An `@Name` is a reference the bot acts on: it calls `message_bot`, which delivers the message into that bot's own DM with the user, where that bot answers (and can message back).
- **Mentions:** picking a bot from the composer's `@` menu records its id, and `chats.send` carries the picks as `mentions`. The CLI keeps the picks whose `@Name` is still in the text, adds any other `@Name` that only one bot answers to, and stores the ids on the message (`Body::Text.mentions`). A bot reads the first `@Name` of each as `@Name (id bot-1a2b3c4d)`, so a name two bots share still says which one the user meant.
- **Replies:** a user message can answer an earlier text message, the user's or a bot's. `chats.send` carries its id as `reply_to`, and the CLI keeps a quote with the reply (`Body::Text.reply_to`: the message's id, its author, and its words as plain text on one line, at most 280 characters), so every Device shows it where the original has not loaded. A bot reads the quote ahead of the user's words (`[Replying to your message: "…"]`, or Scout's message, or their earlier message), and in a group the bot whose message is answered takes its turn right after the ones the message mentions. The macOS and Windows/Linux apps offer Reply on a bubble's right-click, the phone on a swipe to the left; the composer shows "Replying to Name" and the quote until the message goes, Escape or its button drops it, and the sent bubble carries the quote above it, which scrolls to the original and pulses it when clicked.
- **Attachments:** a user message can carry files. Their bytes travel as `file` blobs; before a turn the Runner fetches any it lacks (`files::prefetch`), copies each into the bot's workspace at `attachments/<attachment id>/<name>` (a stable path, so every turn names the same file), and the transcript's user message gets a line per file naming that path, plus the pixels as an image content part made one a model takes (`files::inline_image`, through `beans_agent::images`: converted, turned upright, or scaled down to fit 2000×2000, with a note; a HEIC converts on a Mac), else a line saying why not. It is made once, before the turn that first shows it (`files::make_images`), and kept beside the attachment as `<id>.inline.json`, since every turn builds its messages again. A request carries only the latest 20 images ([providers](../agent/providers.md#before-conversion)), so a long chat's older ones are left out and the bot reads the file again to see one, so a vision-capable model sees it and any model can open it with its tools.
- **Group:** a room exchange (`run_room`). The Device that received the user's message offers every member a turn, one at a time, in chat order with the members the message mentions first. A member's turn is a `room_turn` Job with the whole transcript plus an ephemeral cue (round number, how many messages are new to it); the member replies to the group or answers `PASS`, which never becomes a bubble. A round with at least one reply is followed by another, offered only to members that have heard something new; the exchange ends after a silent round or after the fourth round, which is marked winding down so members add only what is essential. A new user message waits for the current member's turn, including its command, to settle; the old room then yields and a replacement room starts with the new mentions first. **Stop** cancels immediately. A member on another Runner gets its job through the relay and reports back with a `job_result` blob (`sent`, `pass`, `error`) sealed to the requesting Device; the room waits up to five minutes for it and skips an offline Runner.
- **Bot to bot:** `message_bot` from any chat to a bot outside it; the message lands in the target's DM. Each hop carries `hops`; after eight bot-to-bot hops without a user message the tool refuses, so two bots cannot loop. Members of one group talk to each other in the group.

The encrypted roster also carries account-wide Pause (`account.pause { paused }`). Each explicit Pause or Resume, bot capability edit, and bot deletion is additionally an encrypted `policy` action with a logical version; Devices reconcile those actions against roster snapshots before uploading offline edits. A later explicit Resume or capability relax takes effect, while an unrelated stale roster edit cannot lift a restriction or restore a deleted bot. Every paired Device sees Pause; a Runner stops current turns, refuses new jobs, and skips routine checks once the change syncs. An offline Runner cannot learn the change until it reconnects, and a tool's already-issued external effect cannot be undone. Each bot's `capabilities` controls shell, `write`/`edit`, and an optional installed-plugin allowlist at call time, including calls inside codemode. Legacy bots remain unrestricted. These controls are not process isolation: shell may still write files when allowed, and an allowed plugin may perform writes. Separate Runners provide the isolation boundary.

## Routines

A routine is a task a bot runs on a schedule in its direct chat with the user, after Grok Bot's routines: a morning brief, an hourly check, a weekly report. The bot owns its routines: the user asks for one in chat and the bot sets it up with the `routines` tool (a name, a schedule, the prompt, written as an instruction to itself, and a check when the routine watches for something), and edits, pauses, resumes, runs, or deletes it the same way. The system prompt of every turn explains routines and lists the bot's own with each one's next run, or that it checks first.

The roster also carries Auto-review (see [Plugins](plugins.md#plugins)). Routines live in the roster (`Routine { id, bot_id, name, prompt, schedule, timezone, missed_run_policy, last_scheduled_at?, pending?, health?, is_enabled, enabled_at, last_run_at?, last_outcome?, paused_reason?, check?, created_at }`), so every paired Device lists them and can pause, resume, run, or delete one (`routines.create` / `routines.update` / `routines.delete` / `routines.run`, and `routines.describe` to read a schedule back). The bot's assigned Runner runs them (`crates/cli/src/routines.rs`): every half minute it starts due routines or their checks, never taking over another Runner's routines or overlapping a routine's run and check. The local API reports `state`: `on`, `running`, `paused`, `waiting_for_runner`, `failed` or `blocked`.

A schedule (`crates/cli/src/schedule.rs`) is `every 30m`, `every 2h`, `every 1d`, or five cron fields (`0 9 * * 1-5`). Cron reads the routine's saved IANA `timezone`, defaulting at creation to this Device's zone, or UTC when unavailable. A daylight-saving gap skips that firing; a repeated minute fires only at its earlier instant. Intervals count elapsed seconds from the latest run, completed check, taken due time or creation/resume. The CLI supplies `schedule_text`, `next_run_at` and `is_running`. After missed due times, `coalesce` (default) runs once, never a burst; `skip` consumes a due time more than a minute late without running. The Runner takes update admission before saving the checkpoint; failed persistence rolls it back and starts no work.

Interval parsing rejects values longer than 366 days, including integer multiplication overflow, before a routine is created or edited.

The due cursor and a `pending` intent commit together through the existing routine JSON transaction, after update admission and before dispatch. An explicit `skip` commits only the cursor. Pending work carries one stable Job and phase: `check`, `checking`, `model`, or `running`. Restart dispatches unstarted `check` or `model` intent even when its cursor already points past the missed firing. A completed check saves health and either its model Job/report or quiet/blocked completion atomically. Before executing a check or model turn, the Runner persists the corresponding `checking` or `running` effect-start fence; failed persistence starts no work. Model completion clears only its matching Job intent.

After the durable model intent exists, dispatch saves and publishes `last_run_at` before `job.started` and before waiting for the chat lock. A failed timestamp write dispatches nothing and retains the recoverable intent. This queued-start timestamp does not mark effects as started: the pending phase stays `model` until the turn validates its admission conditions and commits the `running` fence.

Claims and explicit skips revalidate the current enabled/account-Pause state, assigned Runner, schedule, timezone, missed-run policy, check, re-arm time, due cursor, and computed firing inside the same roster/state transaction that saves them. A winning edit, disable, Pause, or Runner reassignment rejects a stale tick snapshot. The timestamp and both effect-start transitions recheck current authority and the exact pending binding before publishing a start or admitting effects. The existing DM is resolved under that state lock; missing DMs reject non-skipped claims without consuming their due cursor.

Pending intent saves its schedule binding after the claimed cursor advances. A genuine inactive-to-enabled resume retains unstarted work and explicitly refreshes its binding; redundant enable neither re-arms nor authorizes missing bindings. Older pending JSON without a binding loads blocked and cannot run automatically; the user pauses and resumes it explicitly. Started uncertainty is never rebound or replayed. Owned mutation holds account lifecycle admission through the commit; device identity is captured before taking the state mutex, while enabled/Pause/bot/Runner checks remain inside it.

Queued offline timezone and missed-run policy edits participate in the existing fieldwise roster rebase, so an unrelated remote rename does not erase them. Name and prompt edits keep their existing semantics; the scheduled check fence rejects changed check/re-arm identity, while execution reads the current bot/provider record.

A crash after an effect-start fence leaves uncertain work: provider requests, script-store writes, or tools may already have acted. Such `checking` or `running` intent remains `blocked`, is never automatically replayed, and prevents further scheduled work and Run Now. After reviewing possible effects, the user explicitly resumes the inactive routine to discard only that uncertain intent and re-arm its schedule. Resume retains unstarted `check` or `model` intent. Resume refuses while local routine work remains active. Other Devices cannot replace the assigned Runner's pending intent through a stale roster. This provides recovery before launch and no automatic duplication after ambiguous effects, not exactly-once external execution.

Away auto-pause retains pending intent. Resume retains unstarted `check` and `model` work, while discarding only uncertain `checking` and `running` work. Schedule, timezone, or check edits revoke unstarted intent before re-arming, but retain effect-started uncertainty. When merging roster edits, the assigned Runner preserves its unstarted intent unless the incoming edit re-arms the schedule; effect-started uncertainty remains owned until local explicit resume or matching completion.

A run is a `routine` Job in the bot's DM. It opens with a "Routine · Name" marker (a system notice carrying the routine id), then the turn runs with the routine's prompt as the task and a system prompt that says nobody is typing: the bot does the work, replies with what the user should know, or answers `PASS`, which leaves only the marker. Later turns rebuild the marker as `[Routine "Name" ran on its schedule. Task: …]`, so the bot can talk about a run afterwards; the daily log names the routine as the turn's source. `job.started` / `job.finished` carry `routine_id`, so the apps show the routine as running and the bot at work. A run's outcome (`sent`, `pass`, `error`) is kept on the routine. Run Now from a Device that is not the Runner seals the job to the Runner like any turn.

**Checks.** A watching routine carries JavaScript `check` (at most 8,000 characters; `""` on edit removes it). Each due check runs without the bot's model in its own five-minute codemode sandbox. It may use `read`, `grep`, `find`, `ls`, read-only plugin tools, `store()`, `load()` and `models.ask()`; capability and account Pause checks remain in force. Values share the bot's DM script store. Findings become a routine Job's `check` report (at most 4,000 characters), marked as tool data, not instructions. Auto-review reads the routine task, never findings. Returning nothing, `null`, `false` or an empty string, list or object runs no turn and leaves no marker. Saving a check runs it once and returns its result. Run Now checks first and then runs regardless of findings, except an authentication-paused routine requires explicit resume. Checks on save or by hand wait for an in-flight check; `Checks` retains cancellation tokens only while work runs.

Check health and schedule anchors persist before a finding admits its model turn. Health records check/success times, categorized status, connection/authentication failure counters and retry time, never raw errors or credentials. Quiet status changes, failures and recovery upload the roster; another quiet check saves locally without uploading. Connection failures back off from five minutes, doubling to six hours. Three consecutive authentication failures pause with `paused_reason: authentication`; reconnecting and resuming clears retry state. Model-provider failures have their own nested `health.model` streak, unaffected by quiet checks. Script failures hand their error to the bot; blocked tool calls do not start a scheduled model turn. Stale roster edits preserve the assigned Runner's newer health and taken due time unless a schedule/check edit or explicit resume re-arms the routine. Other Devices show an overdue next firing from now. [Local API](local-api.md#bots-and-chats) specifies the exact health fields.

When the user has not written in any chat for seven days, due routines are paused instead of run (`paused_reason: away`) with a notice in the bot's DM, as Grok Bot does, so nothing keeps spending on results nobody reads; the switch turns them back on.

The macOS app's DM inspector has a Routines section: a row per routine (clock, pause, or running icon; the schedule in words and the next run, or the next check; a switch that pauses or resumes) that opens a sheet with the state, schedule, next run or check and last run, the prompt, the check in a monospaced block when there is one, and Run Now, Pause/Resume, Edit in Chat (which puts `Edit my routine "Name": ` in the composer), and Delete. With none, the section says routines are set up by asking the bot. The Windows and Linux app's sheet is the same. The phone's chat details show the same list with a switch; a tap offers Run Now and Delete.

## Saved workflows

A saved workflow is a bot's definition kept in the roster beside its routines (`WorkflowRecord { id, bot_id, name, definition, created_at }`, `workflows.create` / `workflows.list` / `workflows.delete`). A `definition` is `{ version: 1, revision, steps }`, one to 20 steps of a `prompt` (at most 8,000 characters), optional `tools` (at most 16 unique names, each as the agent lists it: a built-in such as `read` or `bash`, or a plugin tool by its catalog name, `<plugin>__<tool>`, letters, digits and `_` only) and an optional `approval` flag, at most 64 KiB in all; any other field is refused. A bot keeps 20 workflows with distinct names. `workflows.create` refuses the create at either bound and writes nothing, naming the bound and telling the caller to delete a workflow first, because the roster admits the record and counts it under the same lock. Nothing runs a definition, and a definition grants nothing: only the bot's Runner saves one, and it refuses a tool the bot's live capabilities deny or that is not one of the bot's own tools or a tool a plugin installed there last offered. The roster keeps the definition as the JSON it was saved with, so a newer schema passes through any Device untouched. A record that arrives over a bound (a 64-character id or bot id, a 60-character name, 64 KiB), for a bot the roster does not have, or under an id that appears twice is not taken: the definition this Device already holds under that id stays, a new one is skipped, and the rest of the roster applies. Over 20 per bot or 256 in all, the records already held win and the rest are taken in id order, whatever order they arrive in. Status never travels; each Device works it out. `workflows.list` marks a definition `unavailable` when it fails a check later (a newer schema, a revoked tool) and `unverified` on a Device that is not the bot's Runner; it never deletes or rewrites one. Deleting a bot deletes its workflows (`crates/cli/src/workflow.rs`).

## Memory

Every bot keeps its own long-term memory on its Runner, in Grok Bot's shape of a curated profile over append-only logs, as plain markdown under `~/.beans-v2/workspaces/<bot id>/` (keyed by id, so a rename or a changed working directory never moves it; `crates/cli/src/memory.rs`):

- `MEMORY.md` is the curated memory. Its first 200 lines or 24 KB, whichever cuts first, open in every turn's system prompt; past that nothing loads, and the prompt tells the bot how much is cut off and asks it to consolidate. The bot writes it only through `memory_update`, one dated entry per call (`- 2026-09-17 · from your chat with the user · the user prefers short replies`), never a whole-file write, so two of its turns cannot clobber each other: `append` adds a fact (an exact duplicate is refused), `replace` rewrites one unique passage, `supersede` strikes the old entry through with a date and adds the new fact so the file shows what changed, `remove` deletes a passage.
- `memory/<topic>.md` files hold longer notes the bot reads with `read` when it needs them; the prompt lists their names.
- `memory/log/YYYY-MM-DD.md` is the bot's diary: what happened, not what is true. The Runner appends one line per finished turn (`- 09:05 · in group "Standup" · said "Sent the three flagged invoices…" · used bash, edit`), and the bot adds events with `memory_log`. Logs are never loaded into a prompt; `recall` finds them.

Every write is atomic and goes through a credential scrubber first (API keys, AWS and GitHub tokens, bearer tokens, JWTs, private key blocks, `password: …` values become `«redacted N chars»`), since memory is bot-authored as often as person-authored.

Two things keep a bot's chats from being islands, after OpenMausBot. Every turn carries a **recent-work brief**, a bracketed note after the transcript: the newest thing the bot said in each of its *other* chats over the last two days, at most ten lines and about 350 tokens, newest first (`- today 09:05 · group "Standup" · you said: "…"`), so a bot in a group knows what it did in its DM an hour ago without the transcript. It stays out of the system prompt, which it would change each time the bot speaks elsewhere, costing the chat its prompt cache. And `recall` searches the memory files and every chat the bot is in by words and by time, naming the chat and the speaker of each hit.

Before a compaction summarizes part of a chat, a silent **memory flush** turn runs over the messages about to be cut, with a prompt to save what is durable and not yet in memory, and only `memory_update` and `memory_log` run; nothing it says reaches the chat, a failure or a two-minute timeout is logged and the compaction goes ahead (`BEANS_MEMORY_FLUSH=0` turns it off). A compaction of a turn's own context (before the turn, or between its model calls) asks the flush as that turn's next request: the turn's system prompt, tools, and every message, then the prompt naming the message the kept part starts with, so the provider's prompt cache serves the context, and the hooks refuse every tool but the two. Any other compaction asks it as a request of its own, with only those two tools, over the newest of the history one request may carry. This is what keeps a fact from being lost because it was only ever said in conversation.

The macOS app's DM inspector shows the bot's memory (`bots.memory`): the index against its load budget, an editor (`bots.memory.write`, refused with the bot's current text when the file changed under the editor, then Reload or Overwrite), and a Show button for the folder. For a bot on another Runner the CLI asks that Runner through the relay (a `request` / `response` pair, see [Protocols](protocols.md)), so the same rows read and edit it; only the folder cannot be opened, and an offline Runner shows as such with a Retry. The phone shows no memory yet.
