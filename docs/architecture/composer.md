# Composer

Existing presentation and transport: [macOS chat](macos-chat.md#composer), [Windows/Linux app](desktop-app.md), [phone app](phone-app.md).

## Selected shared action and reference contract

This discovery selects future consumers of each bot's permitted context, commands and skills. Current mechanisms remain unchanged. Selection never sends, runs tools or grants access; palettes, typed transport and skill activation remain implementation work.

### Target and catalog ownership

The DM target is its exact bot ID. A group requires an explicit current member as the catalog target before `/`, `$` or bot-scoped context can be selected; never choose the first mention, owner or most permissive member implicitly. Changing that target invalidates existing bot-bound selections and asks for reselection, not silent rebinding. `@` continues to mean a bot mention, not a skill, file or authorization token. Group turn order remains separate from the selected action target.

Catalog requests bind the current account identity, selected relay membership and profile/session, actor Device, chat ID, target bot ID, assigned Runner ID and current key bindings. A profile/session is a client source-selection boundary, not a new account entity or display-name lookup. A future adapter must supply an opaque source-binding token for these boundaries; missing membership/profile authority disables typed selections rather than inventing IDs from relay URLs. Account, membership and profile IDs are distinct from human labels. Renames preserve IDs; duplicate names show kind, target and origin disambiguation. Deletion/recreation, reassignment to another Runner, membership/key change or plugin reinstall never inherits an old reference by matching a name/path.

One core-owned, read-only catalog projection supplies all clients with grouped entries for Attachments, Context, Commands, Skills and Status. Each entry has a stable opaque entry ID within its source binding, discriminated kind, bounded label/description, target/Runner IDs, origin, revision, preview availability and closed availability/reason codes. Authorization-filtered entries exclude other memberships/profiles and resources the target cannot inspect. A disabled row may describe a known permitted capability that needs setup, but may not reveal another principal's private resource, account instance or metadata. Cached labels are advisory and untrusted; markup, instructions and resource bytes are not catalog authority. Search is local over an admitted bounded page; truncation states that more results require explicit paging, never an unrestricted scan of Runner files or chats.

The proposed projection reads admitted local metadata only. Existing codemode search/namespace lookup can connect servers; it is not a safe composer browsing adapter. Built-in agent tools, plugin tools, app menu commands and saved workflow definitions are separate inventories, not automatically `/` commands. A command needs an explicit core-owned command ID, bounded argument schema, bot capability requirements and declared effects before admission. A skill needs an enabled, granted, installed-instance/content binding; discovered or copied metadata alone never qualifies for `$`.

### Syntax, completion and literal text

- `+` is a button, not a text parser. It opens grouped actions/context with descriptions and an explicit preview before committing a selection. Keep existing Files, drop/paste and phone photo/camera flows. Opening, previewing or cancelling never uploads, installs, activates or sends; an explicit send uses the attachment pipeline.
- `/` filters Commands and `$` filters enabled Skills at the caret. `@` filters permitted bot mentions. A trigger requires a collapsed caret at start of text or immediately after Unicode whitespace, outside an IME composition, code span or fenced code block. The query is the uninterrupted token between trigger and caret, at most 64 Unicode scalar values. Whitespace, a second trigger, slash/backslash within the query or caret/selection movement outside that token closes completion. Match bounded labels without using label matching as identity.
- A bare trigger may open suggestions. For `/` and `$`, subsequent query characters are Unicode letters, digits, `_` or `-`; a leading digit does not start a query. Thus `/tmp/report`, `./file`, `https://example.invalid`, `$20`, `$$`, `${HOME}`, `$HOME/path` and `x@y` stay ordinary text; `/tmp` or `$HOME` may briefly suggest but never acquires behavior without an explicit pick. Dismiss to keep those literal tokens. Command/skill execution never follows from matching typed words.
- An immediately preceding backslash suppresses any trigger: `\/`, `\$`, `\@`. Preserve the backslash and all text exactly; there is no send-time unescape. Escape dismisses without editing and suppresses reopening for the unchanged token until it is edited or the user explicitly opens completion. No parser strips currency or shell syntax on send.
- A pick replaces only the trigger-to-caret range, retains the suffix, inserts a readable `@Name`, `/Command` or `$Skill` label plus one separator, and creates an anchored typed selection keyed by ID. Display labels never become executable names or paths. An edit overlapping the anchor removes its typed meaning while preserving edited text; edits elsewhere shift the anchor. Undo/redo includes both text and selection state. Pasted plain text does not create typed references. A `+` context pick adds a removable chip, not a hidden prompt fragment.
- Arrows browse; Enter or Tab commits one enabled row and consumes that event, including the primary-modifier send chord. A disabled highlighted row explains why and still consumes Enter without sending. Escape closes the picker first without clearing reply or draft. Shift-Enter remains newline rather than selection/send in the future shared contract; this differs from current AppKit mention behavior. After closing, normal client send/newline preferences resume. IME confirmation never picks or sends. Touch requires an explicit row tap and a separate Send tap.

### Selected typed payload and compatibility

The selected composer schema is version 1, independent of protocol 5 and the existing version-1 skill metadata/copy DTOs. These are design fields, not currently callable API methods. A future core handshake must advertise catalog schema 1 and typed-message schema 1 for the selected Runner and all consumers that load the reference. Without that positive support, retain current text/files/mentions behavior and explain that typed actions require an update. Never send an unknown field to current `chats.send`, which does not enforce this contract, or downgrade a typed action into a prompt instruction.

The selected catalog envelope is `{version:1, binding, catalog_revision, entries, next_cursor}`. `binding` contains opaque `source_id`, `identity_id`, `membership_id`, `profile_id`, `actor_device_id`, `chat_id`, `bot_id`, `runner_id` and `authority_revision`; `next_cursor` is explicit null or an opaque source/revision-bound cursor. The selected message extension is `{version:1, binding, selections}` alongside existing text, attachments, mentions and reply fields. Each selection contains `selection_id`, `entry_id`, `entry_revision`, `kind`, `anchor` and a closed typed `reference`; `anchor` is null for a chip or `{start,end}` using Unicode scalar offsets into the exact submitted text. Clients translate native UTF-16 offsets locally. The core validates ranges and rejects mismatched/overlapping anchors before persistence, file copying or job admission; it never trims text before validating anchors.

Catalog entries require exactly `entry_id`, `kind`, `label`, `description`, `bot_id`, `runner_id`, `origin`, `entry_revision`, `preview_available`, `availability`, `reason` and `reference`. `reason` is null only for `available`, otherwise a fixed code below. Origin contains a bounded opaque instance ID and safe label, never an endpoint/path. `kind` is `bot`, `attachment`, `command`, `skill` or `context`, matching its reference. Status/setup rows explain state without typed selections. Entry/selection IDs are unique per envelope; revisions are opaque equality tokens. Paging binds authority and catalog revision; revision changes require a fresh catalog, never mixed snapshots.

Reference variants are `bot {bot_id}`, `attachment {attachment_id}`, `command {command_id, arguments}`, `skill {skill_id, content_revision}`, and future `context {resource_kind, resource_id, content_revision}`. Context resource kinds are enumerated by an admitted capability, not arbitrary path strings. Command arguments have the exact selected command's bounded schema; no shell string, provider-private reference, local path or arbitrary JSON fallback. Attachment IDs correlate with the existing send descriptors; paths remain Device-local transport inputs, never shared authority. Plugin skill IDs require an installed-instance ID plus immutable skill identity/content revision; a manifest name/slug is insufficient. Managed-copy IDs stay inactive until a separate activation/grant contract exists. Bot mentions still carry stable IDs; legacy inferred-name mentions do not confer typed authority.

The envelope bot is the action/context recipient. A `bot` reference may name another currently permitted bot in that same source, without changing the recipient or granting access to the mentioned bot's resources. Group bot mentions and action targeting remain independent. Admission correlates every entry, variant and revision with the server-owned catalog; it does not trust client-supplied kind/IDs as capability evidence. Skill selection authorizes only the approved bounded skill content for this turn, never hooks, environment changes or resource execution. Command selection requests its declared action on explicit Send through existing review gates; argument collection and cancellation retain the draft. Any missing command adapter or skill activation/content-delivery route yields `not_supported`, not text injection or a generic tool invocation.

Closed decoding rejects missing/unknown fields, versions, kinds, reasons, invalid IDs, bounds or argument shapes. Selected public limits are 256 catalog entries per page, 32 selections per message, IDs/tokens up to 256 UTF-8 bytes, labels up to 256 and descriptions up to 2,048 bytes, with no control characters; command arguments total at most 16 KiB. Existing attachment/message limits also apply. Unknown versions/kinds block selection/load with an update explanation; receivers may render already-admitted fallback labels but cannot execute or resolve unknown references. Typed payload persistence, encrypted message/job propagation and mixed-client negotiation require future core work before enabling any new selection. No compatibility shim reparses display text.

### Permission, revocation and preservation

Picker visibility is not permission. Core admission and the assigned Runner independently validate current source membership/profile, actor and Runner keys, chat membership, target binding, exact resource ownership, content/entry revisions and bot capabilities before preview, context loading and execution, and again after every asynchronous fetch or approval wait. Imported skills, plugin metadata, external files and previews remain untrusted data; none may alter policies or grant shell/write/plugin access. Existing tool-boundary checks and Auto-review still apply to explicit actions. A command pick supplies intent for a later explicit send, never bypasses confirmation for side effects.

Bot-scoped resources are delivered only to the bound bot. If the group pipeline cannot isolate that context from other bots, block that reference in groups with an explanation; do not append it to a shared transcript. Source chats require current access and target-bot membership; artifacts require their owning chat/bot boundary and revision. A reference never gives access to another account instance, membership, profile or another bot's private files/skills. The catalog sends no credentials, raw filesystem errors, hidden account names, skill bodies or resource bytes.

Observed relay/profile/account switches stickily invalidate caches, previews, pending replies and selections, including away/back transitions. Keep the original draft in its source/chat-owned recovery state; show neither its text nor private chips in the new source. Returning to that source restores intent but requires fresh reference validation. Revocation after selection, changed source content, Runner reassignment or removal fails closed and retains text, files, reply and invalid selections for explicit remove/reselect. Never silently omit an invalid selection and send the remainder. A lost send acknowledgement is unconfirmed, not rejected or completed: retain the submitted revision, prohibit automatic retry, and ask the user to check the chat. A confirmed acknowledgement clears only the unchanged submitted revision; edits made while waiting survive.

Chat navigation, Settings, picker dismissal, source switches and failed sends retain text, files, reply, selected IDs and pending/uncertain submission under the original source/chat, not a widget. Quit/update never clears typed drafts for admission. Recovery is in-process, not crash persistence or draft sync, pending a durable storage contract. Cancellation/revocation cannot undo issued external effects; uncertainty never authorizes replay.

The availability vocabulary distinguishes `available`, `disabled` and `unavailable`, with fixed reasons: `permission_denied`, `needs_setup`, `needs_auth`, `paused`, `runner_offline`, `source_changed`, `resource_changed`, `not_supported`, `update_required` and `catalog_incomplete`. Reasons are localized by clients with safe descriptions and explicit recovery: request access, configure/sign in separately, resume, reconnect/revalidate, reselect or update. Do not replace a failure with an empty catalog, generic missing credentials or a fake enabled control. Cached permitted labels may appear as offline/unverified, but new typed context/actions cannot be submitted or loaded until current authority is verified. Current ordinary offline message queuing remains distinct. Existing offline Runners learn policy changes only after sync; this future contract requires verified current authority for typed loads, not a claim that offline revocation can cancel already-issued external effects.

### Client parity and accessibility

AppKit, full desktop and phone share kinds, scope, previews, unavailable reasons, insertion and preservation semantics; native presentation can differ. Every client offers the `+` browse path for users who cannot type triggers. Phone completion uses actual caret/selection, including DM mentions, not end-of-draft matching. Hardware keyboard users get the same browse/select/dismiss rules on phones. Controls have native accessible names, grouped result lists, current-option/expanded state, kind/target/origin descriptions, disabled reasons and removable-chip actions. Announce loading, no results, stale state and errors without exposing private labels. Disabled rows remain discoverable for explanation but never actionable. Screen-reader focus returns to the preserved caret after dismissal; touch targets, scrolling, text scaling, contrast and Reduce Motion follow platform conventions. No reason or operation depends only on hover, color or a gesture.

### Discovery acceptance boundary

Future acceptance requires grouped `+` previews preserving attachments; caret-local `/` and `$` without pick/send overlap; denied/revoked references loading nothing; literal path/currency/escape preservation; separated drafts across source switches; keyboard/touch/screen-reader parity. Fixtures: two differently permitted bots, duplicate skill names, two relay memberships/profiles, an offline Runner and revocation after selection. Native recordings, failure evidence and core/client tests belong to implementation deliveries. Docs validation proves only budgets and links.
