# Computer provenance

Dependency, license and provenance record for the candidate Beans computer stack: a self-hosted Linux guest under QEMU/KVM managed by libvirt. Evidence is source/documentation inspection on 2026-10-13, not acceptance of installed software or a running guest.

## Status

Beans' existing Runner owns the agent loop and runs tools with its OS user's permissions; its workdir and approval controls are not a sandbox (see [Tools](tools.md)). The computer stack below is proposed and is not an implemented isolation boundary. Beans is [GPL-3.0-only](../../LICENSE), as declared in [README](../../README.md#license-and-credits). Exact component pins follow the existing [plugin version-pinning pattern](plugins.md).

The candidate deployment uses operator-installed Linux/KVM, QEMU and libvirt. This documentation change conveys no third-party executable or image. A later Beans image, bundle or linked component requires a fresh review of its actual package licenses, notices and corresponding-source obligations. This is engineering screening, not a legal compatibility conclusion.

`unverified` means required version, license, provenance or deployment evidence is incomplete. Reading a source file does not verify a distributed binary. Every incomplete row blocks the named downstream work; no candidate is accepted for deployment until the image verification and scratch-host evidence below exist.

## Guest image decision

The candidate build model is a stock cloud image plus a versioned, pinned bootstrap, rather than a Beans-published binary image. The distribution builds and publishes the stock image; Beans does not yet have an image builder, signing process or update channel. Ubuntu 24.04 LTS is the candidate distribution, not an accepted image; its signed manifest, trusted key, exact dated build and package license inventory remain unverified and blocking.

Bootstrap installs exact verified packages, starts an unprivileged desktop/controller, and applies hardening. Its manifest records the base image digest, package versions/digests, authenticated repository snapshot, recipe revision, controller artifact and resulting output digest. It fetches nothing unpinned at boot. A stock image's signature does not authenticate later bootstrap modifications; the derived image needs its own build receipt and verification. If these inputs cannot be verified or required hardening cannot be reproduced, provisioning stays blocked. A Beans-built image is a separate future decision, not an unverified fallback.

### Image verification

These steps are a documented gate, not commands executed in this session. Any missing, failed or skipped step rejects the image.

1. Select Ubuntu's exact dated build directory and image filename. Obtain its checksum manifest, detached signature, image and package/license manifest from its official HTTPS publisher. A rolling `latest` or `release` URL is only a discovery channel.
2. Authenticate the signing key's full fingerprint against an independently published distribution trust source. Record that fingerprint and the retained trust source; downloading a key beside an image does not establish trust. Verify the detached manifest signature in a fresh isolated keyring containing only the pinned trusted key. Missing/invalid signatures, unknown signers and revoked or unacceptable keys reject the image.
3. Hash the downloaded image with the manifest's named algorithm and compare against the signed entry for that exact filename. Missing entries and mismatches reject it. Record immutable build URL, builder/distribution, architecture, format, build identity, image digest, signed-manifest digest, signer fingerprint and verification receipt.
4. Validate the image format and backing-file chain on an isolated scratch host before attaching it. Reject unexpected external backing files or a format that differs from the declared input. Build/bootstrap only from the accepted base and pinned manifest; retain package license/source inventory and resulting image digest. The inspection tools themselves need verified provenance.
5. Store the accepted image/bootstrap identity with the computer definition. Keep the base immutable and guest disks separate. Recheck admitted input hashes before provisioning; image provenance never grants access to account keys, provider credential blobs, relay material or host mounts.

Update channel: an operator discovers new distribution builds through the official channel, then repeats the complete verification gate and reviews the changed license/package inventory. New verified pins create new guests; no running or retained guest disk is overwritten by an image update. Existing guest security/package updates use authenticated distribution repository metadata, explicit package/build receipts and a scoped guest update policy. Distribution package security updates are separate from [data-preserving image updates #70](https://github.com/bloodf/beans/issues/70). Base/data separation, approved replacement at stop/start after backup, and rollback to a previous base are not implemented or established by a package-manager update. Changing a signed image, firmware, desktop, controller or package pin requires a new evidence record and scratch acceptance; old documented semantics do not verify a new binary.

## Pinned virsh semantics

Reference pin: libvirt **v12.8.0**, release-tag object `592dc5ba641ae8a3e68c2dc3b0bc18ef86c69a9e`, commit **`940c2352cec2f7759d73ad8725d3ce7f3651cbe9`**. The [commit-pinned `docs/manpages/virsh.rst`](https://raw.githubusercontent.com/libvirt/libvirt/940c2352cec2f7759d73ad8725d3ce7f3651cbe9/docs/manpages/virsh.rst) is the reference, not the rolling rendered manual. Its fetched UTF-8 contents have SHA-256 **`0f526d3521294abfd6b6e29ebaff5f3cb18e6fe08bb0548206cbd906ff2174ab`**. This content digest identifies the inspected document, not a verified release signature.

The manual confirms lifecycle behavior below. Asynchronous shutdown is additionally explicit in the [commit-pinned `virDomainShutdown` API source](https://raw.githubusercontent.com/libvirt/libvirt/940c2352cec2f7759d73ad8725d3ce7f3651cbe9/src/libvirt-domain.c), and [`cmdShutdown`](https://raw.githubusercontent.com/libvirt/libvirt/940c2352cec2f7759d73ad8725d3ce7f3651cbe9/tools/virsh-domain.c) returns after that request. No guest was run.

| Command | Upstream-documented behavior |
| --- | --- |
| `start domain [--force-boot]` | Starts a previously defined inactive domain. Existing managed-save state resumes by default; otherwise it boots fresh. `--force-boot` discards managed-save state and boots fresh. `--autodestroy` ties guest survival to the virsh connection and is not part of the candidate start operation. |
| `shutdown domain [--mode MODE-LIST]` | Requests graceful guest shutdown and returns when the request is issued, not when the guest stops. The guest can ignore it; `on_poweroff` can even cause a reboot. Mode names are `acpi`, `agent`, `initctl`, `signal`, `paravirt`; order in a comma-separated list is undefined. Use one supported mode per request when ordering matters. |
| `destroy domain [--graceful]` | Immediately terminates the domain, equivalent to pulling power. It does not delete storage volumes; a persistent domain remains restartable. RAM/application state is lost and unsaved disk writes can be lost or corrupt the filesystem. `--graceful` limits extreme host-side termination measures such as SIGKILL; it is not guest OS graceful shutdown. |
| `domstate domain [--reason]` | Returns domain state, optionally its reason. Poll it with a bounded deadline after shutdown; command success and hypervisor-running state are not guest-controller readiness. |
| `autostart [--disable] [--once] domain` | Regular and one-shot autostart are independent. `autostart --disable domain` disables regular autostart; `autostart --disable --once domain` disables one-shot autostart. Either enabled can start the guest at the next host boot. |
| `managedsave domain` | Saves and stops a running domain. The next plain `start` restores that saved state, including RAM. |
| `managedsave-remove domain` | Removes managed-save state if present, so the next start is a full boot. `dominfo` can report whether managed-save state exists. |

Consequences for the candidate stop contract in [#32](https://github.com/bloodf/beans/issues/32):

- Stop requests `shutdown`, then observes shut-off state under a bounded deadline. Timeout or rejection is blocked/error, never a successful stop inferred from exit code. Persistent domain XML must specify an appropriate `on_poweroff` action.
- `destroy` requires explicit user confirmation with a data-loss warning. Retaining a disk file does not guarantee crash-consistent disk contents.
- Stop preserves disk contents, not RAM or running applications. `managedsave`/hibernation is a later measured optimization. Cold start uses `start --force-boot`, or removes and verifies absence of managed-save state before plain `start`.
- Disable **both** autostart settings and verify neither remains enabled. Do not use `start --autodestroy`, managed-save-based stopping, or NVRAM-reset flags as an incidental lifecycle shortcut.
- Client, daemon and QEMU versions are separate pins. A real host's `virsh`, modular daemon or `libvirtd`, and QEMU can differ; mismatch, unsupported flags or unexpected behavior blocks admission instead of silently changing the contract.

## Pending live evidence

No image signature verification, binary installation, host probe or VM cycle runs for this documentation change. Source/documentation inspection is not installed-app or live-service acceptance. These gates remain pending:

1. Record trusted signer fingerprints and verify the exact selected host packages/tarballs, firmware and guest image. Retain package/source/license manifests and all immutable digests; resolve every unverified table row.
2. On an explicitly authorized disposable Linux/KVM host, record client, daemon, QEMU, kernel and firmware versions. Define a uniquely owned **persistent** scratch domain using verified inputs and an isolated disposable disk; disable regular and one-shot autostart, select shut-off `on_poweroff` behavior, and verify the settings. Do not operate on unrelated domains.
3. Run `start --force-boot`, observe `domstate`, request `shutdown`, and poll under a bounded deadline for shut off. Record command results, elapsed time and guest/disk observations. Restart before testing `destroy`; obtain explicit confirmation, destroy, then confirm shut off and retained disk/domain. Check filesystem consistency and distinguish persisted file data from deliberately unsaved RAM/application state.
4. Restart the inactive domain, create a distinguishable RAM-only marker, then `managedsave`. Confirm saved state with `dominfo`, plain `start` and verify resume. While running, create another managed-save state; now inactive, use `start --force-boot` and verify fresh boot. Create a third managed-save state from a running domain, use `managedsave-remove` while inactive, then plain `start` and verify fresh boot. Stop gracefully and confirm the disposable disk remains. Each managed-save test requires a running domain before save and an inactive domain before start.
5. Reconcile this evidence with [probe #29](https://github.com/bloodf/beans/issues/29), [threat model #31](https://github.com/bloodf/beans/issues/31), [lifecycle #32](https://github.com/bloodf/beans/issues/32), [controller #33](https://github.com/bloodf/beans/issues/33), [ownership #34](https://github.com/bloodf/beans/issues/34) and [display #35](https://github.com/bloodf/beans/issues/35). Only then can [epic #9](https://github.com/bloodf/beans/issues/9), [supervisor #36](https://github.com/bloodf/beans/issues/36) and [bootstrap #38](https://github.com/bloodf/beans/issues/38) consume accepted deployment decisions.

The Runner remains the control plane and agent loop. Guests receive only scoped computer capabilities, never account master keys, the full provider credential blob, relay storage or host filesystem mounts. Missing KVM or provenance evidence blocks provisioning; it does not select a container or host-execution fallback. Hypervisor display endpoints stay private, and the relay remains zero-knowledge. Display/controller transport and client feasibility belong to their separate contracts, not to the existence of a VNC/SPICE name in libvirt documentation.
