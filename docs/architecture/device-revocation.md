# Device revocation

### Lost, un-wiped Device: current boundaries

Revocation is relay access control, not remote erasure. This trace assumes a previously paired Device and a holder able to read its account files; physical possession alone does not establish access past the OS lock, sandbox or disk encryption. A Device that never contacts the relay again does not observe `410` and does not perform cooperative local forget. Copied plaintext and secrets cannot be retracted by a later forget.

These are source traces, not installed-app, live-provider or exploit results. Forensic erasure after local cleanup and exact cross-process revocation timing are unverified. Relay reachability is separate from provider or local-tool reachability. Offline cached work does not establish that a revoked machine can publish its outbox to the relay.

### Proposed lost-device containment and rotation contract

This discovery contract is proposed and unimplemented. It does not change current pairing, backup or restore behavior. Four confirmed-gap child proposals cover account-key containment, exposed master-secret recovery authority, execution fencing and push dispatch fencing; filing and acceptance remain pending. Cached-data irretractability is a limit, not a promise to implement remote wipe.

1. **Confirm the loss and revoke.** Select the exact Device and distinguish paired-only loss from identity-device/master-secret exposure. Explain that previously synced plaintext and copied secrets remain exposed. Require an acknowledged relay revocation; an unreachable relay leaves revocation pending, not containment complete. Trusted Runners stop routing work to the removed Device and cancel affected tracked work without promising rollback of completed external effects.
2. **Replace external authority.** Inventory exposed provider, plugin and memory-service credentials without displaying secret bytes. Guide issuer-side key replacement and session/refresh-token invalidation, then distribute replacements only to retained trusted Devices. Track each invalidation separately as pending, confirmed or unavailable; Beans disconnect is not evidence that an issuer refuses the old secret.
3. **Exclude the old DEK from content published after rotation.** For paired-only loss, generate a fresh random account DEK and push-key epoch. Authenticate the transition and bind account, epoch and retained membership. Wrap the new key to retained machine box keys and to recovery authority known uncompromised, never only under the old DEK. Offline retained Devices must obtain the current epoch before publishing; require supported reader/writer capabilities and fail closed on old-epoch publication or uncertain membership. This proposed exclusion protects new content only, not prior relay history. Current [key publication](../../crates/cli/src/identity.rs#L53-L58) uses an unaddressed, [unslotted blob](../../crates/cli/src/app.rs#L687-L695); publishing another key does not supersede old key blobs, and [restore selects the last returned key](../../crates/cli/src/sync.rs#L1601-L1609). Rotation alone does not purge old key blobs or remaining old-DEK ciphertext from the relay. A holder with the old DEK and access to that prior ciphertext can still decrypt it; revocation and rotation cannot retract captured history.
4. **Replace a compromised root.** If the lost Device exposes the master secret, sealing a new DEK to the unchanged content key does not contain the loss: the same master still derives that secret and authorizes fresh machine registration. Use a new identity/master and recovery phrase with an explicitly authorized, data-preserving migration from a trusted Device. Preserve the existing backup/restore path for current accounts; do not silently reinterpret a backup or claim that machine revocation invalidates it.
5. **Preserve data through interruption.** Stage replacement recovery records and retained DEK-encrypted blobs, attachments, credentials, memory configuration and key-derived namespaces before activation. Preserve transcript slot order, read marks, deletion fences and quota accounting. Use durable, idempotent, crash-resumable phases; after activation never roll back to a compromised key. Reconcile retained offline intent against current state before re-encrypting its outbox. Re-encryption cannot protect old ciphertext or plaintext already copied by the lost Device.
6. **Fence side effects and pushes.** Bind new and resumed execution and approval consumption to authenticated membership/epoch evidence; invalidate old approvals at transition. If revocation must bound cooperative execution while relay-offline, use a finite authorization lease and refuse side effects after expiry. Unlimited offline execution and immediate remote revocation cannot both be promised, and a modified hostile client already holding secrets cannot be remotely constrained. Update retained phone extension keys and revalidate token generation/membership at push dispatch admission; state the already-admitted/provider-handoff boundary rather than promise recall.
7. **Report separate outcomes.** Show relay revocation, trusted execution fencing, account-key rotation and issuer-side invalidation independently. Before implementation acceptance, exercise interrupted migration, stale concurrent writers, offline retained-Device rejoin, exclusion of the revoked DEK holder, exposed-root replacement, queue/approval cancellation and push snapshot-before-revoke dispatch. No delivery or exploit result is implied by this contract.
