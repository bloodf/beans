# macOS app

For the transcript, composer, and working state, see [macOS chat](macos-chat.md).

Sidebar, search and toolbar mechanisms are in [macOS sidebar](macos-sidebar.md).

SPM `Beans` executable ships in `Beans.app` (or `Beans Dev.app`), an AppKit app with bundle identifiers `ai.amoena.beans` and `ai.amoena.beans.dev`.

The app starts the bundled `beans` (`Contents/Resources/bin/beans`; `BEANS_CLI` overrides, PATH is the fallback), logs under `~/Library/Logs/Beans/` or `~/Library/Logs/Beans Dev/`, and restarts its child after exit. Stable uses fixed home `~/.beans-v2` and port `4874`; Dev uses `~/.beans-dev-v2` and port `4875`. Manual commands are `beans serve --home ~/.beans-v2 --port 4874` and `beans serve --home ~/.beans-dev-v2 --port 4875`. App-owned preferences use `beans-v2.*` without old-key reads or migration; AppleLanguages and distribution/signing identities stay unchanged. Inherited `BEANS_HOME` cannot override the fixed app home, and an unexpected saved port fails closed in both launcher and websocket client. The native websocket sends `Beans-Protocol: 5` and `Beans-Format: beans-v2`; fixed ports avoid ordinary attachment to old-format CLIs but do not authenticate an arbitrary process on that port.

Release packaging reads `BEANS_DEFAULT_RELAY_URL` into the bundle's optional `BeansRelayURL` metadata, not a source constant. The launcher supplies that fallback only when its environment does not already select one; saved settings and pairing still use the CLI's normal relay precedence. Builds without this value have no preset relay, and development bundles omit it.

Which window a launch opens depends on the identity, which only the CLI knows, so the app keeps a hint: `Preferences.hadIdentity`, whether the CLI's last answer had one. With it, the main window opens during AppKit launch with a loading indicator and the saved inspector visibility. Without it (a fresh install, or a Mac whose identity went away) no window opens until the snapshot picks onboarding or the main window, so onboarding never replaces a main window that just appeared; a startup failure or the 2.5-second deadline opens the main window on the offline recovery controls. The main window's inspector keeps its width while the snapshot loads; the chat and inspector views are built when their data arrives, and automatic layout changes apply without a collapse animation. A dedicated serial queue probes localhost, locates and spawns the CLI, and reads its readiness pipe while AppKit builds the window on the main thread. Only lifecycle notifications and the ready callback return to the main thread; stopping the launcher fences queued starts and terminates its child. It launches its child with `--ready-stdout`; after loading local state and binding its server, the CLI flushes `{"event":"ready","port":<port>}` to stdout. The app reads this startup pipe and opens its websocket on that signal. CLI logs go to stderr, and the app saves both streams in its log. An existing CLI is used once the localhost probe succeeds. A dropped connection backs off from 400 ms and asks the launcher to prepare the endpoint again; a child restart connects on its new readiness signal.

The first request is `bootstrap`, which carries identity, chat metadata, and messages together. The app buffers incoming events until the snapshot arrives, applies the snapshot and buffered changes with view notifications held back, then publishes one complete state with the connection marked ready. The sidebar creates its scroll view and outline when rows first arrive, with their previews and activity order, and restores the selection after creating the rows. Settings navigation, the Device picker, and offline/empty-state views are created on first use. The window configures its saved frame and toolbar before attaching the split view, sized to that frame, since a window takes the size of its content view controller; it uses deferred creation and is ordered front once with opening animations disabled. Notifications and the updater start after this initial presentation (or after startup fails). A startup failure or 2.5 seconds without a snapshot replaces the loading indicator with the offline recovery controls. `BEANS_TRACE_STARTUP=1` writes launch milestones and elapsed times to `startup.log` in the app's log directory. CLI milestones are recorded on the launcher queue and window milestones on the main thread. `bun run test:mac-startup` checks that the launcher progresses with the main thread blocked, handles fragmented readiness and early exit, and cancels queued starts without leaving a child running.

First run: the CLI's `bootstrap` snapshot has `has_identity: false`, and the app shows onboarding: create (the CLI returns the phrase), restore (phrase → relay), or pair (paste the string from a computer that already has the identity). After create, the user names the first bot (the CLI's default Chef, edited through `bots.update`), then connects an API-key or subscription provider for the account (skippable; Skip for Now during a browser sign-in cancels it through `providers.auth.cancel`), or picks a custom provider preset or Other Server, whose Set Up button opens the custom provider sheet over onboarding and moves the first bot to the provider it saves. In Chinese, onboarding offers **幕僚长** and a Chinese description for the default profile; Continue saves those values through `bots.update`. While a restore or a pairing runs, its field and button are disabled beside a spinner; Back cancels a pairing still waiting on the other Device (`pair.abort`), and stays disabled through a restore and the sync after either. Restore and pair then show "Syncing the account from the relay…" and ask the CLI for the account's providers (`sync.account`), which it answers once its first pull has brought the account's credentials, or after 30 seconds; the provider step shows only when the account has none connected. The last step says how the Mac came by the identity (the first Device, a restored identity, or a paired Mac) and points to Pair a Device in the File menu, which every paired Mac offers. Onboarding is the app's window until it finishes: closing it leaves the app running, the Dock icon brings it back (`applicationShouldHandleReopen`), a notification click brings it forward, and the menu commands that open the main window (New Bot, New Group Chat, Marketplace, Pair a Device, Find, Command Palette) are disabled. Settings › Advanced › Show Onboarding Again, like Debug › Show Onboarding, hides the main window and opens onboarding. Over an identity nothing there can run (create, restore, and pair refuse), so closing it is Cancel: the main window comes back as it was, on the same pane with its history, and a notification click does the same before opening its chat.

Backup display and clipboard copy retain every CLI-returned token unchanged: first `beans-v2`, then thirteen base32 groups. Restore requires that first token; it does not promise old-phrase recovery. Native signed readiness rejects protocol below 5, and selected-relay checks require `beans-relay`, `beans-v2`, sufficient protocol and supported effective account/roster floors at least 5.


Settings rows share `Settings/SettingsRows.swift`: accessory rows keep a 10 pt gap between the wrapping label and the trailing control, and their height grows with the label. A settings pop-up takes at most 55% of its row, truncates long selected titles before the chevron platter, and keeps the full choice in its native menu and tooltip. Each accessory exposes its row label to accessibility clients. General's update row puts the version and last-check status below the label and native Check for Updates action, so the status wraps without squeezing the action. `sh macos/Tests/run-settings-layout.sh` checks production AppKit rows at 280, 360, 504, and 760 pt with English and Chinese text in light and dark appearances; `SettingsLayoutTests` also runs in the existing `BeansTests` target.

The Devices pane reports the CLI/core version. Beans does not advertise standalone CLI self-update availability; its native app updater continues to use Beans signed readiness and Runner admission drain.

General settings has an account-wide Pause switch, synchronized across Devices through the encrypted roster; the sidebar footer shows Paused status. A DM inspector's Abilities controls gate shell, file writes, and either all installed plugins or selected plugin IDs for that bot. Existing bots remain unrestricted until their abilities are changed.

Settings › Plugins lists marketplace installs and user-managed MCP servers for the selected Runner. Its MCP section loads `mcp.list` from that Runner and reloads its `mcp.json` with `mcp.reload`. A server sheet fetches `mcp.get` only when opened; it edits JSON configuration and name through `mcp.save`, toggles availability, reconnects, signs in or out, hides or shows individual tools, and confirms removal. Credentials in environment and header fields appear masked, with unchanged values preserved on save. Remote Runner requests are sealed by the CLI; server configuration is not roster state.

Memory-service drafts and the independent local MEMORY.md editor are described in [Memory service UI](memory-ui.md).

Beans release bundles enable Sparkle with the project-owned public key and GitHub Beans appcast. Signed readiness pins the version, archive and required relay protocol before an update is offered; installation waits for a guarded normal quit rather than forcing an unattended relaunch. Saved opt-outs remain intact. Debug bundles omit the feed/key and disable checks. The root `package.json` supplies the bundle version. Packaging requires the matching Beans signing key, a Developer ID Application identity and a notarization profile; see [Mac releases](../releasing-mac.md).

The launcher passes the fixed home’s `native-update-token` path to its child but provisions or validates the token only after core readiness, once the core has validated/initialized storage. Token reads and provisioning open the existing home and bounded regular `format.json` through no-follow descriptors and require `beans-v2`. Token creation remains exclusive/private (0600); existing bytes and permissions are never replaced. Inherited explicit disable/operator token settings cannot authorize native installation and the app never reads an operator token as fallback. An external CLI needs compatible drain control and matching app-owned token. See [native drain prerequisites](../releasing-mac.md#atomic-runner-admission-drain).

Guarded installation takes an actual token-authenticated `update.prepare` Runner lease with a 1,800-second TTL before fetching readiness or inspecting Runner work. Admission closes atomically under the CLI's work-producer lock; admitted work is not canceled. While the lease holds, the updater rechecks the signed release, bootstrap work state, actual selected-relay health and a subsequent `hello` relay selection. Final `update.status` must report the same Runner process, enabled/prepared/ready control, no active work or jobs and positive remaining lifetime. Renewals must preserve the lease id and process; a conservative monotonic deadline, current relay selection and native quit guard are checked immediately before authorization is used.

Retained drafts (including reply-only drafts behind Settings), active work, command input, onboarding, modal windows, sheets and edited documents block installation. A postponed Sparkle relaunch uses the same AppKit quit path and a synchronous main-actor continuation; the lease stays held through that handoff and the subsequent quit revalidates it. Failed/canceled quits and completed/aborted update cycles release the lease, waiting for any in-flight prepare first; a handoff that does not reach another guarded quit within 30 seconds releases it too. Failed cancellation surfaces an error and leaves installation unauthorized while the CLI lease can expire independently. The app does not discard drafts, stop commands or change account Pause to make an update ready. Installed quit/relaunch still needs real UI verification; source and compilation do not establish acceptance.

Bot portraits: `Design/AvatarView.swift` draws generated portraits as Core Animation shape layers from shared numeric geometry on every bot surface, including sidebar clusters, transcript, inspector, and onboarding; the renderer, its clock, activity states, and the Look sheet are in [Bot avatars](avatars.md#macos-renderer-activity-and-look-sheet). Marketplace template previews use the template ID until a bot exists.

Inspector: `Inspector/InspectorViewController.swift` compares what each section would show with what it last showed on every store event and touches only a section that changed. A changed section reconfigures the rows it keeps for each bot, Runner, routine, and plugin; Runs with builds its pop-ups again only when the provider, model, thinking level, or the account's providers changed (custom providers follow the built-in ones in the Provider pop-up, and a custom provider's models fill Model), and the usage rows take each turn's values in place. Collapsed, or in a closed window, the inspector skips reloads and memory fetches and catches up in `viewWillAppear`.

The Group inspector section edits the group's Name and Description, with Description opening its own sheet. The description is shared roster metadata supplied to every member's system prompt, not a bot profile; see [DMs and groups](bots.md#the-lead-bot).

## Development and builds

`bun run dev` rebuilds the CLI and Beans Dev on Rust or Swift changes (the generated markdown bindings under `macos/Sources/BeansMarkdown` are left out of the watch, and rewritten only when they differ) and relaunches the app through `open`, so the app is its own responsible process for TCC: a binary spawned from the terminal is charged to the terminal app, whose Info.plist decides whether a microphone or speech request aborts. The development loop leaves production Beans processes alone.

`bun run build` produces the Beans release bundle. The bundle step restamps the app binary's SDK version (`stampSDK` in `scripts/app.ts`, through `vtool`): the Swift Build engine writes the deployment target (14.0) there, and AppKit gives a binary stamped below the macOS 26 SDK its older look, with a flat sidebar and an opaque titlebar strip.

The production app icon uses the coral Beans mark. Editable SVG masters in `design/brand/` supply every platform export through `scripts/export-brand-assets.cjs`: macOS ICNS, desktop package and onboarding PNGs, tray icons, Expo icons, splash screens and favicons. Beans Dev uses a near-black icon with a coral mark. Android adaptive icons use transparent foregrounds over coral or near-black backgrounds. The export command and dependencies are in [the brand asset guide](../../design/brand/README.md).
