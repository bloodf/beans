# macOS sidebar and navigation

## Settings navigation

Settings is a mode of the main window. The foot of the sidebar has two icons and a button: the gear opens General (as ⌘, does), this Mac's icon, red while the CLI is not answering and orange while the CLI cannot connect to the relay (its tooltip says why), opens the Devices pane on this Mac, and at the other end the marketplace icon (`circle.grid.2x2`) opens the marketplace. The sidebar gives way to the settings sidebar: a search field where the chats' one is, the panes, and Back (a chevron and the word; Escape does the same) in the footer, where the chats' sidebar has the two icons (General, Providers, Auto-review, Plugins, Bots, Devices, Advanced). Plugins, Bots, and Devices each show one Device, picked from a pop-up in the window's toolbar: a standard toolbar item at the content area's trailing edge, in the toolbar while Settings is up. On macOS 26 the item's view is a plain container holding the pop-up on a glass capsule of its own (`NSGlassEffectView`), and the other panes hide that capsule: a toolbar item entering, leaving, or hiding makes the toolbar lay its glass out again, which blinks the back and forward buttons, and a hidden pop-up in a standard item leaves its platter behind. It lists the paired Devices with Pair a Device at its foot (`MainWindowController.updateToolbar`). The titlebar's Create button and the inspector toggle belong to the chats and leave while Settings is up. It starts on this Mac, and the pick holds across the three panes: the root keeps it in `settingsDeviceID` and hands it to the `DevicePaneViewController`s (`Settings/DeviceSettingsViewControllers.swift`). Providers has the account's credentials, with Connect and Disconnect for each, then the custom providers (`server.rack`, Edit…) and an Add Provider… row whose menu lists presets (OpenAI Compatible, Anthropic Compatible, OpenAI, OpenRouter, Gemini, Groq, Together AI, Ollama, LM Studio; a named-service preset the account has is checked and opens it, while either Compatible preset adds another connection) and Other Server…; the custom provider sheet (`Sheets/CustomProviderViewController.swift`) takes a name (the matching preset's or the host when left empty), the protocol, the base URL with a note naming the URL the CLI will call, and an optional key, and loads the server's models through `providers.list_models` half a second after those stop changing: a checklist with each model's name, id, window, and an eye for images, a search field that filters it and offers Add "…" for an id the server does not list (Return adds it), the count, and a Default pop-up. A new provider starts with the entire first nonempty model catalog checked; either Compatible preset initially hides the name, protocol, and model checklist behind Advanced. It opens an existing provider with its key fetched through `providers.api_key`, its saved models checked above the rest of the listing, and Delete; Bots lists the bots assigned to the Device, each opening its chat; Plugins has what the Runner installed and the marketplace, then its own MCP servers ([MCP servers](mcp-servers.md#in-the-apps)); Devices has the machine key, role, last seen, relay (with why the last try to connect failed, while it is not connected), and Unpair, this Mac's too: there it is `identity.forget`, which brings back onboarding, and when this Mac holds the identity the confirmation is critical and says that the backup phrase becomes the only way to restore the identity. An unknown Device, a machine the relay lists that never sent its name or system (`Device.OS.unknown`), has a question mark for its icon, no model or OS, and a note above its key to unpair it if nobody recognizes it; Bots and Plugins show the same note. The demo, which has no CLI, opens onboarding over its account instead, as Show Onboarding Again does. A Device that is not a Runner shows a note in Plugins and Bots. A query (⌘F focuses the field) narrows the list to the panes and settings that match, each setting under its pane (a Device pane's bots and plugins are those of the picked Device); picking a setting opens the pane, scrolls to its row, and flashes it. The index is `SettingsEntry` (`Settings/SettingsSearch.swift`): a title, keywords, and the row label the panes take their labels from, so the results and the pages share one spelling. Both sidebars use a standard `NSSearchField`, which brings AppKit's capsule and focus ring. From macOS 26 a sidebar's list fills the pane and scrolls under everything in it, as System Settings' does: the bars (the chats' search field and footer, Settings' search field and Back footer) are `NSSplitViewItemAccessoryViewController`s the root sets on the sidebar's split view item for whichever sidebar shows, so AppKit insets the list by them through the safe area and softens the rows passing behind them and the titlebar. On macOS 14 and 15 the bars and the list are stacked inside the pane (`SidebarChrome.floats`). The selection says which sidebar shows (`Selection` is `chat` or `settings(pane)`); opening a Device from the inspector picks it and lands on Devices, and Back returns to the chat that was open. While Settings is up the toolbar has back and forward ahead of the title (a navigational `NSToolbarItemGroup`), walking the panes visited since Settings opened (`RootSplitViewController.paneHistory`). The panes' cards follow System Settings: a bold group title on the rows' text column, a fill with 12 pt corners and no border, and dividers between the rows' text margins (`SectionView.style = .heading`; the inspector keeps the captioned, bordered card). A pane's pop-ups are `SettingsPopUpButton`s (`Design/Controls.swift`), System Settings' look: the choice as plain text, as wide as it needs, and the chevrons on a small rounded platter, which grows to hold the text too under the pointer. The panes show while the CLI is not answering, since the CLI port and the relay URL live there. While onboarding is up there is no main window, and ⌘, opens General and Advanced in a small window of their own.

## Search and command palette

The command palette (⌘K, View › Command Palette…, `Palette/`) is a borderless child panel of the main window on Liquid Glass (`NSGlassEffectView`; the menu material before macOS 26): a search field over an inset `NSTableView` of actions, chats, historical message matches, and settings. The actions are the menu bar's own items, looked up by selector (`PaletteIndex.commands`): the palette validates the menus while the main window is still key, lists the enabled items with their titles and key equivalents, and runs one by sending the item's action down the responder chain after the panel closes, so a command reads and behaves as it does in the menu. A query is debounced into `chats.search`, which scans local chat metadata and visible message rows on demand; message rows show the newest matching snippets, and matching tokens in titles and snippets are highlighted. A chat opens with the composer focused; a settings pane opens in place, and a query also finds the settings on the panes (`SettingsSearch.entries`), which open scrolled to their row. The field keeps the keyboard while the arrows move the selection, the pointer selects as in a menu, and Return, a click, Escape, or the panel losing the keyboard closes it. The chats sidebar's search field is the palette's other door: a click on it, or ⌘F outside Settings, opens the palette, and the field never takes the keyboard. The phone's chat-list search bar calls the same API and shows highlighted chat and message results.

## Native chrome and verification

Chrome: split view, vibrancy, bubbles, `@` mentions. The titlebar is AppKit's own: the transcript and the settings panes run their scroll views under it, so the header has no background at rest and gets the scroll-edge effect and its separator once content is beneath it. The app renders CLI events and applies its own edits optimistically; `BEANS_MOCK=1` runs the seeded demo instead. Keys stay in the CLI.

`HoverButton` preserves native actions, menus, keyboard focus and 28 pt footer/titlebar hit areas. A centered, unscaled, click-through `NSImageView` draws icon-only optical outsets at 1×/2× with native symbol configuration/palette tinting. Initialization, property changes and layout synchronize it; titles hide it and use text attachments. Settings pop-up titles use line-fragment layout to center text inside their drawing rectangle.

Sidebar search uses a regular native `NSSearchField` in a 32 pt strip. On macOS 26, split-item accessories supply outer content insets and the list adopts them automatically, without an additional top safe-area inset or duplicate horizontal padding. macOS 14/15 stack the bars with 10 pt horizontal padding. Pane icons use independent, centered 28 pt glyph boxes inside the shared label-alignment slot; unscaled 15 pt symbols retain their optical outsets, and Auto Layout measures the complete image view rather than the symbol alignment rectangle. Footer hit areas and source-list selection remain native.

`NativeChromeTests` renders attached AppKit controls: 1×/2× contours on available displays, light/dark, pane icons against independently configured roomy 15 pt references, palettes/disabled state, real English/Chinese Back constructors, popup text alignment, hit testing, and 860/1180/1600 pt window chrome/sidebar swaps. First-row and search geometry share window coordinates; list insets are compared with AppKit's accessory safe area, not a fixed gap target. Run `BEANS_MOCK=1 swift test --package-path macos --scratch-path /tmp/beans-chrome-tests --filter NativeChromeTests`. `bun macos/Tests/run-sidebar-chrome.mjs` compiles the production sidebar controllers, pane cells and native controls against isolated domain inputs, without the app, CLI or avatar renderer; `--show` opens its visible host. `sh macos/Tests/run-settings-layout.sh` runs isolated title/popup checks. `BEANS_CHROME_EVIDENCE` saves bounded PNGs and measurements. Native focus-ring probes explicitly report unavailable compositor drawing; inactive-window geometry does not establish key-window focus-ring acceptance. macOS 26 rendering does not establish macOS 14/15 acceptance.

## Chat outline

Sidebar: an `NSOutlineView` (`Sidebar/SidebarViewController.swift`) with one item per chat, kept for as long as the chat is listed. Only the first rows come in with a reload. After that, a store event moves, inserts, or removes the rows whose place in the order changed (new activity moves a chat up in one move, without animation), and a cell is reconfigured only when what its row shows (`SidebarChatCell.Content`: avatars, working dot, title, preview, stamp, pin, unread count) changed. Cells come from `makeView(withIdentifier:)`, and a moved row keeps its row view, cell, and selection.

## Toolbar commands

Command navigation follows [Terminal sessions](terminal-sessions.md): Running tasks opens from the terminal button in the chat toolbar, and a foreground command offers Run in Background before Stop. The Chat menu and command palette expose Run Command in Background (⌃B) only while such a command exists; otherwise the shortcut stays with the composer. Transcript cards, attachments, dictation, reply drafts and working state belong to [macOS chat](macos-chat.md).
