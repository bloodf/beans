# Phone app

`mobile/` is an Expo app (React Native, expo-router, TypeScript) for iOS and Android. A phone is a Device and never a Runner, and it links the same Device core the CLI is built from rather than porting it: `crates/mobile` (`lorca-mobile`) wraps the `lorca` library, built without the `runner` and `server` features, in a UniFFI object with three calls, and `mobile/modules/lorca-core` is the Expo native module around it.

Beans and Beans Dev install separately as `ai.amoena.beans` and `ai.amoena.beans.dev` with primary schemes `beans` and `beans-dev`. Both also register `lorca` to open the pairing links the Rust core emits; if another installed app claims that scheme, scan or paste the code inside Beans to choose the target app. Their iOS app/keychain groups are `group.ai.amoena.beans` and `group.ai.amoena.beans.dev`. Android reads its Firebase client file from `BEANS_GOOGLE_SERVICES_FILE` when supplied; without it, the build omits Firebase push configuration.

`bun run android:release` builds the Rust core, runs a clean production prebuild, and assembles the release APK with a keystore outside the repo. The Android signing plugin adds the release signing configuration from `BEANS_ANDROID_KEYSTORE`, `BEANS_ANDROID_KEYSTORE_PASSWORD`, `BEANS_ANDROID_KEY_ALIAS`, and `BEANS_ANDROID_KEY_PASSWORD`; the script loads the complete set from `BEANS_ANDROID_ENV` or `~/.config/beans/android/keystore.env`, requiring both the env file and keystore to have mode 0600. Inherited signing values cannot fill missing file entries. It leaves the development signing configuration alone. The Android locale plugin puts the English permission descriptions from `mobile/locales/en.json` into default resources so translated resources have fallbacks.

Phone release versions come from the root package; EAS remote versions own store Android versionCode and iOS buildNumber. The all-scope release builds a GitHub APK, Play AAB and TestFlight store IPA, validates exact source/project/build provenance and waits for all artifacts before readiness. Store IPA is not an ad-hoc installer. Store submission is a separate manual workflow limited to Play internal testing and TestFlight. Local `android:release` and ad-hoc `release-ios` remain separate tools; Android installation needs OS approval and ad-hoc iOS installation needs provisioned devices. See [Releases](releases.md).

- **The core** (`crates/mobile/src/lib.rs`): `Core.start(home, name, os, osVersion, model, listener)` loads the App from the app's own folder, sets the host facts (a phone cannot probe them), and starts the relay sync loop on an embedded tokio runtime; `request(method, params)` is one call of the JSON API in `crates/cli/src/api.rs`, blocking on the module's background queue, answering `{ result }` or `{ error: { message } }`; `wake()` asks the relay again now (the app calls it on foreground, since the sync socket may have died while iOS suspended the app). Every event on the App's bus reaches the listener as the `{ event, data }` frame the websocket carries.
- **The native module** (`mobile/modules/lorca-core`, picked up by Expo autolinking): a Swift `Module` and a Kotlin one, each about forty lines, forwarding `start`, `request`, and `wake` and turning the listener's frames into a `sendEvent`. `bun run core` (`build.ts`) builds the Rust for `aarch64-apple-ios` and the simulator into an xcframework with the UniFFI Swift beside it, and for `arm64-v8a` and `x86_64` with `cargo ndk` into `jniLibs` with the Kotlin (over JNA). The built pieces are gitignored; a Rust change needs `bun run core` and a native rebuild, a JS change is a Metro reload.
- **The JS side** (`mobile/src/core`): `engine.ts` starts the core, mirrors its events into the zustand store (`store.ts`, the way the macOS app's AppStore mirrors the CLI: `snapshot`, `roster.changed`, `message.*`, `job.*`, `chat.usage`, `relay.status`, `identity.changed`; events that arrive while a `bootstrap` snapshot is on its way wait and apply after it, as in the macOS app, so a snapshot built before the relay connected cannot undo that `relay.status`), and offers the screens the same verbs the macOS app has, each one request (`chats.send`, `bots.create`, `bots.update`, `pair.accept`, `providers.connect_*`, `providers.list_models`, `providers.api_key`, `providers.disconnect`, `device.rename`, `device.unpair`, `identity.forget`, `sync.wake`, …). `prefs.ts` keeps the one thing that is the phone's own, the dictation language. Nothing about the account is stored outside the core's folder.
- **Pairing**: the phone scans the QR code the desktop app shows, pastes a string from the app or `lorca pair` on another computer, or opens it as a `lorca://pair?…` link; `pair.accept` does the handshake in the core and the first `bootstrap` snapshot fills the store.
- **Relay status**: the chat list's title slot (`src/ui/ChatsScreen.tsx`) stays empty while the relay connects, and speaks once that has taken a second, or four after the app comes to the foreground, when the socket the suspension killed is replaced: "Connecting…" with a spinner, or, once a try has failed (`relayError`), "Can’t connect" or, for an unknown machine, "Pair this phone again" beside a warning glyph. A tap on those opens an alert with the error (`src/ui/relay.ts`) and Try Now (a wake) or Unpair This Phone. "Update Beans to sync" takes the slot over all of them. Settings › Account › Relay shows the error in place of "Connecting…".
- **Attachments**: the composer's `+` offers the photo library, the camera, and the file picker; a picked file's path goes with `chats.send`, and the core copies, encrypts, and uploads it as a `file` blob ahead of the message. A bubble that shows an attachment this phone does not have asks `files.path`, which fetches the blob and answers with the file. Images render as thumbnails sized from the width and height in the message (full screen on tap); other files as a name-and-size card.
- **Bot avatars** (`src/ui/Avatar.tsx`): `@beans/blobatar/react-native` draws each bot's deterministic SVG from `bot.id` through `react-native-svg`, the same seed and look as the Mac and desktop apps. Generated looks use no image URL or network request; an uploaded profile image overrides the SVG after `files.path` fetches its encrypted `file` blob. The working presence dot and group clusters compose those same bot avatars; the You avatar remains separate. Details › Look previews the generated look and lets the user choose, change, or remove the photo. New Bot sends required legacy symbol and accent fields to the core but does not offer controls for fields that no longer affect the generated look.
- **Group details**: Group Info edits Name and Description; Description pushes a full editor and saves through `chats.set_description`. Every member reads the shared description in its system prompt. A DM uses its bot's description instead; see [DMs and groups](bots.md#the-lead-bot).

`mobile/metro.config.js` extends Expo's Metro defaults with the file-linked `packages/beans-blobatar` source as a watch folder and `mobile/node_modules` as a resolver search path. Its React and `react-native-svg` imports use the app's installed copies, including `react/jsx-runtime`; Metro does not install or bundle a second React for the adapter.

`bun run release-ios --local` builds the release core and copies `mobile/` into `dist/ios/mobile` without uploading. The release copy also carries `packages/beans-blobatar` at `dist/ios/packages/beans-blobatar`: the first copy uses APFS clone copies, later releases sync changed files with rsync. Its `mobile/node_modules/@beans/blobatar` link points to that copied source rather than Bun's absolute per-file links into the working tree. Metro watches the copied package and resolves React and `react-native-svg` from the copied mobile app, keeping one React instance when Xcode bundles the iOS app. The script then prebuilds, installs pods, and archives from the copied project; only a run without `--local` exports and uploads.

- **Dictation**: the primary disc is Dictate while the field is empty (a small microphone sits inside the field once there is text). While recording, the field shows Grok Bot's pill: a stop square, the elapsed time, and bars that follow the microphone, with Send still beside it. The words land in the field after whatever was typed when the user taps the square, or go out at once when the user taps Send. The recognizer (`expo-speech-recognition`) listens in the first of the phone's preferred languages it supports (`src/ui/dictation.ts`; a Chinese speaker on an English-region phone gets zh-CN), or the language chosen in Settings or by a long press on the microphone.
- **Notifications** (`src/core/push.ts`, `expo-notifications`): after pairing, and on every launch and foreground, the app asks for permission once, reads the native device token, and registers it with the relay through the core (`push.register { platform, token, environment }`). The Swift module writes the core's push key into the build's keychain group (`group.ai.amoena.beans` or `group.ai.amoena.beans.dev`) at start and on `identity.changed` (removed when the phone holds no account); the notification service extension is its own target, generated at prebuild by `@bacons/apple-targets` from `targets/notify`. A tap opens the chat, a reply in the chat on screen makes no banner, and opening a chat dismisses its notifications.
- **Turns**: sending is `chats.send`; the core admits a `turn` Job on the bot's Runner or a group room, exactly as any Runner's CLI does. When a direct turn already owns the chat, the Runner promotes the new user message as steering after the current model step and its tools settle, and a question the turn waits on is dismissed rather than waited for; the admitted Job then exits when it reaches the lock because that message was already handled. In a group, the current member settles and the newly admitted room takes over. The `job.started` / `job.finished` events drive the "is working" row and "Chef stopped without replying"; `job.thinking`, `job.retry`, and the running tool rows fill in what the bot is doing, which the core reads in the Runner's `machine` blob and the chat log. The row shows every turn in flight, whichever Device started it, and is back when the app is closed and opened again (see Working state in [macOS chat](macos-chat.md)). The phone has no hard Stop control.

Settings › custom provider offers Refresh Models, which asks the core to run `providers.refresh`; newly discovered model IDs appear in the bot's Model picker without replacing the saved selection. The action reports changed, unchanged, or a generic error without revealing the provider key.

When a refresh snapshot omits optional provider or model lists, the store keeps them only for the same paired identity and relay URL; explicit empty lists clear them. Account changes, forgotten identities, and relay-source changes discard prior catalog metadata. A `relay.status` URL change clears those lists before a later partial snapshot can reuse them, without changing a bot's saved model.

The UI is native: a native stack with large titles, search, and toolbar items; a composer after Grok Bot's phone app, a liquid-glass `+` button and glass pill (`expo-glass-effect`, a filled pill where glass is unavailable) floating over the transcript with the Dictate or Send disc inside the pill's right edge, riding the keyboard as a `KeyboardStickyView` while the transcript's `KeyboardChatScrollView` lifts the last messages with the keys by growing its bottom inset, so the list is never resized; form sheets on iOS and full-screen Material modal screens on Android for chat info, new bot, new group, and settings; provider credential screens under Settings, with API-key fields and an in-app browser for subscription OAuth, the same browser that opens a computer's plugin sign-in from its card, and custom providers after the built-in ones: Add Custom Provider is a native menu of the same presets as the desktop apps (one the account has is checked and opens it) and Other Server…, opening a form (`app/settings/custom-provider.tsx`: name, API menu, base URL with the URL the CLI will call and, for a server on localhost, a note to name it as the Runners reach it, key, a Models row, and a Default Model menu) whose Models row slides in a picker (`app/settings/custom-models.tsx`) of the server's listed models with a native search bar that offers Add "…" for an id it does not list; the two share their rows through `src/ui/modelDraft.ts`; Link previews and context menus on iOS chat rows and Material long-press menus on Android; SF Symbols on iOS and Material Symbols on Android; UIKit semantic colors and Material 3 dynamic colors; haptics. Android toolbar actions and popup menus are Jetpack Compose views from `@expo/ui`: the chat list has Settings on the leading side and Search plus the New menu on the trailing side, with no title, while the composer's attachment sources open in a Material bottom sheet. Conversation headers overlay the transcript on both platforms; UIKit supplies its navigation material, while Android lays a nearly opaque light or dark veil through the status-bar and controls and fades it into the transcript, leaving scrolled messages faintly visible like Gemini. The transcript follows the macOS app: bubbles with the bot's name above and its avatar beside the bubble's bottom edge in a group, neither in a DM; "Today 4:13 AM" separators after fifteen minutes; the "is working" row ("Working…" in a DM, "Chef is working…" in a group, or what the one working bot is doing, in the Mac's words and by its rules, such as "Thinking…" or "Running command: Install dependencies…" (`workingActivity` in `src/ui/format.ts`), its words shimmering inside `ShimmerView`, a native container in `lorca-core` that masks its children with the Mac's sweeping gradient) and the breathing green dot on avatars; "Message from ◉ X" and "Messaged ◉ X" markers; tool calls never shown, except a `bash` call's command card while the command needs the user, after the Mac's (`showsCard` in `src/core/model.ts`): the command's first line in a code block that opens the whole command in a sheet on tap; while Auto-review asks, its question with the answers; once the bot handed the running command over, Stop on the title's line and its last lines in a code block that scrolls past six lines, fading at an edge with more past it (Android's `fadingEdgeLength`, a gradient in the block's color on iOS); at a question, Answer, which opens `@expo/ui`'s bottom sheet sized to its content (SwiftUI's on iOS, Material's on Android; `src/ui/AnswerSheet.tsx`) holding only a field, with the command's question as its placeholder, that takes the text as typed, without capitalization or correction, and hides it unless the question is a yes or no, and Send; the sheet closes when the command ends; Running tasks (see [Terminal sessions](terminal-sessions.md)) as a terminal button beside the chat's ⋯ (a native bar button on iOS, the Android header's own button), which opens them as rows in a sheet with its own stack (`app/tasks/`), each sliding in its command's details: the bot and how the command stands, Run in Background while the bot's call waits on it, Stop Command, the whole command, and its last lines; sidebar-style previews and stamps, and in the chat list, while a chat has a turn in flight, three dots lighting up in turn and "Working…" in place of its preview.

A window at least 700 pt wide (a tablet, or a tablet window with room to spare) shows two panes (`app/(main)/_layout.tsx`, `src/ui/layout.tsx`): the chat list as a sidebar (320 pt, 375 pt from 1100 pt) and the open chat beside it; a narrower one stacks the chat over the list. The route group `(main)` holds the list and the chat in a stack of their own inside the root stack, so sheets and the pairing screen cover both panes. The sidebar (`src/ui/Sidebar.tsx`) is the same `ChatsScreen` in a native stack of its own, one screen deep, in an independent navigation tree, so it keeps the native bar and toolbar buttons; the pane's stack starts at an empty "Select a chat" screen, a chat picked in the sidebar replaces the one open, its row stays lit, and the chat's bar has no back button. Sidebar rows open their menu on a long press on both platforms, with no Link preview. On iOS the sidebar sits in a `CompactWidthView` (`modules/lorca-core`), a container that overrides the horizontal size class to compact as a split view's sidebar column does. On both platforms the sidebar's search field is a capsule at the foot of the list (`src/ui/SidebarSearch.tsx`; glass on iOS, filled on Android), level with the composer and riding the keyboard: UIKit moves a search bar into the bottom toolbar only on an iPhone, and on Android the search action is an item of the activity's one action bar, which react-native-screens hands to whichever stack updated its header last, so a sidebar's item would vanish once the pane opens a chat. The transcript sits in a `SoftScrollEdgeView`, which gives its scroll view the soft top edge a phone has where an iPad would rule a line under the bar. Bubbles and Markdown measure against the pane's width (`usePaneWidth`) and stop growing at 620 pt.

The production app icon uses the coral Beans mark. Editable SVG masters in `design/brand/` supply every platform export through `scripts/export-brand-assets.cjs`: macOS ICNS, desktop package and onboarding PNGs, tray icons, Expo icons, splash screens and favicons. Beans Dev uses a near-black icon with a coral mark. Android adaptive icons use transparent foregrounds over coral or near-black backgrounds. The export command and dependencies are in [the brand asset guide](../../design/brand/README.md).
