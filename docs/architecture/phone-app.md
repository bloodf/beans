# Phone app

`mobile/` is an Expo app (React Native, expo-router, TypeScript) for iOS and Android. A phone is a Device and never a Runner, and it links the same Device core the CLI is built from rather than porting it: `crates/mobile` (`beans-mobile`) wraps the `beans` library, built without the `runner` and `server` features, in a UniFFI object with three calls, and `mobile/modules/beans-core` is the Expo native module around it.

Beans and Beans Dev install separately as `ai.amoena.beans` and `ai.amoena.beans.dev` with primary schemes `beans` and `beans-dev`. Both also register `beans` to open the pairing links the Rust core emits; if another installed app claims that scheme, scan or paste the code inside Beans to choose the target app. Their iOS app/keychain groups are `group.ai.amoena.beans` and `group.ai.amoena.beans.dev`. Android prebuild requires an operator-supplied existing `BEANS_GOOGLE_SERVICES_FILE`; the Android-only plugin validates the file/project and a client matching the actual production or Dev application id. Missing or mismatched input fails clearly. iOS prebuild does not require Firebase. Fresh core roots are `beans-v2/core` and `beans-dev-v2/core`; storage and push decryption validate the marker before any account mutation. Existing distribution ids/groups remain unchanged, but old-format accounts and unversioned backups are incompatible and are not migrated.

`bun run android:release` builds the Rust core, runs a clean production prebuild, and assembles the release APK with a keystore outside the repo. The Android signing plugin adds the release signing configuration from `BEANS_ANDROID_KEYSTORE`, `BEANS_ANDROID_KEYSTORE_PASSWORD`, `BEANS_ANDROID_KEY_ALIAS`, and `BEANS_ANDROID_KEY_PASSWORD`; the script loads the complete set from `BEANS_ANDROID_ENV` or `~/.config/beans/android/keystore.env`, requiring both the env file and keystore to have mode 0600. Inherited signing values cannot fill missing file entries. It leaves the development signing configuration alone. The Android locale plugin puts the English permission descriptions from `mobile/locales/en.json` into default resources so translated resources have fallbacks.

Phone release versions come from the root package; EAS remote versions own store Android versionCode and iOS buildNumber. The all-scope release builds a GitHub APK, Play AAB and TestFlight store IPA, validates exact source/project/build provenance and waits for all artifacts before readiness. Store IPA is not an ad-hoc installer. Store submission is a separate manual workflow limited to Play internal testing and TestFlight. Local `android:release` and ad-hoc `release-ios` remain separate tools; Android installation needs OS approval and ad-hoc iOS installation needs provisioned devices. See [Releases](releases.md).

Settings shows the installed app version/build and update distribution status. Only the production EAS `github` profile embeds the native GitHub-update capability and installer permission; Play installs, other profiles, Beans Dev and iOS remain store/development-managed. Kotlin discovers at most 100 public stable releases and inspects at most 20 newer candidates in numeric order. It verifies exact bounded readiness bytes with the unchanged bundled Beans Ed25519 public key, validates protocol 5 and signed APK/provenance inventory, and skips server-only releases. Invalid signatures or transport failures stop discovery rather than authorizing unsigned APKs.

Each Install Update action consumes one native release snapshot. Kotlin re-verifies readiness/provenance, streams at most the signed APK size, checks SHA-256, package/version/allocated build number and compatibility with the installed package's runtime signing identity/history before creating one PackageInstaller session. Android remains final signature/rotation-capability authority. API 31+ explicitly requires user action; the unexported status receiver opens system confirmation. Unknown-source permission sends the user to Settings and requires a new check and consent afterward. Background cancels uncommitted work; committed sessions retain system confirmation. Restart abandons prior sessions and never resumes consent. Partial APKs are removed. No release signer certificate pin is invented.

One native operation deadline covers every metadata request, redirect and APK transfer: two minutes for discovery and ten minutes for installation revalidation/download. Cancellation and deadline expiry actively disconnect the current HTTP connection; every request and read checks the operation independently of progress reporting. Hashing and installer-copy loops also check cancellation before commit. Completion releases the busy gate and removes partial APKs; another check requires fresh consent.

Daily checks and exact-version skips are device-local preferences; manual checks override skip. Checks, Later and Skip never download/install. Unsent composer drafts block installation, including after navigation; other editor changes must be saved before the explicit installation confirmation. Settings warns that process replacement loses unsaved edits. Native build/device installation, signing rotation and accessibility acceptance require separate exercised evidence; source and host fixtures alone do not establish installed-upgrade acceptance.

Composer text, picked attachment paths and mention selections live in a process-local draft store keyed by account identity, relay and chat, rather than by component mount. Reopening the same chat restores its draft and clearing or sending it releases only that chat's blocker. Unmount stops dictation and retains its latest transcript as editable text, without sending. Navigation does not discard drafts; this store does not promise recovery after process termination or attachment-cache eviction.

- **The core** (`crates/mobile/src/lib.rs`): `Core.start(home, name, os, osVersion, model, listener)` loads the App from the app's own folder, sets the host facts (a phone cannot probe them), and starts the relay sync loop on an embedded tokio runtime; `request(method, params)` is one call of the JSON API in `crates/cli/src/api.rs`, blocking on the module's background queue, answering `{ result }` or `{ error: { message } }`; `wake()` asks the relay again now (the app calls it on foreground, since the sync socket may have died while iOS suspended the app). Every event on the App's bus reaches the listener as the `{ event, data }` frame the websocket carries.

JS `coreHome()` returns `beans-v2/core` or `beans-dev-v2/core` without mkdir; core owns marker-before-write validation and creation. Android PushService independently selects the exact same variant root under its files directory. Native input/generator source names are `BeansCore`, `BeansCoreModule`, `beans-mobile` and `uniffi.beans_mobile`; generated Swift/Kotlin/JNI/xcframework outputs remain generator-owned.

- **The native module** (`mobile/modules/beans-core`, picked up by Expo autolinking): a Swift `Module` and a Kotlin one, each about forty lines, forwarding `start`, `request`, and `wake` and turning the listener's frames into a `sendEvent`. `bun run core` (`build.ts`) builds the Rust for `aarch64-apple-ios` and the simulator into an xcframework with the UniFFI Swift beside it, and for `arm64-v8a` and `x86_64` with `cargo ndk` into `jniLibs` with the Kotlin (over JNA). The built pieces are gitignored; a Rust change needs `bun run core` and a native rebuild, a JS change is a Metro reload.
- **The JS side** (`mobile/src/core`): `engine.ts` starts the core, mirrors its events into the zustand store (`store.ts`, the way the macOS app's AppStore mirrors the CLI: `snapshot`, `roster.changed`, `message.*`, `job.*`, `chat.usage`, `relay.status`, `identity.changed`; events that arrive while a `bootstrap` snapshot is on its way wait and apply after it, as in the macOS app, so a snapshot built before the relay connected cannot undo that `relay.status`), and offers the screens the same verbs the macOS app has, each one request (`chats.send`, `bots.create`, `bots.update`, `pair.accept`, `providers.connect_*`, `providers.list_models`, `providers.api_key`, `providers.disconnect`, `device.rename`, `device.unpair`, `device.update`, `identity.forget`, `sync.wake`, …). `prefs.ts` keeps the one thing that is the phone's own, the dictation language. Nothing about the account is stored outside the core's folder.
- **Pairing**: the phone scans or pastes the exact `beans://pair?v=2&…` code, or opens that versioned link. Scheme, authority, version and duplicated fields are validated before core dispatch/persistence; arbitrary `pair?` strings are not accepted. The sealed handshake requires `beans-v2` and protocol 5. Deep-link handling validates the original `expo-linking` URL, not reconstructed router params, so duplicate/version evidence survives. Scan, paste and manual entry share that validation before invoking the core. Unknown fields, malformed escapes, invalid relay credentials/query/fragment, noncanonical 32-byte keys and invalid/oversized nonces reject.
- **Relay status**: the chat list's title slot (`src/ui/ChatsScreen.tsx`) stays empty while the relay connects, and speaks once that has taken a second, or four after the app comes to the foreground, when the socket the suspension killed is replaced: "Connecting…" with a spinner, or, once a try has failed (`relayError`), "Can’t connect" or, for an unknown machine, "Pair this phone again" beside a warning glyph. A tap on those opens an alert with the error (`src/ui/relay.ts`) and Try Now (a wake) or Unpair This Phone. "Update Beans to sync" takes the slot over all of them. Settings › Account › Relay shows the error in place of "Connecting…".
- **Attachments**: the composer's `+` offers the photo library, the camera, and the file picker; a picked file's path goes with `chats.send`, and the core copies, encrypts, and uploads it as a `file` blob ahead of the message. A bubble that shows an attachment this phone does not have asks `files.path`, which fetches the blob and answers with the file. Images render as thumbnails sized from the width and height in the message (full screen on tap); other files as a name-and-size card.
- **Bot avatars** (`src/ui/Avatar.tsx`, `AvatarFigure.tsx`): the shared `@beans/blobatar` API generates cached numeric endpoint geometry from stable `bot.id`, saved look, and activity state. `react-native-svg` draws a background, 24-cubic body, 4-cubic extra contour, nine petal slots, and two eyes. Reanimated computes intermediate geometry, poses, colors, and composite matrices on the UI thread through `@beans/blobatar/frame`; there is no per-frame React state or SVG parsing. Retargeting begins at the last displayed geometry. Square, squircle, circle, and transparent generated backgrounds retain their bounds. An uploaded photo uses circular cropping and overrides the generated avatar after `files.path` fetches its encrypted bytes; missing bytes use the customized generated fallback. The You avatar remains separate.
- **Activity and lifecycle** (`src/core/activity.ts`, `src/ui/avatarClock.ts`, `avatarVisibility.tsx`, `AvatarFlashList.tsx`): chat portraits pass `chatId` and each group member resolves separately; profiles and pickers use the bot's highest-priority activity across chats. Signals are structured turns, thinking, retry, pending permissions or command questions, running tools, and streaming text, never model content or localized status. Retry attribution survives another group member's message or finish. The store expires live-observed failures after eight seconds and notifies avatars; historical failures do not enter that map. FlashList viewability excludes measurement, draw-distance, and recycled offscreen rows. Native measurement and scroll notifications gate avatars in forms. Offscreen, inactive, unfocused, Reduce Motion, and `motion:false` deactivate the frame callback and snap to the selected endpoint at amplitude zero, disabling ambient and expression motion as well as morphs. Unmount unregisters the callback. Photo-only avatars mount no geometry renderer; presence pulsing stops under the same visibility and accessibility gates.
- **Look editor** (`app/chat-info/look/[id].tsx`, `src/ui/lookDraft.ts`): Details › Look edits a draft of the base and each state: all shapes, expressions, backgrounds, motion, tones, hue, and explicit body, eye, and background colors. State choices inherit omitted base fields and palette channels. Shuffle changes generated customization; Same as Base resets one state; Restore Default Look clears customization without removing the photo. The generated preview uses the real geometry renderer, even with a retained photo shown separately. Contrast feedback uses the shared resolved palette and never discards explicit colors. Preview Activity Cycle stops offscreen, in the background, on route blur, and under Reduce Motion. Photo selection, replacement, and removal stay in the draft. Save submits look and photo together in one `bots.update`; failure retains the draft and shows an error. Invalid color input blocks Save. Cancel and system navigation confirm discarding unsaved changes; an in-flight save keeps the editor open until completion.
- **Group details**: Group Info edits Name and Description; Description pushes a full editor and saves through `chats.set_description`. Every member reads the shared description in its system prompt. A DM uses its bot's description instead; see [DMs and groups](bots.md#the-lead-bot).
- **Memory services** (`app/chat-info/memory/`, `app/settings/memory/`, `src/core/memoryService.ts`): DM Details › Memory opens the bot's recall/capture draft, explicit save/search/inspect/reflect, delivery queue, fenced deletion and capability-driven backend panels. The page links account connections and embedding profiles. The focused native wrapper uses the same public `beans-core.request` transport as `engine.ts`; service operations route to the assigned Runner, while local asset setup names a selected paired Runner. The phone contains no vector SDK or ONNX runtime. Stored keys/endpoints/options stay masked; secret edits distinguish keep, replace and clear. OpenViking binds exact bot IDs to USER keys or an explicitly trusted gateway. Capture starts off, covers future eligible turns only, and group text has separate approval; unattended capture stays unavailable without enforceable downstream spending policy. Service, reflect and advanced operations require explicit action approval with plaintext/cost disclosure, never render-time requests or automatic retries. Pgvector setup displays the actual target and full SQL; Lance binding/export/import displays private Runner-local paths, namespace and vector-space fingerprint. Local runtime/model/tokenizer setup previews exact sources, licenses, bytes and hashes on the selected Runner. Apply sends only the frozen one-use token/digest and affirmative confirmation, not changed paths or SQL. The independent local MEMORY.md editor retains hash-based conflict protection. Save/Cancel and system dismissal share draft guards; busy work blocks removal and failed requests retain drafts. Phone fixture tests cover consent, masking, exact approvals and failure states without live service calls.

Memory deletion invalidates its confirmation at attempt start and refreshes preferences in `finally`, including failed and pending remote results. A failed refresh disables document/bank deletion until an explicit refresh succeeds; cleanup confirmation uses the refreshed deletion epoch. OpenViking connection edits patch only named bot IDs: omitted bindings keep their private identity/key, and explicitly confirmed `null` removes only that bot’s binding. Keep key requires the exact saved bot/mode/account/user identity, enforced by core. Changing identity, changing key action or removing/reopening a draft discards entered replacement bytes. Metadata-only saves omit options; the phone never sends whole-map replacement flags or reads saved keys back.

Advanced panels intersect their concrete adapter-defined forms with the negotiated `advanced_actions` map for the exact feature and verb. Missing or empty permissions hide feature links, action selectors, fields and Run controls; feature-level support alone never authorizes a verb. The request helper rechecks exact permission and plaintext approval before dispatch. Document deletion is excluded from advanced actions and uses only the confirmed revision/epoch-fenced `memory.service.delete` path.

LanceDB Cloud activation is disabled until an upstream safe transport hook exists. The phone reports `lancedb_cloud_transport_unavailable`, not missing credentials, and exposes no Cloud URI, region or key editor. Its connection boundary rejects Cloud inputs before dispatch, with no paid or local fallback. Masked metadata edits preserve the private target; explicitly configuring Runner-local storage requires confirmation before clearing an existing endpoint/key. Local binding and transfer remain explicit operations on the assigned Runner, never phone database execution.

Connection snapshots require masked `availability: supported | blocked` and `reason: null | string`. Supported means eligible configuration, not initialized/ready. Blocked connections appear with their reason but cannot be selected or activate preferences, readiness, service, queue, deletion, advanced or setup actions. Supported Runner-local Lance keeps its explicit setup flow. Optional health `reason` is displayed separately from eligibility. No endpoint, path, key or additional wire field is inferred or exposed.

`mobile/metro.config.js` extends Expo's Metro defaults with the file-linked `packages/beans-blobatar` source as a watch folder and `mobile/node_modules` as a resolver search path. Its React and `react-native-svg` imports use the app's installed copies, including `react/jsx-runtime`; Metro does not install or bundle a second React for the adapter.

`bun run release-ios --local` builds the release core and copies `mobile/` into `dist/ios/mobile` without uploading. The release copy also carries `packages/beans-blobatar` at `dist/ios/packages/beans-blobatar`: the first copy uses APFS clone copies, later releases sync changed files with rsync. Its `mobile/node_modules/@beans/blobatar` link points to that copied source rather than Bun's absolute per-file links into the working tree. Metro watches the copied package and resolves React and `react-native-svg` from the copied mobile app, keeping one React instance when Xcode bundles the iOS app. The script then prebuilds, installs pods, and archives from the copied project; only a run without `--local` exports and uploads.

- **Dictation**: the primary disc is Dictate while the field is empty (a small microphone sits inside the field once there is text). While recording, the field shows Grok Bot's pill: a stop square, the elapsed time, and bars that follow the microphone, with Send still beside it. The words land in the field after whatever was typed when the user taps the square, or go out at once when the user taps Send. The recognizer (`expo-speech-recognition`) listens in the first of the phone's preferred languages it supports (`src/ui/dictation.ts`; a Chinese speaker on an English-region phone gets zh-CN), or the language chosen in Settings or by a long press on the microphone.
- **Notifications** (`src/core/push.ts`, `expo-notifications`): after pairing, and on every launch and foreground, the app asks for permission once, reads the native device token, and registers it with the relay through the core (`push.register { platform, token, environment }`). The Swift module writes the core's push key into the build's keychain group (`group.ai.amoena.beans` or `group.ai.amoena.beans.dev`) at start and on `identity.changed` (removed when the phone holds no account); the notification service extension is its own target, generated at prebuild by `@bacons/apple-targets` from `targets/notify`. A tap opens the chat, a reply in the chat on screen makes no banner, and opening a chat dismisses its notifications. App and extension use keychain account `beans-v2.push-key` in the preserved groups; fresh-format code neither reads nor deletes the prior slot.
- **Turns**: sending is `chats.send`; the core admits a `turn` Job on the bot's Runner or a group room, exactly as any Runner's CLI does. When a direct turn already owns the chat, the Runner promotes the new user message as steering after the current model step and its tools settle, and a question the turn waits on is dismissed rather than waited for; the admitted Job then exits when it reaches the lock because that message was already handled. In a group, the current member settles and the newly admitted room takes over. The `job.started` / `job.finished` events drive the "is working" row and "Chef stopped without replying"; `job.thinking`, `job.retry`, and the running tool rows fill in what the bot is doing, which the core reads in the Runner's `machine` blob and the chat log. The row shows every turn in flight, whichever Device started it, and is back when the app is closed and opened again (see Working state in [macOS chat](macos-chat.md)). The phone has no hard Stop control.

Settings › custom provider offers Refresh Models, which asks the core to run `providers.refresh`; newly discovered model IDs appear in the bot's Model picker without replacing the saved selection. The action reports changed, unchanged, or a generic error without revealing the provider key.

When a refresh snapshot omits optional provider or model lists, the store keeps them only for the same paired identity and relay URL; explicit empty lists clear them. Account changes, forgotten identities, and relay-source changes discard prior catalog metadata. A `relay.status` URL change clears those lists before a later partial snapshot can reuse them, without changing a bot's saved model.

Native screen presentation and adaptive navigation are described in [Phone interface](phone-interface.md).

The production app icon uses the coral Beans mark. Editable SVG masters in `design/brand/` supply every platform export through `scripts/export-brand-assets.cjs`: macOS ICNS, desktop package and onboarding PNGs, tray icons, Expo icons, splash screens and favicons. Beans Dev uses a near-black icon with a coral mark. Android adaptive icons use transparent foregrounds over coral or near-black backgrounds. The export command and dependencies are in [the brand asset guide](../../design/brand/README.md).

## Development loop

`bun run mobile:dev` (`scripts/mobile.ts`) is the Beans Dev phone loop on the iOS Simulator, or on `--device <name or udid>`: it fingerprints the crates the phone links, the prebuild inputs (Expo config, assets, `package.json`, plugins, targets), the pod inputs with the checkout's path, and the native module sources (stamps in `mobile/.expo/dev-stamps.json`), rebuilds what is stale (`bun run core ios`, a clean `expo prebuild`, `pod install`, `expo run:ios`), starts Metro, and opens the dev client on it. A Rust save while it runs rebuilds the core and installs the app again. The Mac and phone loops leave production Beans processes alone, so all builds run side by side.
