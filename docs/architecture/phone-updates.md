# Phone releases and updates

iOS builds go to TestFlight, which updates them. Android GitHub APKs ship on stable `beans-vX.Y.Z` releases as `Beans-X.Y.Z.apk`, built by the all-scope release path ([Releases](releases.md)). The root `package.json` supplies the version; EAS remote versions own Android versionCode and iOS buildNumber. Play AAB and TestFlight IPA updates stay with those stores. Local `scripts/android-release.ts` remains a separate release tool.

## Distribution and native gate

Only the production EAS `github` profile embeds the GitHub-update capability and installer permission. `beans-core` must expose every signed-update function and its progress listener; absent, incomplete or failing native capability stays blocked before discovery. Beans Dev, iOS, non-GitHub profiles and Android below API 28 cannot self-update. The native installer-source check accepts a missing installer of record (sideload) or Beans itself after a Beans-managed update. Every other recorded installer, including Play, third-party stores and system package installers, is conservatively store-managed. Device acceptance must establish which sideload paths produce an eligible source.

Settings shows the installed version/build, distribution status, daily-check switch, manual check and exact-version skip. Once a day at launch or return to the foreground, Kotlin discovers at most 100 public stable releases and inspects at most 20 newer candidates in numeric order. GitHub metadata is discovery input, never install authority. The native verifier checks exact bounded readiness bytes with the unchanged bundled Beans Ed25519 public key, protocol 5, the signed APK inventory and signed EAS provenance. Server-only releases are skipped; an invalid signature or transport failure stops discovery.

## Consent, progress and cancellation

A verified snapshot supplies an opaque one-use id, version and plain-text release notes. The daily alert offers Install Update, Remind Me Later and Skip This Version; Settings has the same actions. Automatic checks and dismissal never install an APK. Skip suppresses only that version's automatic offer; manual checks override it. Every button captures its exact snapshot id, so a stale alert cannot authorize or dismiss a newer offer. Install warns that process replacement loses unsaved edits, and unsent composer drafts, replies, pending sends, dictation and microphone-permission work block it ([Phone app](phone-app.md)). New composer work cancels an uncommitted download. If Android has already committed the session, the app warns the user to cancel system confirmation to keep newly created drafts.

Install opens the Material dialog from `mobile/src/ui/UpdateProgress.tsx`. Download progress is a finite fraction, clamped to 0–1 and monotonic for the active snapshot. The bar becomes indeterminate after native commit and stays visible through system confirmation. Hide changes only the dialog's visibility; Settings retains download progress. A new installation shows the dialog again. Failure closes progress and displays an alert. Each native event carries its snapshot id; stale events, late promise completions and download events after commit cannot restore a cancelled dialog or regress its phase. Installer results are checked on return to the foreground and while confirmation is pending, including failures that do not cause a focus change.

Native foreground admission follows the Activity resume/pause lifecycle, not window focus, so the app's own progress dialog does not block installation. Backgrounding cancels discovery and uncommitted installation, invalidates the offer and disconnects transport. A committed PackageInstaller session retains its system confirmation. Cancellation synchronously reports native commit state under the same lock as commit, so a delayed progress event cannot erase tracking or stop result checks. Unknown-source permission sends the user to Android Settings and requires a new check and consent afterward. Restart abandons prior sessions rather than resuming consent. Partial APKs are removed.

## APK verification and installation

Installation re-verifies readiness and provenance; exact readiness digest, APK digest, size and allocated versionCode must still match the consented snapshot. Kotlin streams at most the signed APK size, checks SHA-256, package name, version and build number, and compares the APK's signing identity/history with installed Beans before creating a PackageInstaller session. Multiple current signers must match exactly; a single-signer rotation must contain the installed signer in the authenticated candidate history. Android remains final authority for signature/rotation capabilities. No release signer certificate pin is invented.

API 31+ explicitly sets `USER_ACTION_REQUIRED`; the unexported status receiver opens Android's confirmation. If confirmation is absent or launching it throws, the receiver records failure, clears the saved session and abandons it; another attempt requires fresh consent. The updater does not request silent installation. Metadata, redirects and APK transfer share a total operation deadline: two minutes for discovery, ten for installation revalidation/download. Cancellation and expiry disconnect HTTP; request, read, hashing and installer-copy loops check cancellation before commit. Completion releases the busy gate, and another attempt requires fresh consent.

Source and host fixtures do not establish installed-upgrade acceptance. Full Expo/generated bridge assembly, on-device success/denial/cancellation/rotation, draft preservation and accessibility QA remain separate evidence for [#252](https://github.com/bloodf/beans/issues/252) and [#419](https://github.com/bloodf/beans/issues/419).
