# Codemode and Plugins

## Codemode

A bot uses plugins by writing a script, after pi's codemode: `codemode { code }` runs JavaScript whose calls reach the plugins' tools, and only what the script outputs or returns reaches the model. A script pages through an API, runs calls in parallel, filters what came back, and hands the bot the lines that matter, so the results it read never fill the bot's context, never become chat rows, and never sync.

- **The sandbox** (`lorca_agent::codemode`): each script runs in a fresh QuickJS VM (`rquickjs`) on a thread of its own, with a 256 MiB heap, no timers, network, file system, or modules, and one way out: the bridge that carries its calls and output. Stop ends it wherever it stands, and so does its deadline: 30 minutes, 10 in a routine, questions to the user included. The code is an async function body and may start with `// @options: {"max_output_tokens": …, "timeout_ms": …}`; the output has a 10,000-token budget, keeping its start and end, with the whole text in a temp file the result names. The host bounds what a script sends it: past 16 MB of output or 1,000 calls it has not awaited the script stops; up to ten images are prepared from their bytes for the model, with invalid ones left out. A call whose arguments cannot be read rejects without running, and `store()` writes over their limits fail the script.
- **What a script calls** (`plugins::mcp::PluginCatalog`): `tools.<plugin>__<tool>(args)` for installed plugins, and `read`, `write`, `edit`, `grep`, `find`, `ls`, `memory_update`, `memory_log`, and `recall` with the bot's own arguments. When shell is permitted, `tools.bash({ command, description? })` runs one command at a time on pipes with no stdin, not a persistent terminal; it resolves to the output (up to 1 MB, keeping both ends when cut), exit code, wall time, and full-output path when truncated, including a nonzero exit. A plugin tool resolves to its whole MCP `CallToolResult` (`content`, `structuredContent`, `isError`), uncut; other local tools resolve to their text. At most eight calls run at once, and one that may ask the user runs alone. `searchTools(query)` ranks plugins' tools; `describeTool(name)` gives a declaration; `describeNamespace(name)` gives one visible plugin's complete instructions and tools even when its listing was cut. `store(key, value)` and `load(key)` keep JSON in the Runner's database per chat and bot (`codemode_store`), never synced. `models.ask(prompt, { system?, maxTokens? })` asks the small model on the bot's provider to rate, sort, or summarize items without reading them itself: four answer at once and 200 per turn, with tokens and cost counted in chat spending, not its context size.
- **The listing**: the tool's description, rendered once per turn, declares callable tools as TypeScript: shared MCP result types, `models.ask`, local tools (with the structured output shape of script bash), and each plugin's name, description, what it needs, the start of its servers' instructions, and its tools' declarations from JSON Schemas. About 3,000 tokens are offered, each plugin getting one tool before any gets all. A plugin with no saved list remains named; `describeNamespace()` or a call by name connects it.
- **Every call goes through the loop**: arguments and current account Pause and bot shell/write/plugin capabilities are checked before the nested call runs, including after an approval wait. Shell and writable plugin calls go through Auto-review with the script beside them. A refusal, unanswered question, or new-message dismissal ends the script; waiting calls never start. A question stopped waiting reads as dismissed, not as the user's no. The script's row retains nested calls; its working state names the latest command's description as "Running command: …" or the plugin as "Using GitHub…", and its finished row summarizes the plugins used.

Custom servers entered in a Runner's `mcp.json` use this same catalog, permission gate, and sign-in flow; their file, lifecycle, and management API are in [MCP servers](mcp-servers.md).

## Plugins

A plugin is an MCP server (or several) a bot can use, after Grok Bot's marketplace: GitHub, Jira, Notion, Stripe, Zapier, a headless browser, and the other services the bundled index lists. A plugin is described by a manifest (`crates/cli/src/plugins/mod.rs`): `id`, `name`, `description`, `icon`, `author`, `category`, and `featured` for the marketplace, `servers` (`stdio` with `command`, `args`, `env`, or `http` with `url`, `headers`, and `auth`: `oauth` or `bearer`), `variables` (setup fields, `secret` ones never read back), `skills` (notes written to the plugin's folder that the prompt points the bot at), and `tools` hints (`readonly` patterns, `hide`). `${VAR}` in args, env, and headers is filled from the variables; a header or an environment variable that names a variable with no value is left out, so an optional key left unset is never sent as its placeholder (Context7 refuses every call made with one). A stdio server starts in its plugin's folder with the login shell's environment (see [Tools](tools.md)), so a `command` such as `npx` or `uvx` resolves from the user's `PATH`, on Windows through `PATHEXT` as a terminal finds it (`npx` is npm's `npx.cmd`); the manifest's `env` goes on top. A server that cannot start says so with the file it found: `Cannot start npx (C:\Program Files\nodejs\npx.cmd): batch file arguments are invalid`.

**Installed per Runner, gated per bot.** The Runner holds the install under `~/.lorca/plugins/` (`installed.json`, the plain variables; `secrets.json`, mode 0600, the secret variables and OAuth tokens; a folder per plugin with its skills) and advertises each plugin's id, name, and state (`ready`, `needs_setup`, `needs_auth`, `connecting`, `error`) in its `machine` blob, so every Device lists what each Runner has without a secret leaving it. A bot sees and calls only the installed plugins its encrypted `capabilities.plugins` allows; a capability edit takes effect at the next tool boundary on a synced Runner. Installing, removing, setting variables, signing in, and reading a plugin's detail run on the Runner: locally when the app's CLI is that Runner, else as a `request` sealed to it (`plugins.install`, `plugins.uninstall`, `plugins.variables`, `plugins.connect`, `plugins.detail`), so a phone installs a plugin on another computer and hands it a key through ciphertext.

An installed marketplace plugin follows text-only index updates at startup and when the marketplace loads. Changes to servers (including command, args, env, cwd, URL, headers, and auth), setup variables, skills, or tool permissions stay pinned to the installed manifest; its status says the marketplace update requires reinstall. Explicit reinstall from the marketplace approves the new manifest. Saved OAuth tokens and challenges are bound to each HTTP server's origin, including marketplace plugins; originless older sign-ins require signing in again. A plugin installed from its own manifest (`plugins.install { runner_id, manifest }`) is left as it is.

The bundled Browser manifest launches `@playwright/mcp@0.0.83`, whose Playwright dependency is `1.64.0-alpha-1790635538000`. Marketplace resolution pins Browser to that bundled manifest; installed Browser servers remain pinned if their identity differs, until explicit reinstall. The Runner needs a compatible Chromium installation. Network egress restrictions belong to the deployment, not the plugin permission gate. An allowed shell or plugin may still read and write Runner files; an offline Runner cannot learn a new account restriction until it syncs.

**The marketplace** (`crates/cli/src/marketplace.rs`), after Grok Bot's, offers plugins and bots: a version-1 JSON index with UTC `updated`, plugin manifests (`plugins`), and bot templates (`bots`). The CLI bundles `crates/cli/marketplace/index.json`; the configured relay serves `/marketplace/v1.json` as a public feed. `LORCA_MARKETPLACE_URL` or `marketplace_url` in settings overrides that URL, and `LORCA_MARKETPLACE_FETCH=0` turns fetching off. On startup the Device reads a validated cache from `marketplace.json` only when its saved source matches the current feed, keeping a newer index than the bundle even offline. The app checks the feed at most hourly, sends its ETag for a 304, and can force a reload; a missing plugin search or install checks at most every five minutes. A valid newer relay index replaces the current relay index in full; an explicit custom URL instead overlays its entries by id on bundled entries, retaining bundled entries it omits. An older index cannot downgrade either, and unreadable entries are skipped without discarding valid plugins. Browser remains pinned to the bundled manifest. The public GET carries no account credentials. An entry with `featured` is listed under Featured Plugins or Featured Bots, in index order, and `category` names its section, one of Grok Bot's filter categories (`credentials`, `productivity`, `communication`, `design`, `code`, `data`, `sales`, `finance`, `research`, `support`). Each remote plugin in the bundled index is the service's own server, and it needs no account, signs in through dynamic client registration with the Runner's loopback redirect (GitHub's device flow aside), or takes a personal API key the user copies from the service (Zhihu, Metaso), so a plugin never asks the user to register an app first. `marketplace { query? }` answers with the plugins, each with the Runners that have it, and the bots, each routine with its schedule in words (`schedule_text`); a query keeps the entries that have every word.

**Bots from the marketplace.** A bot template is a bot's starting point: `id`, `name`, `summary` (its line in the marketplace), `description` (the new bot's description, so its instructions), `symbol_name` and `accent`, `category`, `featured`, `author`, `plugins` (the marketplace plugins it works with), `routines` (`name`, `schedule`, `prompt`), and `memory` (facts it starts with). `bots.create { template_id, greeting }` makes a bot from one, as Grok Bot's template import does: the template's profile, its routines added paused, and the app's `greeting` ("Hi Researcher, introduce yourself.", in the user's language) as the user's first message in its DM. The turn that answers carries the setup (`Job.setup`: a `TemplateSetup` of the plugins, the routines' names, and the facts), and the Runner puts a cue after the greeting (`turns::setup_cue`): save the facts with `memory_update`, ask once whether to turn the routines on and resume them only on a yes, call `install_plugin` for each plugin the Runner lacks (the user allows or denies each on its card), and greet the user. The cue exists only in that turn's context; the chat keeps the greeting and the reply.

**At turn time** (`crates/cli/src/plugins/mcp.rs`, `rmcp`), the system prompt carries a bounded catalog of installed plugin ids, names, states, and skill locations, and the turn's codemode listing declares their tools (Codemode, above). A plugin's tools come from `catalog.json` in its folder, what its servers offered when they last connected, so listing them starts no server and reads the same from turn to turn. A server writes it each time it connects, and a plugin that becomes ready (an install, a setup, a sign-in) connects once in the background to write it. A script's call connects its server on first use; the Runner keeps connected servers in a pool (stdio children, or streamable HTTP with the plugin's headers, a pasted token, or the saved OAuth tokens), so later calls reuse them. A server has two minutes to start and answer the handshake, and a connection that began before the plugin's settings changed (an install, a setup, a sign-in, a removal) is dropped rather than kept or saved. Browser-flow OAuth tokens are refreshed by the transport and written back as soon as the handshake rotates them. A device-flow token is a plain bearer; the Runner refreshes and saves its rotating pair itself, and drops the pooled connection before that bearer expires so the next use reconnects with a fresh one.

A tool the server marks read-only (`readOnlyHint`) or the manifest lists as such runs at once. The mark counts only as the live server gives it, never as `catalog.json` holds it, since a bot can write that file: the review connects the server, through the pool, to read it and the tool's description. Any other tool goes through the same Auto-review boundary as local actions: the loop's `before_tool_call` (`mcp::review_call`), before the MCP call, with the script it comes from beside the call, marked as the bot's own words. When it asks, the card reads "Chef wants to use GitHub · create_issue · repo: …"; Always allow saves the exact `plugin/tool`. A refusal ends the script (Codemode, above). Server instructions appear in the plugin's section of the listing and do not replace the server’s own tool description at the permission-review boundary.

**Sign-in** for a remote server is the MCP authorization flow, held by the Runner through `rmcp`: discovery from the server's challenge, dynamic client registration as a native app, PKCE, and a loopback redirect on a free port, whose code the Runner swaps for the tokens with its PKCE verifier. The browser opens on the Device where the user asked (`plugins::sign_in`): the Runner's own, or any other Device's, which listens on its own loopback and sends the redirect with its request (`redirect_uri`). The Runner registers that redirect and answers with the page and the sign-in's id; the Device opens the page (a computer's browser, or a phone's in-app browser through the `plugin.auth` event) and sends the Runner where the browser landed (`plugins.sign_in.finish`), sealed like every request, or that the page closed first (`plugins.sign_in.cancel`), after which the card asks again. So a phone signs a computer's plugin in with nobody at the computer. It starts from a card in the chat, as in Grok Bot: after an install that needs a sign-in, or when the bot calls `connect_plugin`, the bot posts a `permission` message with `tool` `connect` ("Chef needs a sign-in to GitHub · Sign in to GitHub on Workbench · Sign in · Not now"); Sign in answers it with `chats.permission { decision: allow }`, and the card then reads "Finish signing in in the browser on Pocket" (the Device where the page opened), "Signed in", or "Sign-in failed: …" (`decision` `allowed`, `connected`, `failed`). Once the plugin is signed in, by any card, its sheet, or a pasted token, every card of the Runner's bots that asks for it reads Signed in, and Sign in on a card that waited through it reads Signed in without starting another. A chat holds one waiting sign-in card per plugin and Runner: asked again before the user writes, as when the bot calls `connect_plugin` after an install already put the card up, the Runner answers with that card; asked after, it puts up a new one and the old one reads Dismissed. The inspector's plugin sheet offers the same sign-in. Discovery is seeded from the server's own 401 challenge, since GitHub keeps its resource metadata under the server's path. A manifest can name a `token_variable` so a pasted token stands in for the sign-in, and `client_id_variable` / `client_secret_variable` (or fixed `client_id` / `client_secret`) for a server that registers no clients on the fly; the card says what to fill in when nothing is set. With a `client_id` and a `device_authorization_endpoint` plus `token_endpoint`, the sign-in is the device flow (RFC 8628) instead: the Runner asks for a code, the card shows it with the link ("Copy code and open github.com" on the Mac, the same on the phone), and the Runner polls until the code is entered. While the code waits, the plugin reads "Enter the code at github.com" and `plugins.detail` carries the code and link on the server's `auth` (`code`, `link`), never the machine blob, so the plugin sheet, where a sign-in starts with no card, shows the same code and button on any Device. Nothing opens on the Runner's screen, so the card works from any Device, and no client secret ships. GitHub's entry uses the device flow with Lorca's own OAuth app. GitHub may issue an eight-hour access token and a rotating refresh token; Lorca refreshes it directly at GitHub's token endpoint, persists the new pair before connecting, and uses the access token as the MCP bearer. A saved browser-flow sign-in whose server metadata cannot be found again also falls back to a bearer. `LORCA_OAUTH_NO_BROWSER=1` fetches the authorize page instead of opening a browser, for tests against a fake server.

**The bot** can search the marketplace (`search_plugins`) and, when the user agrees on a permission card with `tool` `install`, install a plugin on its own Runner (`install_plugin`), as Grok Bot's InstallPlugin does after a question. It is told in the result what setup the user still owes (a sign-in, a variable).

**The apps.** The macOS marketplace (`macos/Sources/Lorca/Marketplace/`) is a sheet, as Grok Bot's is an overlay, of up to 800 by 700: the marketplace icon at the foot of the chats' sidebar opens it, as do File › Marketplace… (⌘⇧M, so the command palette has it too), Add from Plugins… in a DM inspector's Plugins section (on that bot's Runner), and the same row in Settings › Plugins (on the picked Device). Its top bar has Back, the Runner that plugins install on and bots are added to (a pop-up when there are two or more), and Close, which Escape presses from any page. The home page has the title with "N installed" (the Runner's plugins, on a page of their own), the search over plugins and bots, and then Featured Plugins, Featured Bots, and a section per category (its plugins, then its bots, leading with what the featured sections do not show and keeping half the rows for bots when it has both), each a two-column grid of up to four rows with View all (a featured section's lists every plugin or every bot, the featured ones first); a query puts the results in their place, and a category's View all or the results offer All, Plugins, and Bots when both kinds are there. A plugin shows its real mark on a white tile, in light and dark mode alike (`Design/PluginLogo.swift`: mostly Simple Icons' CC0 paths in the brand's color, Playwright's logo for Browser, and the brand's own mark for the rest), here and in the inspector and Settings; a plugin without one shows the SF Symbol its manifest names. A plugin's row offers Add, then shows Added, Connect, or Set Up (the last two open the plugin's own sheet); its page has the description, its state on the Runner with Manage…, its servers, skills, and setup variables, and its developer, category, and website. A bot's row and page offer Add; its page shows Instructions, Memories, Routines, and Plugins beside a list of the four, as Grok Bot's does, and adding the bot closes the sheet on its chat. A DM inspector's Plugins section has a row per plugin the bot's Runner has, ending in a green check when it is ready and an orange exclamation mark when it needs something; the mark's tooltip, or a click on it, says what the Runner reports (the same row lists plugins in Settings and the marketplace). A plugin's sheet shows its state, the sign-in per OAuth server, the variables (secret fields write only), the Always allowed rules for its tools with Reset, its skills, and Remove. Settings → Plugins lists what the picked Runner has installed. Settings → Auto-review has the switch ("Lorca checks each action before it runs and asks you first when needed") and a card per rule: its text, with its behavior, Edit, and Delete in a footer beneath it. The section's plus button and each rule's Edit button open sheets; the text of a rule for an exact plugin tool is read-only there, while its Allow automatically or Ask first behavior can change. The transcript shows the permission card: the question ("Chef wants to use GitHub"), the call, Auto-review's reason, Allow once, Always allow, and Deny, and under them the rule Always allow adds ("Always allow adds the rule “…”."); an install offers Allow and Deny. A shell command asks on its own command card instead (see Terminal sessions in [Tools](tools.md)), and what a bot types into a running command asks on a permission card with the command in a code block (its first two lines; a click opens the whole command in a sheet with Copy), Allow once, and Deny. Answered, the card is the answer and the call, and an Always allow says which rule it added. The row's height and the card's layout come from one measurement (`PermissionCellView.Layout`). A shell card's `command` is the whole command (its first 8,000 characters), which `Message::for_app` takes from the reviewed arguments the apps otherwise never get. The phone shows the same card, with Sign in's page in its in-app browser; an answer that cannot reach the Runner (asleep or offline) puts the card back and says why in an alert. It shows the Runner's plugins in chat details, and Auto-review in its settings.
