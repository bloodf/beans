# Protocols

Local request dispatch and relay protocol admission are separate boundaries. The mandatory Beans protocol and format checks also apply to new service methods; method discovery does not grant execution authority.

## App ↔ CLI (local WS)

JSON on `ws://127.0.0.1:<port>/ws`: fresh Beans defaults to `4874`, and Beans Dev to `4875`, paired with isolated v2 homes. Requests are `{ id, method, params }` and get `{ id, result }` or `{ id, error: { message } }`; events are `{ event, data }`.

App → CLI: `hello`, `bootstrap` (which also checks the selected Beans relay's public model catalog and marketplace index, each at most hourly), `models.reload` / `marketplace.reload` (checks now; answers the catalog's or index's `updated` and whether it `changed`), `identity.create`, `identity.restore`, `pair.start` / `pair.status` / `pair.cancel` / `pair.accept`, `sync.account` (the account's `providers`, answered once the sync loop has pulled the account this Device holds, its roster, Devices, and credentials, or after 30 s: onboarding asks after a restore or a pair), `config.set`, `bots.create` (`runner_id` may be another Device; it must be a Runner; `template_id` and `greeting` add a marketplace bot) / `bots.update` / `bots.delete`, `chats.create` / `chats.dm` / `chats.send` / `chats.send_now` / `chats.stop` / `chats.delete` / `chats.rename` / `chats.set_description` / `chats.set_owner` / `chats.pin` / `chats.add_bot` / `chats.remove_bot` / `chats.mark_read` / `chats.messages` / `chats.search` / `chats.compact`, `routines.create` / `routines.update` / `routines.delete` / `routines.run` / `routines.describe`, `marketplace`, `plugins.install` / `plugins.uninstall` / `plugins.set_variables` / `plugins.connect` / `plugins.sign_out` / `plugins.detail` (`runner_id` names the Runner) / `plugins.auth.cancel` (a phone's sign-in page closed) / `auto_review.set` / `chats.permission`, `mcp.list` / `mcp.get` / `mcp.save` / `mcp.remove` / `mcp.set_enabled` / `mcp.reconnect` / `mcp.sign_in` / `mcp.sign_out` / `mcp.hide_tool` / `mcp.reload` (a Runner's `mcp.json`, `runner_id` naming it) / `mcp.parse` (pasted JSON, read here; [MCP servers](mcp-servers.md#managing-it)), `bash.stdin` / `bash.stop` / `bash.background` (a command's row, on its Runner from any Device), `bots.memory` / `bots.memory.write` (this Runner's bots), `providers.connect_deepseek` / `providers.connect_anthropic` / `providers.connect_opencode` / `providers.connect_opencode_go` / `providers.connect_chatgpt` / `providers.connect_grok` / `providers.connect_custom` (adds a custom provider, or saves the one `kind` names, and answers its `kind`) / `providers.list_models` (a custom provider's server's chat models, before saving) / `providers.api_key` (one saved key and base URL, for an editor) / `providers.auth.cancel` / `providers.disconnect` (the account's credentials; a custom provider is deleted), `ui.watching` (the chat on screen in the desktop app), `push.register` / `push.unregister` (a phone's device token).

CLI → App: `attention.changed` (the decrypted attention list), `budgets.changed` (every Runner's limits, what its work used, and what stopped), `reviews.changed` (an item of the encrypted local review projection and the change: [Review queue](review-queue.md)), `snapshot` (what `roster.changed` carries, with each chat's newest messages, the relay's state, the turns in flight, and `budgets`), `roster.changed` (devices, each with the `name` the account shows and its `machine_name`, with `unknown: true` on a machine that never sent its `machine` blob, bots, chats, routines, `providers`, the account's credentials as statuses: `kind`, `is_connected`, a masked `detail`, `base_url?`, and for a custom provider, listed after the built-in ones in the order they were added, its `name`, `api`, and `models` (`id`, `name?`, `context_window?`, `max_output?`, `images?`, and the thinking `levels` it takes, which the pickers offer for it as they do the catalog's), and `models`, the model catalog's `provider`, `id`, `name`, thinking `levels`, and `decides` (a decision model) for every model in its order, which the pickers offer and a newer catalog replaces), `message.added` / `message.updated` / `message.removed`, `chat.removed`, `job.started` / `job.finished` (with `routine_id` for a routine's run) / `job.retry` / `job.thinking`, `chat.usage`, `relay.status`, `provider.auth` (the OAuth URL a phone opens in its in-app browser), `plugin.auth` / `plugin.auth.done` (a plugin's sign-in page for a phone's in-app browser, and that it can close), `pair.completed`, `identity.changed`, `app.update.install` (a Device asked the desktop app for its update).

Routines take an IANA `timezone` and a `missed_run_policy` (`coalesce` or `skip`) on `routines.create` and `routines.update`, and `routines.describe { schedule, timezone?, missed_run_policy? }` checks both. A routine on the wire carries its `health` and a derived `state` ([Routines](routines.md)). `device.service_status { id? }` answers `{ installed, running }` for this CLI's service, or another Runner's through the sealed `service.status` request.

`handoffs.list/get/follow_up/cancel/report` inspect and manage durable delegated work through the same local API. Their request and report shapes, source-chat destination and per-attempt job comparison are described in [Handoffs](handoffs.md#inspection-follow-up-and-recovery).

Workflows add `workflows.start` / `workflows.get` / `workflows.configure` / `workflows.connection` / `workflows.sample` / `workflows.review` / `workflows.enable` / `workflows.cancel`, each answering the setup's view; `marketplace` answers `packs` beside `plugins` and `bots`. The roster's optional `workflows` array carries the setups, merged one by one, and a sample is a `workflow_sample` job on the existing sealed job path: [Workflow onboarding](workflows.md).

[Local API](local-api.md) is the complete reference for this socket: each method's params and result, the events, the field errors, the trust boundary, and the methods and events the two lists above leave out (`pair.abort`, `device.rename`, `device.unpair`, `identity.forget`, `identity.delete`, `sync.wake`, `account.pause`, `files.path`, `providers.refresh`, `memory.changed`, `pair.posted`, and the `memory.*` setup and service methods).

The app may choose ids (`bots.create.id`, `chats.create.id`, `chats.send.message_id`) so its optimistic rows match the CLI’s events.

`update.status` / `update.prepare` / `update.cancel` are local Runner drain control, with token-authenticated mutations. `device.update` / `device.auto_update` reject before local installation or remote routing in Beans. The retained incoming `self_update.install` / `self_update.auto` verbs reject independently of drain control. Device metadata carries `version`; this Beans core leaves optional CLI `update` status absent. See [Service management](service-updates.md#service-management).

`bots.create` / `bots.update` accept the version-1 `look` object (`base` plus optional `states`). An omitted update keeps it, null resets generated settings, and an object replaces the complete validated draft. `avatar` remains independent. Look validation precedes image storage or profile mutation; see [Bot avatars](avatars.md#saved-look-version-1).

What the apps get of a chat is a view of the message rows in `beans.sqlite3` (`LocalStore::page`, then `Message::for_app`). A snapshot queries each chat's newest 60 messages and sets `has_more` when older rows remain; `chats.messages { chat_id, before?, limit? }` queries the page before a message id, oldest first, with `has_more`. The macOS transcript asks for it as it scrolls within reach of the first row and holds what is on screen in place; the phone asks from FlashList's `onStartReached`. Both keep pages they loaded when a later snapshot arrives. A `tool` message reaches the apps, in snapshots, pages, and `message.*` events, with its name, summary, running state, the first 400 characters of its detail, and a command's `terminal`, and without its arguments and result: the apps show none of that, and a file read or a command's output runs to hundreds of kilobytes. Permission cards likewise omit their reviewed argument payload. A Runner's database keeps the complete rows for later model context and permission handling. The no-Runner mobile core persists only `Message::for_app()` for these rows, so a phone never stores the full arguments or tool result it cannot use.

Memory-service configuration RPCs use `memory.connections.*`, `memory.embeddings.set/remove` and `memory.preferences.get/set`. Status replies select masked known fields and never serialize secrets or unknown config extensions. Bot-bound `memory.service.*` and `memory.operations.*` route through sealed requests to the assigned Runner; existing local `memory.read/write` stays separate. Trusted `memory.pgvector.initialize.*`, `memory.lance.binding/export/import.*` and selected-Runner `memory.embeddings.local.preview/apply/status` use typed one-use, account/Device/revision-bound approvals, never model tools. See [Memory services](memory-services.md).

Guided custom-provider `providers.list_models`, `providers.connect_custom` and `providers.refresh` accept optional `runner_id`; refresh optionally limits work to `kind`. Their selected-Runner sealed verbs are `providers.custom.preview/save/refresh`, admitted through the existing request mechanism. Preview is non-mutating. Save/refresh return revision receipts while authoritative credentials still travel only in the encrypted `credentials` blob. Remote setup waits 60 seconds for the Runner and up to 30 seconds for those revisions to sync. No Runner selection preserves existing non-guided CLI behavior.

All sealed remote request verbs wrap their body in `{ payload, signature }`. The Ed25519 signature binds a domain, request ID, verb, requester signing public key, target Runner, creation time and payload. The three guided provider verbs retain their existing `beans-provider-request-v1` domain and wire format; other verbs use `beans-request-v1`. The shared Runner request dispatcher checks current local paired membership and verifies the signature before executing any verb. A relay-listed Device with missing metadata remains eligible; a claimed `requested_by` inside an anonymous sealed box alone is not authenticated authority. Removed requesters, unsigned bodies and forged signatures reject before dispatch. Previously queued unsigned requests are not re-signed or executed; paired clients must upgrade together for remote requests. This request-body cutover does not change protocol 5, the account format or stored account data. Membership is admission-time authority, not a promise to roll back already-started asynchronous effects. Guided provider membership remains checked through the post-discovery credential commit. Guided clients retain a UUID `custom:setup-*` kind for add retries; exact committed replay returns the same kind and stamp without another catalog request.

Custom credentials and provider statuses add optional `capabilities { context_window?, images?, tools? }`; status deserialization defaults absent declarations. Positive integer context windows and boolean/null support values are validated before HTTP. Omitted saves keep declarations, null clears them, objects replace them. Model statuses carry effective declarations ahead of discovery; declaration status separately lets sheets reopen Unknown/Yes/No choices. This is an additive protocol-5 field, without storage-format or home migration.
