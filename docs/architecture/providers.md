# Providers

**DeepSeek** — API key, streamed through DeepSeek's Anthropic-compatible endpoint (`https://api.deepseek.com/anthropic`, `providers::anthropic`), the one that runs DeepSeek's web search on the server: every request declares Anthropic's `web_search_20250305` tool, and the model's searches stream back as `server_tool_use` and `web_search_tool_result` blocks. `BEANS_DEEPSEEK_MODEL` overrides the model. The API root is the credential's own base URL when the user set one, else `BEANS_DEEPSEEK_BASE_URL`, else DeepSeek's (the key check calls its `/models`, bots its `/anthropic`; a root given with `/anthropic` already is used as is).

**Anthropic** — API key, the Messages API (`providers::anthropic`): `claude-opus-5` by default with adaptive thinking, and Anthropic's `web_search_20260209` and `web_fetch_20260209` tools on every request (the basic variants and no thinking parameter for Haiku 4.5 and the 4.5 generation). `BEANS_ANTHROPIC_MODEL` overrides the model; the API root is the credential's base URL, else `BEANS_ANTHROPIC_BASE_URL`, else Anthropic's.

An API-key credential (`credentials.json`: `api_key`, `base_url?`, `connected_at`) can name a custom API root, for a proxy or a compatible server. Every API-key connect method takes `base_url` beside `api_key`, checks the key against that root, and stores both. Before presenting the macOS provider sheet, the app fetches the saved key and base URL on demand from the local CLI with `providers.api_key { kind }`, so it opens fully populated at its final size. The key is masked by default, with an eye button to reveal or hide it. Connected API-key providers open this sheet through Edit, with Save and Disconnect actions. Snapshots and events carry provider statuses: `providers[].base_url` and a masked `key · url` detail.

Both stream the same way, with the conversation marked for caching (`cache_control` on the system prompt, the last user block, and the turn's cache points, so a turn reads what the last one cached even after many tool calls, since Anthropic looks at most 20 blocks back from a mark; the last tool takes one while fewer than four are used; DeepSeek ignores the marks and caches prefixes on its own), tool arguments streamed eagerly, and a request that fails before it streams retried twice: text, thinking (with its `signature`), `tool_use` blocks, and the server tools' own blocks. A server tool call becomes a `ServerToolStart` / `ServerToolEnd` pair for the Runner's activity rows, and the raw `server_tool_use` and `*_tool_result` blocks stay in the assistant message as `ServerBlock` parts, so when the same turn continues after a function call the model gets its searches, their results, and its sealed thinking back verbatim. A later turn's context is rebuilt from the chat and carries none of it. Opus 5.5, Fable 5.1, and Sonnet 5.5 bind each thinking block to the system prompt, tools, and messages before it and refuse one replayed after they change, so the Runner drops a turn's earlier thinking for those models when the turn compacts and in the memory flush (`anthropic::drop_bound_thinking`).

**OpenCode Zen** — API key, the curated pay-as-you-go gateway rooted at `https://opencode.ai/zen`. `deepseek-v4.1-flash` is the default; the catalog adds each lab's frontier model Zen serves on one of these wires (Gemini's own API is not one, so Gemini is not offered). The Runner follows the endpoint OpenCode publishes for each model, which the catalog carries as the model's `wire`: GPT, Grok, and Muse Spark use `/v1/responses`, Claude uses `/v1/messages`, and DeepSeek, Kimi, GLM, Qwen3.8 Max, MiniMax, and the free Big Pickle use `/v1/chat/completions`. A model the catalog lacks goes by its family's endpoint. `BEANS_OPENCODE_MODEL` and `BEANS_OPENCODE_BASE_URL` override the default model and root.

**OpenCode Go** — API key plus an active Go subscription, rooted at `https://opencode.ai/zen/go`. `glm-5.3-flash` is the default, followed by each lab's frontier model on the plan; the Muse Spark Contributor models, whose discount pays for Meta training on the prompts, are not offered. GPT and Grok use Responses, Qwen and MiniMax use Messages, and GLM, DeepSeek, Kimi, and MiMo use Chat Completions. `BEANS_OPENCODE_GO_MODEL` and `BEANS_OPENCODE_GO_BASE_URL` override the default model and root. Every OpenCode request identifies Beans in `User-Agent` and carries the chat id as `x-opencode-session`, as Go requires for routing and prompt caching; Chat Completions and Responses requests carry it as `prompt_cache_key` too.

**ChatGPT** — subscription OAuth (`providers::chatgpt`, isolated): authorization code with PKCE, the localhost:1455 callback the Codex CLI uses, tokens refreshed by the adapter, and the Codex responses backend for streaming. A refused token request shows the endpoint's own reason, OAuth's `error_description` or OpenAI's `error.message` ("403 Forbidden: Country, region, or territory not supported"; see [proxies](runtime.md)). `BEANS_CHATGPT_MODEL` overrides the model. The chat id goes with every request as `prompt_cache_key` and in the `session-id` header, by which the backend keeps a chat on the server that holds its prompt cache, as the Codex CLI does. Every request carries the backend's built-in `web_search` tool, which searches and reads pages server-side; its `web_search_call` items stream back as `ServerToolStart` / `ServerToolEnd` events (`web_search` with the query, `web_fetch` with the URL for an `open_page`).

**Grok** — production subscription OAuth is disabled pending a verified Beans OAuth/client/referrer contract. Sign-in fails clearly before binding a callback or making network requests; no replacement client id, issuer contract or referrer is fabricated. Loopback wire fixtures remain available. The retained isolated Grok adapter uses the shared Responses wire (`providers::responses`), model catalog and server-tool events; this format change does not alter model ids/scopes, encrypted credential merge or the other providers. Grok models through API-key gateways/custom Responses connections remain separate from subscription sign-in.

**OpenAI Compatible and Anthropic Compatible** — neutral presets in onboarding and Add Provider on Mac, phone, Windows, and Linux ask for a URL and an optional API key. OpenAI Compatible defaults to Chat Completions; Advanced exposes an explicit Responses choice, name, and model selection. Anthropic Compatible defaults to Messages. These actions always add a connection, including when another saved connection has the same display name. New credentials have no integration discriminator. Saved names, stable `custom:*` kinds, keys, model IDs/order, creation times, and bot references remain intact; an existing legacy discriminator retains URL normalization and declared gateway-format translation without a read-time credential rewrite. Setup, preview, and refresh use model discovery alone. Listing reachability is not proof of inference authentication, and each Runner must reach the configured URL.

New setup selects the full discovered chat catalog in server order, including exact callable alias and combo IDs. Advanced customization chooses models and the first/default model; edited selection and default stay unchanged during discovery. A model is excluded only by explicit non-chat metadata (`capabilities.completion_chat: false`, a non-chat `kind`/`type`, or text-free output modalities), never by words in its ID. Nested `capabilities.contextWindow`, `maxOutput`, `vision`, `reasoning`, `tools`, `thinkingFormat`, and `thinkingCanDisable` are saved alongside model-list name, window, output, and modality fields. Sparse discovery preserves absent saved facts; explicit false clears a capability. A tool-free model stays available for tool-free requests, but all three wires reject a tool-bearing request locally when `tools: false`.

Discovered model IDs are opaque: save, bot selection, capability lookup, and inference preserve every nonblank ID verbatim, including surrounding whitespace. Whitespace-only IDs are excluded without rewriting the remaining IDs. Manual-entry controls may trim text the user types before adding a new row; discovered and saved rows are never normalized.

### Guided local server setup

Local server is a blank-URL preset in all three clients. Port 11434 and 1234 are suggestions only. Opening or editing a sheet makes no model request: the user enters the exact base URL, chooses a paired desktop Runner, and presses Check Connection. The selected Runner lists models using the explicit API protocol. Loopback names that Runner, not the phone or another desktop. For a separate model host, use an address reachable from the Runner and configure the server bind address, firewall and proxy bypass without exposing an unauthenticated server publicly.

Guided preview, save and refresh carry optional `runner_id`. A local choice executes on that Runner's core; a remote choice uses sealed `providers.custom.preview`, `providers.custom.save` or `providers.custom.refresh` requests with a 60-second response limit. Remote verbs require a known keyed requesting Device and reject execution on a different or non-desktop Device. There is no requesting-Device fallback. Save commits on the selected Runner through the existing staged credential save; its response carries kind and revision receipts, never credential bytes. The requesting core waits up to 30 seconds for encrypted credential sync before returning editable statuses. A sync timeout reports that the Runner saved but local credentials are still pending.

Provider-only remote request bodies carry `payload` and a Device signature over a domain-separated tuple of request ID, verb, requester, selected target, creation time and payload. The Runner verifies with the current roster Device signing key before discovery; anonymous sealed boxes alone do not authenticate senders. Save and refresh recheck the same Device membership/key after discovery and hold roster membership through credential commit. Other request verbs retain their existing transport.

Each guided adding draft retains a UUID `custom:setup-*` provider kind across ambiguous response or credential-sync timeouts. Exact replay of committed input returns that identity without another HTTP request or credential stamp; changed input edits the same identity. Deleted setup identities reject retries rather than resurrecting a provider. Scoped refresh reconciles matching Mac/desktop drafts with refreshed metadata and newly added selected models, preserving manual selections and default while invalidating older preview replies.

Connection `capabilities` declarations contain optional positive integer `context_window`, and boolean/null `images` and `tools`. Omitted save fields preserve declarations, null clears them, and an object replaces them. Declarations override discovered model facts without changing stored discovery rows; manual and periodic refresh retain declarations. Status models and runtime adapters use the same precedence. Clearing returns to discovered values. Unknown image support remains text-only, and unknown tool support is unverified, retaining the adapter's existing permissive behavior. Tools No refuses tool-bearing bot turns before HTTP; it does not silently delete tools. Tool-free inference remains supported.

Listing proves connectivity/catalog access only, not inference. URL, protocol, key, Runner or declaration changes invalidate a sheet's check and late replies. Unreachable errors name the selected Runner and identify exact URL/port, running server/bind address, firewall and proxy bypass checks. Authentication, invalid catalogs and unsupported listing remain distinct. Discovery never scans ports, follows redirects or tries guessed health routes.

**Custom providers** — user-named connections use `chat-completions` (`providers::openai_compat`, `{base_url}/chat/completions`), `responses` (`providers::openai_responses`, `{base_url}/responses`), or `messages` (`providers::anthropic`, `{base_url}/v1/messages`). The protocol is explicit, not inferred from the name, host, or port. OpenAI wires use an optional bearer; Messages uses optional `x-api-key` plus `anthropic-version: 2023-06-01`, without server tools, eager-tool-streaming, or speculative cache marks. Pasted protocol endpoints and model-list endpoints normalize to the corresponding root; Messages removes a trailing `/v1`. `providers.connect_custom { kind?, name, api, base_url, api_key, models }` adds or edits a connection; kind is `custom:` plus a name slug with a numeric suffix when occupied. Duplicate custom display names are permitted; built-in provider names remain reserved. `providers.list_models` previews the same catalog without saving. OpenAI discovery calls `/models`; Messages calls `/v1/models?limit=1000`, following `has_more`/`last_id` with `after_id` on the same endpoint. Catalogs accept `data`, `models`, or a bare array. Only 404/405 mean unsupported listing and permit manual IDs. 401/403, network failures, malformed lists, redirects, 429, and 5xx fail distinctly rather than saving as if the list were unsupported. Discovery is bounded to 1 MiB across at most 16 pages and a 20-second deadline. Discovery and custom inference clients follow no redirects; URLs require HTTP(S), a host, and no embedded credentials, query, or fragment. Inference streams are capped at 32 MiB and HTTP error bodies at 64 KiB. Custom OpenAI requests omit `prompt_cache_key`. Saves persist a staged credential copy before publishing it in memory or syncing, so failed saves do not mutate the connection.

Custom Chat Completions streams report `sensitive`, `network_error`, and `model_context_window_exceeded` terminal reasons as provider errors, not successful replies. The agent loop stops before dispatching tool calls from such a failed reply. This uses the existing custom connection; provider names and model IDs do not select a different adapter or grant capabilities.

The CLI refreshes saved custom-provider lists every six hours on the elected online Runner (lowest machine id); `providers.refresh` invokes the same pass on demand. Refresh snapshots each provider, discovers models at its normalized endpoint, and appends new chat IDs after saved models while retaining picked/manual IDs and their order. Metadata updates merge only present fields. Missing models stay available. Name, protocol, stored URL, key, and creation time stay unchanged. Unsupported listing changes nothing; any discovery failure leaves that catalog untouched and returns a generic kind-only refresh error. Snapshot comparison lets an intervening edit or deletion win. Only a changed catalog stamps `changed_at`, persists `credentials.json`, encrypts and queues the account credentials blob, and emits status. Persistence failure restores the prior catalog and stamp. `providers.refresh` returns `{ updated: <number of changed providers> }`.
Settings in the Mac, phone, and Windows/Linux apps offers Refresh Models for connected custom providers. It calls `providers.refresh`, reports how many catalogs changed (or that none changed), and shows a generic failure without exposing an API key. Synced credential updates refresh each Device's model picker; a bot's chosen model is not overwritten.


At turn time a custom model uses only this connection's saved capabilities: unknown windows have no model-window compaction threshold, unknown image support sends text/path notes, and unknown thinking formats send no thinking parameter. IDs never supply capabilities from a built-in catalog. `reasoning: true` plus a supported `thinkingFormat` enables controls: `openai` maps to Chat Completions effort words or Responses `reasoning.effort`; Messages supports `claude-adaptive` (`thinking.type: adaptive` plus `output_config.effort`) and `claude-budget` (`thinking.type: enabled` plus a token budget). Explicit allowed Off maps to `none` on OpenAI wires, disabled adaptive thinking or omitted budget thinking on Messages. Legacy gateway formats retain their explicit effort translation. Model status carries the supported levels for all app pickers. Cost is unknown because this connection has no known rates; it is not reported as free. Auto-review and `models.ask()` use the first saved model at its lowest explicitly supported level, otherwise the server default. `beans provider add <name> <base-url> [--api …] [--model …]… [--api-key-stdin]` adds a connection; `beans provider remove custom:<slug>` deletes it.

Budget-based Messages thinking reserves 1024 output tokens for the answer before choosing its thinking budget, so the budget is at most the declared output cap minus 1024. Enabled thinking also needs a minimum budget of 1024: a cap below 2048 is rejected locally with an answer-reserve explanation. This is the app's answer policy, not a claim that the Messages protocol forbids a smaller answer allowance. Default or Off requests without enabled budget thinking do not require that reserve.

Server tool events from any provider become tool rows on the Runner, so the status line reads "Searching the web…" or "Reading the web…" while one runs; `build_context` never replays those rows to the model.

The encrypted bot profile carries `provider`, `model`, and `thinking` as string identifiers; the Runner resolves them against the account's credentials and the model catalog at turn time. A bot whose custom provider was deleted gets the not-connected notice until it moves to another provider or one is added again under that name. `thinking` is one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` (or unset for the provider's default) and is mapped to what the model takes: an `output_config.effort` with adaptive thinking on DeepSeek and current Claude models (Fable 5.1 and Opus 5.5 cannot turn thinking off, so `off` becomes their lowest level; Sonnet 5.5 refuses `disabled`, so its `off` is `between_tools`), a `budget_tokens` on Haiku 4.5, `reasoning.effort` on ChatGPT and API-key Responses, and `reasoning_effort` on OpenAI-compatible gateways. A catalogued model gets the word for its level; `off`, on a model that can stop thinking, is the effort `none` on Responses and `thinking: { type: "disabled" }` on Chat Completions. Each model clamps the choice to its catalogued levels; models with no explicit control receive no parameter. The bot tools that create and edit a teammate take `model` and `thinking` too, held to what the Model and Thinking pickers offer (see [Tools](tools.md)).

The team tools offer the same provider models and thinking levels as the apps' pickers. `create_bot` and `edit_bot` validate a requested model against the built-in catalog or the custom provider's saved list before changing a bot; an invalid model or thinking level changes nothing. Switching providers uses that provider's default model and thinking unless specified, and switching models keeps thinking only when the new model supports it. Editing other profile fields leaves the model untouched.

**The model catalog** (`crates/models`, `beans-models`, a snapshot of models.dev that `beans-agent` re-exports as `beans_agent::models`) knows each offered model's context window, output cap, image support, thinking levels, and rates. It is its own crate so the phone's core, built without the agent, has it too. The snapshot carries its `models`, and every app's Model and Thinking pickers come from them, so a new model is added in the catalog alone. The Thinking picker offers Default and only the levels the bot's model takes, the default model's when the bot has none, and every level the provider has for a model the catalog lacks; a model without levels shows no Thinking picker, and picking another model returns a level the new one does not take to Default. Every assistant message carries `usage.cost`: its dollar fields are the known subtotal, and `known` is true only when all contributing calls have known rates. Missing rates produce unknown cost; explicit zero rates produce known zero. ChatGPT and Grok sign-ins are not billed per token; their known cost is what the work would cost at API rates, not a provider bill. `usage.input` is the input read fresh and `usage.cache_read` the input served from the provider's prompt cache: Messages reports the two apart, and the adapters for Chat Completions and Responses, which count cached tokens inside their input total, take them out of `input`. The Runner adds each turn to the chat's `usage` (`context_tokens` and `context_window` of the last turn, totals of tokens, cost, and turns), kept in the local database and never synced. Chat `cost_usd` retains the known subtotal and `cost_known` records completeness; missing historical completeness is unknown. Side calls preserve this same monetary state without changing context or turn counts. The app gets usage in the snapshot, in `roster.changed`, and as `chat.usage` events. The desktop DM inspectors show "Context 128k of 1M · 13%" and known spend such as "Spent $0.42 · 18 turns"; unpriced work shows "Unknown cost", and mixed work labels the known subtotal with "total unknown".
The CLI keeps the version-1 bundled `crates/models/catalog.json` available offline and checks the selected Beans relay's public `/models/v1.json` for a newer validated catalog. Checks at startup and bootstrap are at most hourly; `models.reload` forces one, and a turn on an unknown built-in model checks at most every five minutes. A 1 MiB response cap, version and UTC time validation, supported model wires and thinking levels, and required review-model mappings protect the runtime catalog. A cached index and its ETag belong only to the relay URL that supplied them; changing relays resets to the bundled snapshot before using that relay's own cache. `BEANS_MODELS_URL` explicitly selects another source and `BEANS_MODELS_FETCH=0` disables network checks. No provider keys or account bearer are sent with public feed requests. Provider adapters hold the model metadata of their turn in an owned snapshot, so a refresh cannot change a running turn.

**Compaction** keeps a long chat inside the window (`beans_agent::compaction`, pi's prompts and cut rule; `BEANS_COMPACTION=0` turns it off): when the transcript a turn rebuilds is estimated above `window - 16k` tokens, or more than 400 messages of the chat are not covered by a summary yet, or a turn's own context grows past the window between model calls (the loop's `prepare_next_turn` hook), or the provider answers that the prompt is too long, the older part is summarized by the same model into a structured checkpoint (goal, progress, decisions, next steps, files touched), about 20k tokens of recent messages stay as they are, and a `Compaction { bot_id, summary, after_message_id }` on the chat (local, per bot) makes every later turn start from the summary and the messages after that one. The summary covers the whole chat since the last one, in pieces of at most the window less twice the reserve, each piece updating the summary of the ones before, so a backlog of any size compacts. A compaction of the context a turn sends (a transcript over the threshold that the turn rebuilds whole, or a context that grows between the turn's model calls) asks the summary inside the conversation instead (`compaction::compact_in_place`): the request is the turn's next one, with its system prompt, tools, thinking, cache points, and messages, and the checkpoint prompt as one more user message that names the message the kept part starts with. The provider's prompt cache serves everything the turn's last request sent, where a summary of the transcript as text pays for all of it again. It falls back to the summary of the transcript when the window leaves under 4,096 tokens for the reply, or the model answers with a tool call, a reply the limit cut off, an error, or anything but the checkpoint. A backlog past what a turn rebuilds, a prompt the provider called too long, and Compact summarize the transcript. The memory flush runs first, the same way (see [Memory](bots.md#memory)). Automatic compaction is silent, as in Grok Bot; the inspector's Context row shows the result, and its Compact button (`chats.compact`) does it by hand with a notice in the chat.

**Retries**: a model call that fails before it streams in a way that reads as transient (overloaded, rate limited, 5xx, a dropped connection) is asked again after a backoff, three times at most on top of the adapters' own HTTP retries; the app hears `job.retry` and the working row reads "Retrying (2 of 3) in 4 s…". A failure that outlasts the retries is the bot's failed bubble, as before.
