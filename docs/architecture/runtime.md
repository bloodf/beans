# CLI (runtime)

Local storage, account format admission, staged scratch preload and mutable startup persistence are described in [Local storage and startup admission](storage-admission.md).


Commands:

- `beans serve` — the app connects here; `beans` alone lists the commands and starts nothing, so a bot's `beans` never starts a second service
- `beans identity new` / `identity restore <phrase>` / `identity show`
- `beans pair` — show a pairing string and wait; `beans pair <string>` joins
- `beans provider set <kind> [api-key] [--base-url <url>]` — connect DeepSeek, Anthropic, OpenCode Zen (`opencode`), or OpenCode Go (`opencode-go`) with an API key, or open the browser sign-in for `chatgpt` (`grok` production OAuth rejects before callback/network pending a verified Beans contract). The key is checked against the API first and read from stdin when omitted. `provider add <name> <base-url> [--api chat-completions|responses|messages] [--model <id>]… [--api-key-stdin]` adds a custom provider, its server checked first; `provider remove <kind>` (a custom provider's kind deletes it) / `provider list`. A running `beans serve` carries out the change over the local websocket; with none, the command changes `credentials.json` itself and runs one sync pass
- `beans mcp list|get|add|add-json|remove|enable|disable|hide|show|sign-in|sign-out|reload|import` — manage [custom MCP servers](mcp-servers.md) in this Runner's private `mcp.json`, through a running local service when available. `mcp add` accepts a command and arguments or a URL, `--transport stdio|http`, repeated `-e`/`--env NAME=VALUE`, repeated `-H`/`--header "Name: value"` for HTTP, `--description` and `--timeout` in seconds. Import skips existing names; explicitly named invalid files or entries fail. List and reload connect enabled servers before reporting health and exit nonzero for invalid or unready servers; disabled servers do not fail health checks.
- `beans marketplace reload` / `beans models reload` — force a check of the configured public feed through the running service, or update its source-bound cache for the next startup. Bundled catalogs remain available offline.
- `beans chats list` / `beans chats set-owner <group> <bot>` — list chats and group owners, or choose a member as owner by case-insensitive title/name or exact id. Ambiguous names require an id. Changes reach the running service over its websocket, or update the local store and run one sync pass.
- `beans status` — account snapshot for local inspection, not a support export.
- `beans doctor` / `beans doctor --json` — the same privacy-safe setup report, rendered as text or JSON. The existing invocation and home/port defaults remain unchanged. Both outputs deliberately disclose the selected relay host and explicit port; userinfo, URL paths, query strings, fragments, account names, keys, local paths, message content and raw errors are omitted. Review before sharing; nothing is uploaded. Only the relay's public health endpoint is probed. Provider checks mean configured credentials, not verified authentication or reachability. Plugin slots are anonymous, report-local ordinals with cached setup states, not live connection checks. Runner rows include only desktop Devices; presence is not admission readiness. Paired versions appear only when they are numeric three-part releases.
- `beans service install` / `uninstall` / `status` — keep `beans serve` running from login on ([Service management](service-updates.md#service-management)).
- `beans self-update` — reports that CLI self-update is unavailable in Beans, before opening account data or making network requests.

The hidden global `--message-format <value>` option is accepted and ignored for Cargo-wrapper compatibility, including when appended after `serve` arguments. It does not change output formatting; unrelated unknown flags remain errors.

Bind: `127.0.0.1:4874` (Beans) or `127.0.0.1:4875` (Beans Dev), selected by `--port` / `BEANS_PORT`; native builds fix their matching isolated port. Relay: `BEANS_RELAY_URL`. A busy port fails loudly.

The `/ws` upgrade checks `Host` before opening the socket: only `localhost:<serve port>` or `127.0.0.1:<serve port>` is accepted, even though the listener binds to loopback. Native clients (the AppKit app and the Go desktop client) send no `Origin` and connect with either host. Browser clients send an `Origin`; the CLI accepts its own HTTP origin or one explicitly listed in `BEANS_ALLOWED_ORIGINS`, a comma-separated list of exact HTTP(S) origins. Invalid entries, paths, prefixes, wildcards, cross-site origins, and mismatched hosts or ports receive HTTP 403 before upgrade. The allowlist is for browser development, not a production default.
Outgoing requests (providers and their sign-ins, the relay, MCP servers over HTTP) use the proxy in `HTTPS_PROXY`, `HTTP_PROXY`, or `ALL_PROXY`, less the hosts in `NO_PROXY`, else the system's: the HTTP and HTTPS proxies in macOS's network settings, or Windows' Internet Options with their bypass list (reqwest's `system-proxy`). So the CLI reaches a provider the way the browser does behind a proxy app set as the system proxy, and a ChatGPT sign-in whose browser half went through the proxy swaps its code through it too; OpenAI refuses the swap from a country it does not serve. Neither a PAC file nor macOS's bypass list is read, so on a Mac with a system proxy a model or MCP server on the computer itself is reached through the proxy as well.

Over HTTPS, those requests, public catalog requests, and the relay's sync socket check certificates with one rustls config per process, from `crates/tls` (`beans-tls`). On macOS and Windows the system decides, through rustls-platform-verifier: the Keychain or the Windows certificate store, as in the browser, so a root an administrator installed for a TLS-inspecting proxy such as Zscaler is trusted. `SSL_CERT_FILE` there names a PEM file of more roots to trust beside the system's; a file that does not read is logged and skipped. On Linux the CLI trusts the system's CA store, or what `SSL_CERT_FILE` and `SSL_CERT_DIR` name in its place (rustls-native-certs), together with the Mozilla roots it carries (webpki-roots), so a container without a CA store still connects. The phone core trusts the carried roots alone. `reqwest::Client::new()` would trust only reqwest's bundled roots, so Device code builds its clients with `beans_tls::client()` or `client_builder()` (HTTP/1.1); the MCP client, on reqwest 0.13, takes `client_config` and offers h2. A provider check or turn whose request fails reads `beans_tls::describe`: reqwest's words, then the last cause in the chain, so a certificate the system does not trust says `invalid peer certificate` where a refused connection says so.

Installation, standalone services and Runner admission drain are described in [CLI service and updates](service-updates.md).

The staged `history164_types` module provides closed history event and producer validation, bounded list/export response codecs, and canonical authenticated cursors. Its HMAC helpers borrow an existing purpose key and host-supplied account namespace, distinguishing `LocalTaskEpoch` from `ImportedAccount` without creating task authority. Response validation binds the cursor to the filter, watermark, last-scanned position and captured host context. This pure module is not connected to live history handlers or SQL storage and performs no filesystem export.

## Diagnostics report

`diagnostics.report` and `beans doctor --json` use the same builder. The report contains `schema_version: 1`, `versions {core, relay_protocol}`, `this_device {os, is_runner, has_identity}`, `home {exists}`, `port {free}`, `relay`, `providers`, `plugins`, `mcp_json` and `runners`. It uploads nothing; consumers must let the user review before sharing.

If local account loading fails, either doctor form exits nonzero, emits no report on stdout, and returns a fixed privacy-safe error on stderr. Doctor omits startup logs and the underlying error chain, including private paths and record values. Storage access and account format must be checked locally; account admission still rejects unreadable, malformed and unmarked populated homes without resetting them. Other commands retain their existing startup error handling.

- `relay {configured, host, reachable, reason, http_status, protocol}` deliberately discloses only the selected host and explicit port. `reason` is `none`, `not_configured`, `invalid_url`, `unreachable`, `update_required` or `http_error`. No raw response/error text enters the report. `reachable` is null when no probe runs, false for transport failure, true when health supplies HTTP evidence. The existing health interface represents malformed/wrong-service/incompatible successful responses as 426; `update_required` does not distinguish those cases from HTTP 426. Health 404 is `http_error`, never an unknown Device. `protocol` contains validated advertised protocol only on success; the interface supplies no relay version.
- `providers {built_in: [{kind, configured}], custom_configured, health: "not_checked"}` contains only fixed built-in kinds and a custom connection count. Custom names/kinds/endpoints and credentials are omitted. Configured does not mean working authentication or reachability. No credential-bearing provider calls run.
- `plugins {basis: "cached_setup_state", entries: [{slot, state}]}` uses report-local one-based slots, not stable identities. State is `ready`, `needs_setup`, `needs_auth`, `connecting`, `error` or `unknown`; arbitrary states/details/names are omitted. Anonymous slots cannot identify a private plugin across reports. No plugin connection is started.
- `mcp_json {servers, problems, file_error}` counts configuration problems, including invalid entries, without echoing validation text or file paths.
- `runners [{is_this_device, os, presence, version}]` excludes phones/tablets. Presence is `online` or `offline`, not work admission/readiness. Untrusted paired version text is null unless it is a numeric three-part release. OS values are allowlisted, with `unknown` for unrecognized local values. A busy local port is a note, not proof of a failed service.

`beans status` and snapshots contain private account data and are not substitutes for this report. The report describes configured providers, cached plugin setup and Runner presence, not verified provider health or work readiness.

## Agent loop

`crates/agent` (`beans-agent`) is a port of pi-agent-core: `run_agent_loop` / `run_agent_loop_continue`, the same event sequence (`agent_start`, `turn_start`, `message_start/update/end`, `tool_execution_start/update/end`, `turn_end`, `agent_end`), steering and follow-up queues, `before_tool_call` / `after_tool_call` / `should_stop_after_turn` hooks, sequential or parallel tool execution, and `terminate` hints from tools, plus pi's harness behaviors: a model catalog with rates and windows, thinking levels, cost on every message, compaction, and turn-level retry. Tool arguments are salvaged from cut-off JSON, coerced and checked against the tool's schema before a call runs (a failure is an error result the model reads), and never run from a message the token limit cut off; a `prepare_next_turn` hook can swap the context or provider between turns. A tool can declare an `output_schema` and return `structured` output beside its text, and return an error result (`is_error`) when a failure has output to go with it. A tool that calls other tools while it runs (`Tool::execute_with`) gets the loop's `ToolRunner`, which puts each call through the same argument shim, schema check, `before_tool_call`, and `after_tool_call` as the model's own, with the calling call as the hooks' `parent`. Every adapter puts the transcript through the same transform first (another model's thinking as text, failed turns left out, a result for every call, images downgraded for a text-only model) and retries a request that fails before it streams. A `Provider` turns a request into a stream of assistant events and never fails: errors become an assistant message with `stop_reason` `error` or `aborted`. The crate also ships `agent::harness::AgentHarness`, a general agent over the loop for hosts other than Beans (model switching through a provider factory, skills and prompt templates, queues, hooks, events, an example chat), with persistence left to the host; the Beans CLI uses the loop directly. `docs/agent/` is the crate's own documentation.

```
on decrypted Job:
  build context from the chat (this bot's turns are assistant, other bots' text is user "[Name]: …",
                               this bot's tool rows become tool_call + tool_result pairs)
    + this turn's notes, which later turns leave out: the recent-work brief, the group's turn cue or
      a finished command's, "Continue." after the bot's own reply, a template bot's setup
    cache points: the rebuilt transcript's end, and where the last turn's ended
  run_agent_loop_continue(context, provider = the account's creds, tools, sink)
    events → job.started / job.finished / job.retry / job.thinking (chat, bot) → local app WS, which shows the bot at work
           → the turn and what it is doing (thinking, a retry) → this Runner's `machine` blob, which every
             other Device's CLI turns into the same events
           → each finished turn's usage → chat.usage (context size, cost so far)
           → a reply grows in chunks, not tokens: the text so far is re-sent at paragraph ends,
             or at a sentence end after 1.5 s of silence, never mid-word; the end sends it complete
           → every chunk and every completed message is encrypted with the account DEK → relay,
             so a paired phone watches the reply grow the way the local app does
    tool calls execute: each call's row goes up as the app sees it when the call starts, for the
                        status line on other Devices, and whole when it ends
  a pending confirmation or a turn ending with a reply or failure → an encrypted phone push (see Notifications)
```

Turns in one chat run one at a time on a Runner. A direct turn registers an `AgentMessageQueue` from `crates/agent` while it owns the chat lock. A new user message goes into that queue, and the agent loop drains it at its next safe boundary: the current provider step and any tool calls finish, then the message is added before the next provider call. Until then the message is `queued`: the Runner marks it before it pushes it and clears it when the turn reads it (the promotion), when a turn starts on it as its trigger, or on Stop, so every Device shows it waiting with Send now under it. `chats.send_now { chat_id, message_id }`, here or sealed to the bot's Runner as a `request`, has the turn read it at once (`turns::send_now`): every command running in the chat goes to the background and runs on (`Sessions::background_chat`, so a call waiting on one returns), then the turn's `StepInterrupt` cancels the step, so a reply in progress stops where it got to (its words stay a bubble) and other tools are cancelled, and the loop reads its queue. Send now is for direct chats. A question never holds a message back: the user's message dismisses whatever the chat's turn is asking them (a command's card or a permission card; `mcp::dismiss_questions`), the action does not run, and the call returns telling the bot the user wrote instead of answering, with a hint that ends the run unless the message is there to read next. A question that would go up while the queue holds a message is dismissed without asking. In a group, where a member's turn has no queue, the dismissed call ends the member's turn, and the room the message admitted answers it. Every message still admits a Job, so delivery survives Device races; the active turn marks messages it actually promotes, and those Jobs exit when they later reach the chat lock. In a group, a newer room waits while the current member settles, then takes the lock before another member starts. `chats.stop` is separate: it cancels active and waiting jobs immediately and sends a sealed `job_cancel` to another Runner.

## Notifications

Replies, failed responses, and pending confirmations reach the user wherever they are not looking.

- **Phones** (`crates/cli/src/push.rs`): when a turn ends with a reply or a failed response, or a question appears (a pending permission card, or a command's card that asks), the Runner seals a notice `{ title: the bot's name, subtitle: the group's title, body: the first 280 characters, chat_id }` and posts it to the relay's `/v1/push`. A post the relay does not take (no answer, `429`, or a `5xx`) goes again 2 s later and then after twice the last wait, until a minute has passed, so a turn that ends while the relay restarts still alerts; a `401` (a relay that restarted with a new `--secret`) signs in again before the next try, and any other `4xx` is final. The envelope is `nonce(12) || ciphertext` of ChaCha20-Poly1305 under the push key with `push` as associated data: the IETF cipher, so iOS opens it with CryptoKit alone. Apple, Google, and the relay see "New reply" and ciphertext. On an iPhone the notification service extension (`mobile/targets/notify`) reads the push key from the app group's keychain, opens `c`, and sets the title, subtitle, body, thread, and `chat_id` before the alert shows; on Android `PushService` in the native module opens it through the core (`push_open(home, c)`, which needs only `machine.json`) and posts the notification. A push that cannot be opened shows the fixed words. Android prebuild and FCM tokens require an operator-supplied `BEANS_GOOGLE_SERVICES_FILE` for the matching Beans application id; the relay’s `--fcm-service-account` belongs to that same Firebase project. No Firebase project or client id is fabricated.
- **The macOS app** (`Notifier.swift`) posts a system notification itself from the CLI's events: a new question (a pending permission card, or a command's card that asks) alerts while the turn waits for an answer; on `job.finished` it takes the bot's last completed or failed response in that turn, for a turn on this Runner or another. A failure shows the error text, including when the bot sent partial output first. Confirmation alerts say what action needs approval; repeated card updates do not repeat the alert, and resolving or removing a card clears its Mac notification. A click brings the app forward on the chat; opening a chat clears what was posted for it. The Dock badge (`AppDelegate.swift`) shows the sum of the chats' unread message counts and clears when that total is zero or the Device has no identity.
- **Read on another Device**: the Runner waits three seconds before asking for a phone push, and the macOS app waits the same interval before posting its notification. Replies, failed responses, and questions (pending permission cards, command cards that ask) each count as unread when they arrive. Both notification paths check the chat's current unread count after the wait; an encrypted `ClearUnread` from a paired Device cancels the alert. A confirmation is checked again for a pending decision, so answering, denying, or expiring it during the wait cancels its alert. They check again after push authentication and before each retry of a push, or after notification permission, and drop a pending alert if its account or chat is gone. This is a grace period for sync: a read mark that arrives after delivery cannot prevent the alert that already showed.
- **Watching**: neither fires for a reply, failure, or confirmation the user watches arrive. The macOS app tells its CLI which chat is on screen while it is frontmost (`ui.watching { chat_id | null }`, cleared when the app disconnects); the Runner skips the push for that chat and the app skips its own notification. The phone app shows no banner for the chat it has open while it is in front. On iOS the notification handler declines it. On Android, where `PushService` posts the notification itself, the JS side hands the native module the chat on screen (`setOpenChat`) and the module follows the activity's resume and pause itself, so a push that lands as the user leaves is not lost behind a busy JS thread; while the app is in front `PushService` posts nothing for that chat, and what it posted for the chat comes down when the chat comes on screen.
- **Phone reads**: the focused chat route sets `openChatId`, and the engine follows the app's foreground state. While both are active, unread counts arriving in roster events or snapshots trigger `chats.mark_read`; returning to the app reads the visible chat too. An inactive or backgrounded phone leaves new replies unread, even while the chat remains mounted. A read mark acknowledges replies already received, so an open chat on a disconnected phone does not suppress later replies.
