# CLI service and updates

Installation, standalone service management and Beans Runner admission drain.

## Installing the CLI

The website's `install-cli.sh` / `install-cli.ps1` download `beans` from stable `beans-v<root version>` releases in `bloodf/beans`. They select macOS arm64, Linux arm64/x86-64 or Windows x86-64, check the adjacent SHA-256 checksum, rename the executable into `~/.local/bin` (or `BEANS_INSTALL_DIR`), and update shell/user PATH unless `BEANS_NO_MODIFY_PATH=1`. `BEANS_VERSION` selects a release; the installed CLI reports its Cargo component version. Linux uses static musl; Windows uses the Universal CRT and Git for Windows' bash (`BEANS_SHELL` can select another shell). See [release and server-update mechanisms](../releasing-cli.md).

Stable publication defaults to server scope, which supplies Linux CLI archives; macOS and Windows standalone installs need `BEANS_VERSION` selecting a full release with their archive. The adjacent checksum is archive-integrity checking, not signed automatic-update readiness. The server updater verifies the schema-1 manifest and detached Ed25519 signature against the Beans public anchor, requires its server/updater inventory, and derives asset URLs from the fixed release repository.

New archives contain Beans-only binaries/names and target fresh `beans-v2` accounts, `.beans-v2` / `.beans-dev-v2` homes and ports 4874 / 4875. Old-format accounts, unversioned backup phrases and mixed paired Devices are incompatible. Service installation is a later explicit operator action, not automatic migration or authorization to replace existing production services.


## Runner update drain

`beans update status|prepare|cancel` talks only to an existing local service. `BEANS_UPDATE_TOKEN_FILE` enables token-authenticated prepare/cancel; without it, mutations are disabled. A renewable lease closes new admission under the same lock used by work producers while existing turns, rooms, routines, routine checks, commands left running, command continuations and remote waits finish. Renewing an unexpired lease retains its id; a restart drops the lease. Status is ready only while a lease is prepared and admitted work and running jobs are empty; it reports the Runner pid, active/jobs counts and remaining lifetime. Cancel or expiry resumes admission and wakes sync. Expiry timers hold a weak App reference, so a timer cannot retain a stopped execution owner or its OS lock; it wakes sync only while that App still exists. Account Pause is unchanged.

On Windows, the shared token reader admits the opened token and its actual containing directory before reading secret bytes. Owner/DACL checks trust the current account and LocalSystem, not Administrators or other account groups. Foreign token read/write and directory mutation/security-control grants, including inherited grants, are refused; absent/null DACLs, unsupported evidence, reparse objects and query failures fail closed. The same reader protects CLI prepare/cancel and server authorization. Refusal changes neither token bytes nor existing ownership/ACLs. Unix retains its opened-file owner/mode policy.

The relay sync cursor stops before an envelope it cannot admit, preserving queued work. While held, sync continues polling controls and completion envelopes: account Pause policy, running-job Stop and requests answering or controlling existing work still apply, as do `job_result` envelopes matching a pending `job_id` and `response` envelopes matching a pending `request_id`. These completions let already-admitted running waits finish under the lease without advancing the held cursor or admitting queued jobs. Unmatched completions and cancellations for jobs not running here remain on the relay for the main pull. Held envelopes replay after the lease ends; policy replays by version and consumed envelopes replay as no-ops, preserving deduplication. The external signed updater upgrades and verifies the relay first, then drains/replaces Runners. Installing this control into an old Runner is an explicit bootstrap operation. Binary/catalog rollback never silently restores an incompatible database.

The macOS app uses this same admission control for installation, not a snapshot-only guard: its launcher supplies the build-home `native-update-token`, and guarded quit takes a 1,800-second lease before rechecking work, signed readiness and actual selected-relay health. Final status, Runner process identity, the conservative monotonic lease deadline and native draft/quit safety must still permit installation. The lease remains held across a postponed Sparkle handoff; failed/canceled quits release it without stopping admitted work. An external CLI needs compatible drain control and the matching native token. See [the macOS updater](macos-app.md) and [native drain prerequisites](../releasing-mac.md#atomic-runner-admission-drain).

## Service management

`beans service install` keeps `beans serve` running from login on and whenever it stops: a launchd agent, `app.beans.serve`, on macOS (log `~/Library/Logs/Beans/serve.log`); a systemd user unit, `beans.service`, on Linux, with lingering (log in the journal); and a Windows Run-key entry starting the `beans service run` supervisor (log `serve.log` in the CLI home). It retains the installing command's home, port and `BEANS_RELAY_URL`, sets `BEANS_SERVICE=1`, and rotates its log above 20 MiB. Installation refuses an already-serving port; Linux requires a systemd user session. It does not install a release or change the Beans signed-update trust anchor.

Every service command first reads what is there and classifies it: a definition Beans wrote (current, or from an older `beans`), one edited by hand or damaged, a same-named systemd unit loaded from another file (`/etc`, `/usr`), a job the service manager still runs after its definition was deleted, a definition never loaded (an interrupted install), and the `beans serve` answering on the service's port. That process identifies itself through `hello` (`version`, `pid`, `executable`): one older than the running `beans`, or whose binary is gone, is a leftover, and `install` and `refresh` stop it (SIGTERM, so it drains, then SIGKILL after 15 seconds; on Windows it is terminated). A `beans serve` of the same version (the app's Runner, or one started by hand), a newer one, or a process that does not identify itself is never stopped: `install` refuses while one holds the port and is not the service's own, and `status` reports it. No process is stopped on a PID alone without that answer, and never the command's own process or its parent.

`install` stops any earlier job before writing, so two never run at once, and replaces whatever holds the service's name: a definition edited by hand is overwritten, and a same-named unit in `/etc` or `/usr` is overridden by Beans's unit in `~/.config/systemd/user`, which takes precedence (start verifies that systemd loads Beans's file). `uninstall` removes every state an earlier command left, including an orphaned job and a Windows PID record whose process is gone; a unit elsewhere is stopped and disabled, since Beans cannot delete it. `status` names each problem. Definitions are written whole (a temporary file renamed into place). When stopping a leftover, writing or starting the new definition fails, the previous definition is restored and, if it was running, restarted; a first install that fails leaves nothing behind.

`beans service refresh` brings an installed service onto the running `beans`, keeping the home, port and relay its definition names, and changes only what needs it: it rewrites a definition that runs another program or an older format, restarts the service only when its definition changed, its process is an old `beans` (a binary replaced under it) or it keeps failing to start, leaves a healthy service running and a stopped one stopped, and never moves a service onto an older `beans` than the one it runs. A definition Beans did not write is replaced with the command's own home, port and relay; a same-named unit elsewhere is overridden only when it is a Beans definition. An old `beans serve` left on the port stops whether or not a service is installed. With nothing to do it does nothing, so it runs at every launch of the app and after every CLI install: `install-cli.sh` and `install-cli.ps1` run it after replacing `beans` (when the installed release has it). On Windows, the installer renames the running `beans.exe` aside as `beans.exe.old-<32 hex digits>`; a supervisor running from such a sibling of the Run key's program (with the same process creation time and home-bound command line) is recognized as this home's supervisor, so it can be stopped and its file removed.

Before a leftover is stopped, the operating system must confirm the PID: its binary (`/proc/<pid>/exe`, `proc_pidpath`, or the Windows process image) must be named like `beans` and be the binary the process reported, allowing for a binary deleted since it started. PIDs 0 and 1 are never stopped. The port probe gives up after four seconds however the peer answers (silence, a trickle, events without a reply) and refuses replies over 64 KiB. Read-only questions to launchd and systemd are bounded to ten seconds. `install`, `refresh` and `uninstall` take a per-user lock (in the cache folder, or the temporary folder when that cannot be written), so the app's launch and an installer take turns; a held lock is waited for, never stepped around.

A relative `BEANS_HOME` is written absolute, from the folder the installing command ran in, since launchd, systemd and a Windows sign-in start the service elsewhere. `install` refuses a `beans` running from somewhere that goes away (macOS App Translocation, a mounted disk image, an AppImage mount, the temporary folder, or a binary Linux reports deleted), and `refresh` from one leaves the service's program as it is. On macOS a job is bootstrapped into the login session's domain, or the user's domain where there is no GUI session (a Mac reached over SSH), after clearing a leftover `launchctl disable`. On Linux, systemd drop-ins for the unit are reported and kept. On Windows the Run key names the program by its plain path (`C:\…`) whenever that means the same file as the canonical verbatim one (`\\?\C:\…`), and a `service.pid` whose PID now belongs to a process created later (PIDs are reused, and a record can outlive a restart) is stale: nothing runs for it, and the other process is untouched.

Windows service effects first admit the selected home read-only. The supervisor records its PID, OS process creation time and canonical home in `service.pid`; stopping also verifies the OS executable and the explicit home-bound `service run` command. It terminates the verified held process handle, not an arbitrary live PID. A supervisor-owned kill-on-close job contains its child tree, so stopping that supervisor closes only its own descendants. Fresh installation establishes the core format before service-file writes; incompatible homes and mismatched live process records are refused untouched.

Every Device’s `machine` blob carries its core version. Beans leaves optional CLI `update` status absent. Standalone self-update is unavailable even with compile-time `BEANS_SELF_UPDATE`: checks, discovery and install entry points reject before effects. `device.update` / `device.auto_update` reject locally without sealing remote requests, and incoming `self_update.install` / `self_update.auto` reject independently. Local `update.status|prepare|cancel` drain and Beans signed app/server update trust remain unchanged.
