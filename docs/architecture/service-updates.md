# CLI service and updates

Installation, standalone service management and Beans Runner admission drain.

## Installing the CLI

The website's `install-cli.sh` / `install-cli.ps1` download `beans` from stable `beans-v<root version>` releases in `bloodf/beans`. They select macOS arm64, Linux arm64/x86-64 or Windows x86-64, check the adjacent SHA-256 checksum, rename the executable into `~/.local/bin` (or `BEANS_INSTALL_DIR`), and update shell/user PATH unless `BEANS_NO_MODIFY_PATH=1`. `BEANS_VERSION` selects a release; the installed CLI reports its Cargo component version. Linux uses static musl; Windows uses the Universal CRT and Git for Windows' bash (`BEANS_SHELL` can select another shell). See [release and server-update mechanisms](../releasing-cli.md).

Stable publication defaults to server scope, which supplies Linux CLI archives; macOS and Windows standalone installs need `BEANS_VERSION` selecting a full release with their archive. The adjacent checksum is archive-integrity checking, not signed automatic-update readiness. The server updater verifies the schema-1 manifest and detached Ed25519 signature against the Beans public anchor, requires its server/updater inventory, and derives asset URLs from the fixed release repository.

New archives contain Beans-only binaries/names and target fresh `beans-v2` accounts, `.beans-v2` / `.beans-dev-v2` homes and ports 4874 / 4875. Old-format accounts, unversioned backup phrases and mixed paired Devices are incompatible. Service installation is a later explicit operator action, not automatic migration or authorization to replace existing production services.


## Runner update drain

`beans update status|prepare|cancel` talks only to an existing local service. `BEANS_UPDATE_TOKEN_FILE` enables token-authenticated prepare/cancel; without it, mutations are disabled. A renewable lease closes new admission under the same lock used by work producers while existing turns, rooms, routines, routine checks, commands left running, command continuations and remote waits finish. Renewing an unexpired lease retains its id; a restart drops the lease. Status is ready only while a lease is prepared and admitted work and running jobs are empty; it reports the Runner pid, active/jobs counts and remaining lifetime. Cancel or expiry resumes admission and wakes sync. Account Pause is unchanged.

The relay sync cursor stops before an envelope it cannot admit, preserving queued work. While held, sync continues polling controls and completion envelopes: account Pause policy, running-job Stop and requests answering or controlling existing work still apply, as do `job_result` envelopes matching a pending `job_id` and `response` envelopes matching a pending `request_id`. These completions let already-admitted running waits finish under the lease without advancing the held cursor or admitting queued jobs. Unmatched completions and cancellations for jobs not running here remain on the relay for the main pull. Held envelopes replay after the lease ends; policy replays by version and consumed envelopes replay as no-ops, preserving deduplication. The external signed updater upgrades and verifies the relay first, then drains/replaces Runners. Installing this control into an old Runner is an explicit bootstrap operation. Binary/catalog rollback never silently restores an incompatible database.

The macOS app uses this same admission control for installation, not a snapshot-only guard: its launcher supplies the build-home `native-update-token`, and guarded quit takes a 1,800-second lease before rechecking work, signed readiness and actual selected-relay health. Final status, Runner process identity, the conservative monotonic lease deadline and native draft/quit safety must still permit installation. The lease remains held across a postponed Sparkle handoff; failed/canceled quits release it without stopping admitted work. An external CLI needs compatible drain control and the matching native token. See [the macOS updater](macos-app.md) and [native drain prerequisites](../releasing-mac.md#atomic-runner-admission-drain).

## Service management

`beans service install` keeps `beans serve` running from login on and whenever it stops: a launchd agent, `app.beans.serve`, on macOS (log `~/Library/Logs/Beans/serve.log`); a systemd user unit, `beans.service`, on Linux, with lingering (log in the journal); and a Windows Run-key entry starting the `beans service run` supervisor (log `serve.log` in the CLI home). It retains the installing command's home, port and `BEANS_RELAY_URL`, sets `BEANS_SERVICE=1`, and rotates its log above 20 MiB. Installation refuses an already-serving port; Linux requires a systemd user session. It does not install a release or change the Beans signed-update trust anchor.

Windows service effects first admit the selected home read-only. The supervisor records its PID, OS process creation time and canonical home in `service.pid`; stopping also verifies the OS executable and the explicit home-bound `service run` command. It terminates the verified held process handle, not an arbitrary live PID. A supervisor-owned kill-on-close job contains its child tree, so stopping that supervisor closes only its own descendants. Fresh installation establishes the core format before service-file writes; incompatible homes and mismatched live process records are refused untouched.

Every Device’s `machine` blob carries its core version. Beans leaves optional CLI `update` status absent. Standalone self-update is unavailable even with compile-time `BEANS_SELF_UPDATE`: checks, discovery and install entry points reject before effects. `device.update` / `device.auto_update` reject locally without sealing remote requests, and incoming `self_update.install` / `self_update.auto` reject independently. Local `update.status|prepare|cancel` drain and Beans signed app/server update trust remain unchanged.
