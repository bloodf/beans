# Realtime voice evaluation

## Status and decision

This is a source-only evaluation for [#133](https://github.com/bloodf/beans/issues/133), recorded on 2026-10-13 against Beans `135b2295469614202d3e48f7316f7b7423efe712`. It does not implement or enable voice. Independent review, live measurements, and the platform/package license audit remain pending. The evaluation is not a completed realtime release gate.

**Recommendation for further evaluation:** reuse platform capture/recognition and local playback around the existing Beans Runner agent loop. Require an explicitly selected local recognition mode before describing audio as local-only. Keep hosted speech optional, with consent naming every recipient. Do not import a separate agent runtime or turn the Beans relay into a plaintext voice service.

- **tinyvoiceagents: no-go at the inspected pin.** It is a Rust module template, not an implemented voice stack.
- **tinyliveagents: conditional candidate for optional hosted speech, no adoption yet.** Its Rust provider adapter has useful session events, but all implemented providers require network services. It does not establish local/offline speech or Beans approval integration.
- **OpenDots: reference only, no-go for wholesale import.** Its MIT call controls and compute separation are useful evidence. Its conversation infrastructure and direct browser-to-provider audio path do not match Beans' local-CLI boundary.
- **Platform speech APIs: conditional candidate, not a universal offline solution.** Apple and Android expose on-device recognition controls. Availability, installed language assets, continuous-session behavior, local synthesis, and device-specific echo cancellation need validation. Windows/Linux support is not established by the existing Beans dictation docs.

## Current Beans boundary

[macOS chat](macos-chat.md) describes `Speech` and `AVAudioEngine` dictation into the composer. [Phone app](phone-app.md) describes `expo-speech-recognition` dictation. Neither is two-way realtime voice. The inspected `macos/Sources/Beans/Chat/Dictation.swift` creates `SFSpeechAudioBufferRecognitionRequest` without setting `requiresOnDeviceRecognition`; current macOS dictation is therefore not evidence of enforced local-only recognition. `mobile/src/ui/dictation.ts` selects languages, not a complete audio privacy policy.

The desktop app speaks to its local CLI. The CLI owns inference, tools, cancellation and approvals. Phones are Devices, never Runners. [Identity](identity.md) describes account-encrypted provider credential sync and opaque relay blobs; this encryption does not hide audio or transcript plaintext from a speech/model endpoint receiving it. Every paired Device holds account credentials; do not describe those credentials as existing only on one Runner.

A future platform pipeline is: Device microphone and recognition, authenticated core transport to the assigned Runner, ordinary bot inference, returned text, Device synthesis/playback. Local desktop UI/core traffic uses localhost. Existing cross-Device jobs and messages use sealed/encrypted relay traffic; a realtime audio transport is not implemented and must not be inferred from that text transport. Prefer sending finalized text rather than raw audio to the Runner when recognition runs on the Device.

[Runtime](runtime.md#agent-loop) distinguishes playback interruption from job cancellation. `chats.stop` cancels active/waiting jobs; it is not the default meaning of speaking over playback. Ordinary new chat messages can dismiss pending permission questions without approving them. The future voice path must additionally ensure that spoken “yes” or “approve” leaves an approval card pending until an explicit tap/click, as required by [#135](https://github.com/bloodf/beans/issues/135). Merely routing every utterance through ordinary `chats.send` does not prove that requirement.

### tinyvoiceagents

- [LICENSE](https://github.com/tinyhumansai/tinyvoiceagents/blob/73d17dee410890a9d150ac9096dfda6f8e412148/LICENSE): GNU GPL version 3; [Cargo.toml](https://github.com/tinyhumansai/tinyvoiceagents/blob/73d17dee410890a9d150ac9096dfda6f8e412148/Cargo.toml) declares `GPL-3.0-only`, Rust 2024, Rust 1.88, workspace version `0.2.1`.
- [README](https://github.com/tinyhumansai/tinyvoiceagents/blob/73d17dee410890a9d150ac9096dfda6f8e412148/README.md) identifies the project as “Rust Template”. The manifest points at `rust-template` and contains `template-bus`, TinyBus module integration, serde and tokio dependencies.
- [Entry point](https://github.com/tinyhumansai/tinyvoiceagents/blob/73d17dee410890a9d150ac9096dfda6f8e412148/crates/template/src/lib.rs) exports greeting/template behavior. The inspected tree has no implemented capture/VAD/STT/model/TTS/playback voice pipeline.

There is no voice network path or voice retention implementation to evaluate at this pin. That absence is not an offline voice capability. Echo cancellation, barge-in, latency and voice cost are not applicable to the template. Reconsider only after a new pinned implementation and license/dependency review.

### tinyliveagents

Revision: `e10e6eb2a6cd3d6b45f720f2562d4ee88634af78`.

- [LICENSE](https://github.com/tinyhumansai/tinyliveagents/blob/e10e6eb2a6cd3d6b45f720f2562d4ee88634af78/LICENSE) is GNU GPL version 3; [workspace manifest](https://github.com/tinyhumansai/tinyliveagents/blob/e10e6eb2a6cd3d6b45f720f2562d4ee88634af78/Cargo.toml) declares `GPL-3.0-only`, Rust 2024, Rust 1.88 and version `0.1.0`.
- [Crate manifest](https://github.com/tinyhumansai/tinyliveagents/blob/e10e6eb2a6cd3d6b45f720f2562d4ee88634af78/crates/tinyliveagents/Cargo.toml): unpublished library; default features `gemini`, `elevenlabs`, `sarvam`. Dependencies include tokio, tokio-tungstenite `0.29`, serde, base64, tracing, and optional reqwest for Sarvam.
- [README](https://github.com/tinyhumansai/tinyliveagents/blob/e10e6eb2a6cd3d6b45f720f2562d4ee88634af78/README.md) and [entry point](https://github.com/tinyhumansai/tinyliveagents/blob/e10e6eb2a6cd3d6b45f720f2562d4ee88634af78/crates/tinyliveagents/src/lib.rs) expose `LiveProvider`, `LiveSession`, audio/transcript/tool/interruption events. Capture and playback belong to the host. The library does not execute tools, mint tickets, store credentials, or enforce approval/persistence policy.

The proposed host-side path is Device capture, separately authorized Device-to-Runner audio transport when needed, Runner adapter/provider sockets, returned audio, Device playback. This transport and lifecycle integration are not present in Beans.

| Adapter | Network hops and plaintext recipients | Recognition/model/synthesis and interruption |
| --- | --- | --- |
| Gemini direct | Runner WSS to `generativelanguage.googleapis.com`; Google receives microphone PCM, instructions, text/context, tool declarations/results and generates output audio/transcripts. | Native live audio, server VAD; 16 kHz input, 24 kHz output. | Gemini relay | Host ticket-mint service, then Runner WSS to the supplied relay URL, then Google. | ElevenLabs | Runner WSS to `api.elevenlabs.io/v1/convai/conversation` using agent id/key or a signed URL. A minting backend receives authorization/session metadata; any actual proxy adds another potential plaintext recipient. ElevenLabs receives audio and agent/session context. | Sarvam cascade | Runner WSS to `api.sarvam.ai/speech-to-text-realtime/ws`, HTTPS to `/v1/chat/completions`, WSS to `/text-to-speech/ws`. Sarvam receives raw input audio, recognized text, model context/tool data, and text to synthesize. | Server STT/VAD, streamed chat, streamed TTS. Speech-start or explicit interrupt aborts its active turn and emits interruption/tool-cancellation events. |

Important limits: Gemini and ElevenLabs codecs do not encode `ClientCommand::Interrupt` as a provider cancel command; server detection and local playback control remain necessary. Sarvam keeps in-memory conversation history and its own cascade model loop, which cannot replace the Beans bot loop by assumption. [Transport driver](https://github.com/tinyhumansai/tinyliveagents/blob/e10e6eb2a6cd3d6b45f720f2562d4ee88634af78/crates/tinyliveagents/src/transport/driver.rs) closes provider sockets, not the host microphone. No microphone acoustic echo canceller is established by these provider adapters. None provides a fully offline pipeline. Provider retention, training use, deletion and subprocessor settings remain unverified; a source library's lack of transcript persistence is not a provider no-retention guarantee.

### OpenDots

Revision: `625452e06cde74cb25b0ce319e2c1be0488f5a5f` (the issue's recorded pin).

[LICENSE](https://github.com/CopilotKit/OpenDots/blob/625452e06cde74cb25b0ce319e2c1be0488f5a5f/LICENSE) and [package.json](https://github.com/CopilotKit/OpenDots/blob/625452e06cde74cb25b0ce319e2c1be0488f5a5f/package.json) declare MIT. The manifest describes a Node 24+ application with React, Vite, CopilotKit runtime/Threads/Channels, and TanStack AI dependencies. That application license does not establish licensing for CopilotKit Intelligence deployment or remote model services.

[Client `useVoice.ts`](https://github.com/CopilotKit/OpenDots/blob/625452e06cde74cb25b0ce319e2c1be0488f5a5f/src/client/useVoice.ts) captures with `getUserMedia({ audio: true })`, creates an `RTCPeerConnection`, and handles provider events over an `oai-events` data channel. [Server `voice.ts`](https://github.com/CopilotKit/OpenDots/blob/625452e06cde74cb25b0ce319e2c1be0488f5a5f/src/server/voice.ts) sends SDP, model, instructions and conversation history to `https://api.openai.com/v1/realtime/calls` using a server-held key. The browser then exchanges audio with the provider through WebRTC. TLS/WebRTC protect transport, not plaintext from the provider. Provider-side semantic VAD sets `interrupt_response: true`; input transcription selects `gpt-4o-mini-transcribe` at this pin.

Network/data path: browser microphone to OpenAI; browser SDP to the application server to OpenAI; captions/tool request and recent transcript to the application server; `ask_compute` to the separate compute agent; conversation/tool/run events to the configured Intelligence deployment; context/results to the configured compute model; results back through the server/browser to OpenAI for spoken response. A hosted Intelligence operator and compute model are additional plaintext recipients. Local Intelligence does not make OpenAI audio or a remote compute model local. The [README](https://github.com/CopilotKit/OpenDots/blob/625452e06cde74cb25b0ce319e2c1be0488f5a5f/README.md) also identifies separate SDK telemetry and opt-out controls.

[Workspace storage](https://github.com/CopilotKit/OpenDots/blob/625452e06cde74cb25b0ce319e2c1be0488f5a5f/src/server/workspace.ts) persists call transcripts/status in SQLite. The client posts up to 20,000 transcript characters on end; receipts/conversation persistence therefore exceed transient captions. Raw media storage is not established by these inspected files; OpenAI retention is not audited here. Browser capture does not explicitly configure echo cancellation constraints, so effective browser/device behavior needs testing. Cleanup stops tracks and closes peer/data channel, but the end flow first disables tracks while waiting for server hang-up; disabling a track is not proof that the OS microphone indicator immediately turns off.

The README reports upstream live call/control/receipt verification but explicitly leaves spoken compute delegation and Slack connected-service verification pending. Those upstream claims are not Beans acceptance or measured Beans latency/cost. Reuse the separation of voice and compute and visible receipts as a design reference, not its application runtime or plaintext persistence model.

## Platform APIs and privacy choices

Platform APIs are proprietary OS services under their respective SDK/service terms, not dependencies licensed by the three repositories above. No reproducible OS build, SDK revision, speech asset revision, or mobile wrapper license audit is recorded in this evaluation. Those pins/licenses are pending before implementation approval. Official references are inspected on 2026-10-13; mutable reference pages are not immutable implementation pins.

- **Apple:** [supportsOnDeviceRecognition](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition) reports capability; [requiresOnDeviceRecognition](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition) requests audio stay on-device but is honored only when support is true. A strict local mode must refuse unavailable recognition instead of silently using Apple servers. Otherwise audio can go to Apple; permission alone is not local-only consent. Capture/VAD/recognition and synthesis availability remain separate concerns.
- **Android:** [SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer) warns that the default implementation likely streams audio remotely and is not intended for continuous recognition. `isOnDeviceRecognitionAvailable` and `createOnDeviceSpeechRecognizer` provide a distinct on-device path, subject to device/language assets. Do not treat an offline preference as a fail-closed guarantee. The selected recognition service/vendor and any remote endpoint must be disclosed. Destroy the recognizer when no longer needed.
- **Windows:** [SpeechRecognizer](https://learn.microsoft.com/en-us/uwp/api/windows.media.speechrecognition.speechrecognizer) distinguishes supported grammar languages from predefined web-service topic languages. This is not proof of offline arbitrary dictation in the Beans desktop app. Validate the exact recognition and installed voice path before choosing it.
- **Linux:** no shared native arbitrary-dictation implementation is established in the inspected Beans subjects. A separately selected local engine/model would need its own license, pinned assets, install consent and runtime tests. No engine is selected or installed here.

| User choice | Plaintext outside the speaking Device | Retention and offline consequence |
| --- | --- | --- |
| Strict local speech, local Runner model | Finalized text reaches a different assigned Runner when selected; no speech/model cloud recipient. Relay carries only existing encrypted text/job traffic. | Proposed: no raw audio or session transcript archive; committed chat messages retain normal Beans persistence. Entire pipeline offline only when all assets/model compute are local and the required Device-to-Runner path works without internet. |
| Local speech, chosen remote model | Model provider receives finalized text/context/tool results; raw microphone audio remains local only after recognition/synthesis validation. | Provider text retention remains separate from Beans encrypted sync. This is not an entirely local conversation. |
| Platform remote recognition | Apple or the selected Android/Windows recognition service receives audio; chosen model receives text/context. | Provider storage/training/deletion terms are pending. No automatic fallback from strict local mode. |
| Hosted realtime or cascade | Google, ElevenLabs, Sarvam or OpenAI receives the data described above; any voice proxy/mint service and separate compute/storage providers must be named. | Network required. Provider retention/cost unknown until independently checked for the actual account and model. No hosted service is mandatory. |

For [#134](https://github.com/bloodf/beans/issues/134), consent must precede microphone capture and name audio, captions, context and tool-result recipients separately. Keep voice off by default, with zero voice requests while off. Credentials reuse the encrypted account mechanism without exposing long-lived provider keys in UI snapshots or transcript receipts. Raw audio storage stays off by default; captions are transient unless explicitly committed to chat. New transcript archives, diagnostics containing content, model downloads and additional recipients require separate disclosure/approval. Provider failures never trigger an undisclosed cloud fallback.

## Pending live evidence and fixed-fixture protocol

No latency, interruption, accuracy, price, energy or OS-indicator measurement exists in this evaluation. No zero-cost claim is made. Future measurement requires explicit authorization for any paid call, capture, download, host/device probe or service deployment.

Freeze a fixture bundle before comparing candidates: user-owned English and Simplified Chinese utterances, exact transcripts, a long-task request, a typed follow-up, spoken “yes”/“approve”, silence, noise and overlapping speech. Record SHA-256 hashes, PCM16 mono source at 16 kHz, exact resampling, overlap offsets, volume, and expected assertions. Do not synthesize fixtures through a paid service by default. Freeze OS/device/audio route, SDK/library/model and asset revisions, language, endpoints, network conditions and provider account policy. Repeat the same fixtures on headphones and speakers; separate cold startup from warmed sessions.

Use at least 30 measured trials per candidate/configuration after separately recorded warmups. Record monotonic timestamps and raw per-trial values, failures and timeouts; publish p50/p95/max without dropping failed trials:

1. **First audio:** end of known input speech to first audible output sample, not first API event. Also report connection setup, recognition finalization and model first-output components.
2. **Interruption:** known overlapping speech onset to last audible assistant sample; include local detection, provider interruption, buffer flush and audio-device drain. Record echo-triggered false interruption and self-transcription rates.
3. **Lifecycle/concurrency:** hang-up, backgrounding and crash release capture/streams and turn the OS indicator off; typing reaches the same bot turn; completed work remains in chat. Spoken approval words do not resolve or dismiss a pending permission card. No duplicate tool effect is assumed merely because a request is cancelled.
4. **Privacy/offline:** authorized network observation confirms declared recipients and zero voice traffic while disabled/consent declined. Deny network in strict local mode; missing assets/service failure must fail closed. Inspect authorized redacted receipts/logs for unintended audio/transcript/key persistence.
5. **Cost:** collect actual provider usage and account pricing dated at the run, including STT/TTS, model tokens/audio, idle time, proxies, storage and compute. Report per fixture and per conversation minute with currency, exclusions and failed-call charges. Missing usage or prices remain unknown.

Release bounds are not invented from source inspection. Agree numerical first-audio/interruption targets before running the protocol, then choose only candidates whose raw evidence meets them across supported devices/languages. Existing source tests and upstream recordings do not replace these measurements. [#135](https://github.com/bloodf/beans/issues/135) and [#136](https://github.com/bloodf/beans/issues/136) remain subject to their lifecycle, approval, duplicate-request and receipt contracts.
